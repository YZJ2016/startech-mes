# 工位终端页面布局审查

- 日期：2026-10-09
- 范围：`kuaigeyun-mes/riveredge-frontend/src/apps/kuaizhizao/station/**` 与工位入口下挂载的 kiosk 页面
- 依据：`docs/03.design/20.station-terminal-plan.md`；本文只描述页面形态、场景问题和推荐布局，不写实现任务清单
- 代码前提：现有 `TouchScreenTemplate`、`hmi.css`、`touchButtonProps`、`TouchListItem`、`TouchChip`；不改接口契约、权限模型与业务语义

## 1. 审查目标

工位终端不是普通后台表单页。操作员通常站立、戴手套、使用扫码枪或触摸操作，页面必须让“下一步做什么”一眼可见。

统一目标：

- 主任务占据首屏中心区域，低频动作不抢占主操作面。
- 列表、对象选择、录入、确认分层：左边选对象，右边执行或录入。
- 未确认操作员时允许查看，写动作明确禁用并提示原因。
- 每个子页都有明确的“返回工位入口”，且返回时保留已绑定工位上下文。
- 同屏按钮使用同一套触控尺寸；危险动作与主确认动作有明确视觉差异。
- 屏幕宽度不足时从双栏降为单列，避免横向挤压。

## 2. 通用页面骨架

### 2.1 推荐骨架

```text
┌──────────────────────────────────────────────────────────────┐
│ 页面标题 / 当前业务名                                         │
├──────────────────────────────────────────────────────────────┤
│ 状态与低频控制：返回、刷新、开关、操作员/工位提示              │
├───────────────────────────┬──────────────────────────────────┤
│ 对象选择区                 │ 执行 / 录入 / 结果区              │
│ 工单、工序、物料、人员     │ 数量、原因、按钮、反馈、最近记录    │
│ 可滚动列表                 │ 可滚动内容                        │
└───────────────────────────┴──────────────────────────────────┘
```

### 2.2 不应使用的形态

```text
┌──────────────────────────────────────────────────────────────┐
│ 返回按钮                                                      │
│ 提示 1                                                        │
│ 提示 2                                                        │
│ 对象选择                                                      │
│ 很长的录入表单                                                │
│ 很长的记录列表                                                │
│ 底部纵向堆叠的多个按钮                                        │
└──────────────────────────────────────────────────────────────┘
```

问题：操作员需要频繁滚动才能确认上下文；同权重的按钮堆叠会稀释主操作；列表和表单争抢同一纵向空间。

## 3. 场景审查与示例

### 3.1 工位入口：身份与工单入口

场景：终端账号已登录，操作员先确认身份，再扫工单或从派工列表进入报工。

推荐形态：

```text
┌──────────────────────────────────────────────────────────────┐
│ 工位 A01 │ 操作员 张三 │ 终端账号 STATION-01 │ 已确认          │
├───────────────────────────┬──────────────────────────────────┤
│ 操作员身份                 │ 工单入口 / 我的派工               │
│ 选择员工 / 候选人确认       │ 扫码或输入工单编号                 │
│ 员工码 / 刷脸 / 更换操作员  │ 派工列表：工单 → 报工 / 详情       │
├───────────────────────────┴──────────────────────────────────┤
│ 生产执行 │ 作业资料 │ 现场处理 │ 终端管理                       │
└──────────────────────────────────────────────────────────────┘
```

已修正点：

- 首页不再直接铺开全部员工名单，员工通过按需抽屉搜索。
- 候选人、已确认操作员、无确认状态在顶部和左侧面板同时可见。
- “安灯”作为现场处理动作，视觉权重高于普通导航但低于当前生产动作。
- “切换工位 / 绑定工位”归入终端管理，不与报工入口混放。

### 3.2 工位执行：选工单，再操作工序

场景：操作员先从左侧选择可执行工单，再在右侧对工序开工、暂停、恢复、结束、上下机。

推荐形态：

```text
┌──────────────────────────────────────────────────────────────┐
│ 工位执行                  [返回] [SOP] [资质] [刷新工单]       │
├───────────────────────────┬──────────────────────────────────┤
│ 可执行工单                 │ 工单 MO-001 的工序                 │
│ MO-001 产品A 数量100       │ 10 备料 待开工 [开工][暂停][上机]  │
│ MO-002 产品B 执行中        │ 20 加工 进行中 [暂停][结束][下机]  │
│ 加载更多                   │ 暂停原因：缺料/故障/换模/休息      │
└───────────────────────────┴──────────────────────────────────┘
```

已修正点：

- 工单列表与工序操作不再纵向争抢同一区域。
- 左侧固定承担“选对象”，右侧固定承担“执行动作”。
- SOP 与资质仍是页面级开关；未确认操作员时写动作禁用。
- 暂停原因只在该工序暂停模式下显示，不长期占用页面。

风险保留：工序动作较多，右侧应继续优先展示当前状态的可用动作；后续可考虑按状态隐藏不可能动作，但需要先核对后端状态契约。

### 3.3 快捷报工：先确定对象，再填数量

场景：操作员选择本人/小组、加载工单和工序，然后提交数量；有报工记录时才出现上下料/报废。

推荐形态：

```text
┌──────────────────────────────────────────────────────────────┐
│ 快捷报工                                             [返回]   │
├───────────────────────────┬──────────────────────────────────┤
│ 报工对象                   │ 数量与提交                         │
│ [本人] [小组]              │ 合格数 / 不良数 / 工时             │
│ 工单编号 [加载工单]         │ 不良原因 / 备注                    │
│ 工序选择                   │ [提交报工]                         │
│                           │ 报工记录：上料 / 下料 / 报废        │
└───────────────────────────┴──────────────────────────────────┘
```

已修正点：

- “报工对象”和“数量提交”拆成左右两列，减少表单上下往返。
- 上料、下料、报废只在生成报工记录后出现。
- 工单编号输入框和主提交按钮使用触控尺寸。

注意：小组选择器内部控件仍沿用现有组件；没有为本次布局改动重写选择器业务逻辑。

### 3.4 安灯：左侧发起，右侧处置

场景：操作员选择安灯类型和上下文，发起呼叫；班组长或处理人查看未响应和历史记录。

推荐形态：

```text
┌──────────────────────────────────────────────────────────────┐
│ 现场安灯                                             [返回]   │
├───────────────────────────┬──────────────────────────────────┤
│ 发起安灯                   │ 未响应                            │
│ [质量][设备][物料][主管]   │ 设备故障 · A01 · 10:21 [响应]      │
│ 上下文：工单/设备/通知人    │ 安灯列表                           │
│ 备注                       │ 质量异常 · A02 · 09:40 [关闭][撤销]│
│ [发起安灯]                 │ [刷新]                             │
└───────────────────────────┴──────────────────────────────────┘
```

已修正点：

- 发起区与记录区分列，现场人员发起时不用先滚过长记录。
- 未响应列表放在右侧顶部，处理状态最容易被看到。
- 发起、响应、关闭、撤销都保留操作员确认门禁。

### 3.5 刷脸与交接班：身份动作与班次结果分开

场景：先确认候选操作员，再登记或比对人脸；交接班只依赖已确认操作员与工位上下文。

推荐形态：

```text
┌──────────────────────────────────────────────────────────────┐
│ 刷脸与交接班                                                   │
├───────────────────────────┬──────────────────────────────────┤
│ 我的模板                   │ 交接班                            │
│ 摄像头预览                 │ 班次时间 / 备注                    │
│ [登记] [刷脸确认]           │ [查询汇总] [确认交接班]             │
│ 模板列表                   │ 工序文档                           │
├───────────────────────────┴──────────────────────────────────┤
│ [返回工位入口]                                                  │
└──────────────────────────────────────────────────────────────┘
```

已修正点：

- 人脸采集确认与交接班分栏，避免摄像头、模板、班次、文档全部纵向堆叠。
- 页面底部有固定返回入口。
- `@vladmandic/human` 按需动态加载，避免人脸依赖阻塞整个页面模块。

### 3.6 作业资料与详情：内容优先，动作收到底部

适用页面：SOP、图纸、程序、工单详情 kiosk。

推荐形态：

```text
┌──────────────────────────────────────────────────────────────┐
│ 文档 / 图纸 / 程序 / 工单详情                                  │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│                     内容查看区                                │
│                                                              │
├──────────────────────────────────────────────────────────────┤
│ [返回工位入口] [上一步] [下一步] [放大] [缩小]                   │
└──────────────────────────────────────────────────────────────┘
```

原则：

- 查看型页面不强行拆双栏；内容完整性优先。
- 底部动作横向排列并允许换行，不能形成一整列按钮。
- 打开资料页时必须能从 URL 或父页面恢复 `workstationId`，返回后回到正确工位。

### 3.7 模块未就绪 / 加载失败

场景：动态模块加载失败或导出缺失。

推荐形态：

```text
┌──────────────────────────────────────────────┐
│ 模块未就绪 / 页面加载失败                      │
│ 说明：该功能暂不可用，可返回工位入口            │
│ [返回工位入口]                                 │
└──────────────────────────────────────────────┘
```

要求：

- 即使是失败页，也必须给返回入口。
- 失败信息以后可区分“导出缺失”和“动态导入异常”，便于定位；但不能把内部路径或凭据暴露给操作员。
- React lazy 的失败状态可能被当前页面生命周期缓存，修复后仍可能需刷新页面。

## 4. 触控与视觉约束

- 主提交按钮使用 `touchButtonProps({ variant: 'primary', size: 'primary' })`。
- 普通动作使用 `size: 'action'`；页头返回/刷新使用 `size: 'header'`；筛选类小块使用 `size: 'chip'`。
- `TouchScreenTemplate` 的 `footerButtons` 横向排列、按 220px 最小宽度换行，不再纵向堆叠。
- 页面左右分栏使用 `hmi-station-split`，左右区域使用 `hmi-station-pane`；需要内部滚动的列加 `hmi-station-pane--scroll`。
- 1100px 以下降为单列；单列顺序必须仍是“对象/主输入在前，结果/历史在后”。

## 5. 本轮审查结论

- 首页、执行、快捷报工、安灯、刷脸交接都适合采用同一套“状态条 + 对象区 + 执行区”。
- 查看器类页面不适合强行分栏，应继续内容优先、底部动作聚合。
- 所有子页都必须可返回入口，且失败态也不能形成死胡同。
- 未确认操作员的页面权限表现已经一致：可查看、写动作禁用；不要在视觉上把禁用按钮做得像仍可点击。
