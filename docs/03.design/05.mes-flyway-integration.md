## 已拍板决策

| 编号 | 问题 | 选择 | 影响 |
| --- | --- | --- | --- |
| FLY1 | 要不要 Flyway | **要。** 从切线之后的新增量起由 Flyway 执行；不把 `backend/sql/` 历史文件改写成迁移链 | 现网不重放 `ry_*` / xinhe dump / 带 `DROP` 的初始化 |
| FLY2 | 主库何时 migrate | **应用启动自动 migrate。** 失败则**拒绝启动** | 与 I6「应用打增量」一致；启动失败 = 结构未对齐，不得对外服务 |
| FLY3 | 共享库租户（`ROW` + 平台） | 无独立 schema。启动时对 **master 一次** migrate 即覆盖全部非独立库租户 | 不要按租户循环打主库 |
| FLY4 | 独立库 · 新开 | 开通步骤：`CREATE DATABASE`（若缺失）→ Flyway 跑 **tenant location 全链**（空库建表）→ 角色模板 → ping → `READY` | 取代手搓 `TenantWarehouseSql` 迁表；失败保留登记（I6） |
| FLY5 | 独立库 · 已 `READY` | **启动时**对该专库跑尚未应用的增量。一次性 JDBC，**不建 Druid 专池** | 对齐 I5（启动只建主池）；并行 N≤2 |
| FLY6 | 专库启动迁失败 | 原 `READY` 租户改为 `FAILED`，不可登录、不回落主库。**不**阻止主库启动 | 与 FLY2 不对称：主库失败起不来，专库失败仍服务 `ROW` |
| FLY7 | 登录时补跑 | **不。** 登录只校验专库 Flyway 版本已追上主库 tenant 版本 | 避免首请求卡在 DDL |
| FLY8 | `baselineOnMigrate` | **禁止默认打开。** 现网/已对齐库由运维显式 `baseline` | 空库被误钉基线会跳过建表 |
| FLY9 | 历史脚本进不进 `db/migration` | **不进。** 含 `DELIMITER`、runbook、rollback 注释、`05`/`07` 拒绝执行文件、xinhe dump | 新文件按 Flyway 语法重写；不再用客户端 `DELIMITER` |

## 1. 为什么不能整包迁移 `sql/`

`backend/sql/` 同时承担四类互斥用途，不能映射成单一 Flyway 版本链：

| 类别 | 代表 | Flyway |
| --- | --- | --- |
| 含 `DROP` 的初始化 | `ry_20210908.sql`、`quartz.sql`、`20260821_14_xinhe_schema_baseline.sql` | 禁止当 versioned migration |
| 现网增量（人可重复执行） | `20260820_02`～`06`、`20260821_09`～`18`、`20260822_19`～`20` | 多数含 `DELIMITER` + 临时存储过程；JDBC/Flyway 不能原样执行；现网已（或将）手工执行，禁止再自动跑 |
| 说明/拒绝执行 | `20260820_00_runbook.sql`、`05`、`07`、`08` | 不是 DDL |
| 序号冲突 | `14`、`15` 各两份 | Flyway 版本必须全局唯一 |

现行专库开通（`TenantSchemaProvisioner`）从 `sql/` + `doc/` 抽 `CREATE` 再跑 `TenantDedicatedSchema.incrementalSqlFiles()`。Flyway 落地后**只保留一套迁表器**：Flyway Java API。禁止启动后再跑旧清单。

切线时仓库增量最后一号为 `20260822_20_s4_dup_rename.sql`。**基线版本钉为 `20260822.20`。** 实现开工时若 `sql/` 又追加了手工号，先把那些号手工打进已有库，再把基线号前移，然后才打开 Flyway。

## 2. 目标行为（按场景）

```text
启动
  1. 仅初始化 master 连接池（I5）
  2. Flyway migrate 主库（locations = master + tenant）
     失败 → 进程退出
  3. 查询 isolation_level=DATABASE 且 provision_status=READY 的租户
  4. 并行 N≤2，一次性 JDBC：Flyway migrate 该专库（locations = tenant）
     失败 → 该行标 FAILED，不建池，主库继续启动
  5. 专池仍在首次业务访问才懒加载

开通 DATABASE（平台「创建 schema/表」）
  1. 预算门禁（I5）+ 并行槽（N≤2）
  2. CREATE DATABASE IF NOT EXISTS
  3. 空库：Flyway migrate tenant 全链（从基线快照到最新）
  4. 复制角色 / 角色菜单模板（不克隆 sys_menu 行，不复制物料）
  5. ping → READY；失败 → 登记保留、可重试

ROW / 平台
  只走步骤 2 的主库 migrate。无 per-tenant 循环。
```

登录：`DATABASE` 且非 `READY`，或专库 `flyway_schema_history` 的当前 tenant 版本 **落后于** 主库已应用的 tenant 版本 → 拒登录，文案仍「用户名或密码错误」（D9），不回落主库。

## 3. 目录与版本约定

代码仓库（`startech-mes-basic/backend`）新增：

```text
ktg-system/src/main/resources/db/migration/master/
ktg-system/src/main/resources/db/migration/tenant/
```

放在 `ktg-system`：`TenantSchemaProvisioner` 与单测都能读到 classpath；`ktg-admin` 依赖该模块，启动时 Boot Flyway 同样能扫到。**禁止**在 admin 再拷一份，以免 checksum 双份。

命名：`VyyyyMMdd.nn__slug.sql`（例：`V20260822.21__add_foo.sql`）。`nn` 按当日序号，**全局唯一**，不再使用会撞车的 `_14` / `_15` 双文件。

| Location | 谁执行 | 内容 |
| --- | --- | --- |
| `master/` | 仅主库 | 全局表增量：`sys_tenant` / 许可、`sys_menu`、`sys_dict_*`、`sys_config`、`QRTZ_*`、`gen_*` |
| `tenant/` | 主库 **和** 每个 `DATABASE` 专库 | `TenantDedicatedSchema.tenantTables()` 范围内的 DDL（身份 + md/pro/wm/qc/cal/dv/tm/rest）。**不含** I8 全局表 |

切线第一份 tenant 文件：

- `V20260822.20__tenant_schema_snapshot.sql`
- 对 `tenantTables()` 做 **CREATE TABLE**（无 `DROP`，无真实口令）。结构对齐切线当日（含 `tenant_id` 与复合 UNIQUE），不是再跑一遍 `DELIMITER` ALTER。
- 空专库靠这一版建表；已有库靠 baseline **跳过**这一版。
- 不要 `CREATE TABLE IF NOT EXISTS` 当「现网也可直接跑」的替代：缺列不会被补上，会把缺口标成已应用。

`master/` 在切线日可以没有文件。主库仍配置两个 location：baseline 跳过 `V20260822.20`，之后 `tenant/` 与 `master/` 的新版本照常执行。

`backend/sql/` 继续保留为历史记录与空实验室手册（runbook、xinhe dump）。**切线之后禁止再往 `sql/` 追加作为发布 DDL**；新 DDL 只进 `db/migration`。回滚说明可写在对应 migration 头注释，或独立不执行的注释文件；不启用 Flyway Teams undo。

## 4. 基线与空实验室

### 4.1 已有主库（现网或已按 runbook 对齐的实验室）

前置：确认已手工执行到切线最后一号（含 `20260822_20`）。

运维在**启动应用前**对该库执行一次 Flyway `baseline`，版本 `20260822.20`（写入 `flyway_schema_history`，不跑任何 SQL）。

配置：

- `spring.flyway.enabled=true`
- `spring.flyway.baseline-on-migrate=false`
- `spring.flyway.validate-on-migrate=true`
- 禁止 `outOfOrder=true`

未 baseline 就启动：Flyway 会尝试在已有 `sys_user` 上执行 tenant 快照 `CREATE` → **失败拒绝启动**（fail-closed，符合 FLY8）。

### 4.2 空实验室主库

Flyway **不**负责从零建平台库。仍按 `20260820_00_runbook.sql`：新若依初始化 + quartz + MES 结构（xinhe dump 或等价），再手工跑完切线前增量，然后 `baseline` 到 `20260822.20`，再启动。

禁止把 `ry_*.sql` / xinhe dump 放进 `db/migration`。

### 4.3 已有 `READY` 专库

同样显式 baseline 到 `20260822.20`，再纳入启动 migrate。未 baseline 的专库：启动迁表失败 → 该租户 `FAILED`，主库仍可起。

### 4.4 新开空专库

无 history 表。Flyway 从 `V20260822.20` 快照跑到最新。不 baseline。

## 5. 运行时组件

不引入第二套 ORM/认证。Flyway 只通过 JDBC 执行 DDL。

| 组件 | 模块 | 职责 |
| --- | --- | --- |
| 主库 Flyway | `ktg-admin` 启动路径 | 绑 master DataSource；locations = `master` + `tenant`；启动期 migrate；失败抛错停机 |
| 专库 Flyway 调用 | `ktg-system`（替换 `TenantWarehouseSql` 执行段） | 解密 JDBC（`TENANT_JDBC_CIPHER_KEY`）→ 一次性连接 → locations = `tenant` → migrate |
| `TenantSchemaProvisioner` | `ktg-system` | 仍负责预算、N≤2、`CREATE DATABASE`、角色模板、ping、`provision_status`；迁表改为调专库 Flyway |
| 启动补齐 | `ktg-system` ApplicationRunner（主库 Flyway **之后**） | 只处理 `READY` 的 DATABASE；一次性连接；N≤2；失败标 `FAILED` 不抛到进程 |

约束：

- 专库 migrate **不得**注册 Druid 专池。ping / migrate 均一次性连接（与现网 P-D ping 一致）。
- lookup key 仍是 `TENANT_{id}`，禁止把 URL/口令打到日志。
- 迁表 SQL 失败关闭：不删 `sys_tenant` 行，不把该厂数据写入主库。
- 全局表检测：tenant location 的 migration 不得 `CREATE`/`ALTER` I8 名单表；实现期用单测扫脚本文本（延续 `assertNoGlobalCreates`）。
- `QRTZ_*` 只在主库；`sys_job` / `sys_job_log` 在 tenant 快照内（专库有任务元数据，调度引擎表仍主库）。

Spring Boot 4.1：除 `flyway-core` 外必须加 `org.flywaydb:flyway-mysql`。不要让 Boot 默认 Flyway 再对专库自动跑一遍（只绑 primary/master）。专库用编程 API，避免第二套 `SecurityFilterChain` 式的双自动配置。

## 6. 新脚本写法

Flyway 对每个版本只执行一次，因此：

- 新文件写普通 `ALTER TABLE ... ADD COLUMN` / `CREATE TABLE`，**不要** `DELIMITER` 与临时存储过程。
- 不要靠 `IF NOT EXISTS` 掩盖「这版是否该在该库执行」；该执行而未执行应由 history 缺口暴露。
- 加 UNIQUE 前仍遵守 S4 窄口（脏数据检测）；检测 SQL 可放在同一 version 文件、失败则整版回滚（单文件事务视 MySQL DDL 隐式提交：文档写明「失败需人工修数后修 checksum 或后继修复版」，禁止改已发布文件）。
- **已发布的 Flyway 文件视为冻结。** checksum 漂移 → 启动失败。修正用新版本，不改旧文件。

## 7. 安全

- 迁移文件、配置、日志不得含口令、Token、真实 JDBC 主机。
- 专库连接串仅内存解密；异常信息剥连接串。
- 不扩大匿名 HTTP 面。
- 生产缺 `TENANT_JDBC_CIPHER_KEY` 且存在 DATABASE 租户 → 已有 S6 拒启动；Flyway 补齐专库时同样缺密钥则跳过专库并标失败，**主库仍先完成自身 migrate**（密钥问题不应用「主库结构未对齐」掩饰）。

## 8. 验证（实现单元时）

- 主库：无 `flyway_schema_history` 且已有业务表 → 启动失败。
- 主库：baseline 后启动 → history 仅基线行，无重放 `ry_*`。
- 主库：新增 `V*__*` 后启动 → 该版 applied；第二次启动 0 pending。
- 改已发布 migration 字节 → 启动失败（validate）。
- 空专库开通 → 快照 + 后续版本全部 applied；库内无 `sys_menu` / `sys_tenant` / `QRTZ_*`。
- 已 baseline 的 READY 专库 → 启动只跑新版本。
- 专库故意失败 → 主库进程存活；该租户不可登录；主库无该 `tenant_id` 业务写入。
- 启动补齐期间连接数：无 READY 专库业务访问时专池数仍为 0。
- 并行：三个 READY 专库启动补齐同时最多 2 个 migrate。

未连现网库前，上述可用 Testcontainers 或 H2/MySQL 测试夹具；交付时写明是否跳过真实 MySQL。
