## 1. 为什么不能整包迁移 `sql/`

`backend/sql/` 同时承担四类互斥用途，不能映射成单一 Flyway 版本链：

| 类别 | 代表 | Flyway |
| --- | --- | --- |
| 含 `DROP` 的初始化 | `ry_20210908.sql`、`quartz.sql`、`20260821_14_xinhe_schema_baseline.sql` | 禁止当 versioned migration |
| 现网增量（人可重复执行） | `20260820_02`～`06`、`20260821_09`～`18`、`20260822_19`～`20`、以及切线前的 `20260823_21`～`20260827_35` | 多数含 `DELIMITER` + 临时存储过程；JDBC/Flyway 不能原样执行；现网已（或将）手工执行，禁止再自动跑 |
| 说明/拒绝执行 | `20260820_00_runbook.sql`、`05`、`07`、`08` | 不是 DDL |
| 序号冲突 | `14`、`15` 各两份 | Flyway 版本必须全局唯一 |

现行专库开通（`TenantSchemaProvisioner`）从 `sql/` + `doc/` 抽 `CREATE` 再跑 `TenantDedicatedSchema.incrementalSqlFiles()`。Flyway 落地后**只保留一套迁表器**（A11）：Flyway Java API。禁止启动后再跑旧清单。

76 钉死的 tenant 基线为 **`20260825.31`**（`incrementalSqlFiles()` 最后一项 `20260825_31_ai_tool_audit.sql`）。其后 `sql/` 的 `20260826_32` / `33` 改 `sys_menu`（I8），`20260826_34` / `20260827_35` 为平台种子，均不抬 tenant 基线、不改写成 Flyway 去重放。切线打开后新发布 DDL 只进 `db/migration`。

## 2. 目标行为（按场景）

```text
启动
  1. 仅初始化 master 连接池（I5 / I1）
  2. Flyway migrate 主库（locations = master + tenant）
     失败 → 进程退出
  3. 查询 isolation_level=DATABASE 且 provision_status=READY 的租户
  4. 并行 N≤2，一次性 JDBC：Flyway migrate 该专库（locations = tenant）
     失败 → 拒绝启动（FLY6）。无 READY DATABASE 则跳过本步
  5. 专池仍在首次业务访问才懒加载

开通 DATABASE（平台「创建 schema/表」）
  1. 预算门禁（I5）+ 并行槽（同时最多 2 家；第 3 家拒绝）
  2. CREATE DATABASE IF NOT EXISTS
  3. 空库：Flyway migrate tenant 全链（从切线快照到最新）
  4. 复制角色 / 角色菜单模板（不克隆 sys_menu 行，不复制物料）
  5. ping → READY；失败 → 登记保留、可重试；进程不停

ROW / 平台
  只走步骤 2 的主库 migrate。无 per-tenant 循环。
```

登录：`DATABASE` 且非 `READY` → 拒登录（D9），不回落主库。不在登录路径跑 DDL。另比专库 vs 主库已应用的 **tenant location** 版本，落后或主库 tenant 版本不可读 → D9（FLY7）。

A6/FLY6 与 A2 同为启动失败关闭：READY 专库补齐失败或主库 migrate 失败都停进程。A4 开通当场失败仍只挡该租户、进程不停。缺 `TENANT_JDBC_CIPHER_KEY` 且已有 DATABASE 租户同样拒启动（S6）。

## 3. 目录与版本约定

代码仓库（`startech-mes-basic/backend`）新增：

```text
ktg-system/src/main/resources/db/migration/master/
ktg-system/src/main/resources/db/migration/tenant/
```

放在 `ktg-system`：开通器与单测都能读到 classpath；`ktg-admin` 依赖该模块，启动时 Boot Flyway 同样能扫到。**禁止**在 admin 再拷一份，以免 checksum 双份。

命名：`VyyyyMMdd.nn__slug.sql`（例：`V20260828.01__add_foo.sql`）。`nn` 按当日序号，**全局唯一**（`master/` 与 `tenant/` 共用同一版本号空间，避免主库两个 location 撞号），不再使用会撞车的 `_14` / `_15` 双文件。

| Location | 谁执行 | 内容 |
| --- | --- | --- |
| `master/` | 仅主库 | 全局表增量：`sys_tenant` / 许可、`sys_menu`、`sys_dict_*`、`sys_config`、`QRTZ_*`、`gen_*` |
| `tenant/` | 主库 **和** 每个 `DATABASE` 专库 | `TenantDedicatedSchema.tenantTables()` 范围内的 DDL（身份 + md/pro/wm/qc/cal/dv/tm/rest + 切线前已进 catalog 的 `ai_*`）。**不含** I8 全局表 |

切线第一份 tenant 文件：

- `V20260825.31__tenant_schema_snapshot.sql`
- 对当时 `tenantTables()` 做 **CREATE TABLE**（无 `DROP`，无真实口令）。结构对齐切线当日（含 `tenant_id`、复合 UNIQUE、以及 21–35 已加入 catalog 的 AI 表），不是再跑一遍 `DELIMITER` ALTER。
- 空专库靠这一版建表；已有库靠 baseline **跳过**这一版。
- 不要 `CREATE TABLE IF NOT EXISTS` 当「现网也可直接跑」的替代：缺列不会被补上，会把缺口标成已应用。

`master/` 在切线日可以没有文件（菜单/字典增量 21–35 已在 `sql/` 手工执行）。主库仍配置两个 location：baseline 跳过 `V20260825.31`，之后 `tenant/` 与 `master/` 的新版本照常执行。

`backend/sql/` 继续保留为历史记录与空实验室手册（runbook、xinhe dump）。**Flyway 切线已打开**：禁止再往 `sql/` 追加作为发布 DDL；新 DDL 只进 `db/migration`。回滚说明可写在对应 migration 头注释，或独立不执行的注释文件；不启用 Flyway Teams undo。

`ktg-system` 里为专库拷贝的 `tenant-sql/` 副本：落地后随旧清单一并停止作为发布路径（A11）。历史文件可留作记录，不再执行。

## 4. 基线与空实验室

运维手册见 `docs/05.manuals/01.mes-flyway-baseline.md`（基线号以 76 钉死的 `20260825.31` 为准）。

### 4.1 已有主库（现网或已按 runbook 对齐的实验室）

前置：确认已手工执行到 catalog 尽头及之后不进 tenant 基线的平台增量（含 `20260827_35` 种子）。

运维在**启动应用前**对该库执行一次 Flyway `baseline`，版本 **`20260825.31`**（写入 `flyway_schema_history`，不跑任何 SQL）。

配置：

- `spring.flyway.enabled=true`
- `spring.flyway.baseline-on-migrate=false`
- `spring.flyway.validate-on-migrate=true`
- 禁止 `outOfOrder=true`

未 baseline 就启动：Flyway 会尝试在已有 `sys_user` 上执行 tenant 快照 `CREATE` → **失败拒绝启动**（fail-closed，符合 A8 / A2）。

### 4.2 空实验室主库

Flyway **不**负责从零建平台库。仍按 `20260820_00_runbook.sql`：新若依初始化 + quartz + MES 结构（xinhe dump 或等价），再手工跑完切线前增量，然后 `baseline` 到 **`20260825.31`**，再启动。

禁止把 `ry_*.sql` / xinhe dump 放进 `db/migration`。

### 4.3 已有 `READY` 专库

同样显式 baseline 到 **`20260825.31`**，再纳入启动 migrate。未 baseline 的专库：启动迁表失败 → **拒绝启动**（A6/FLY6）。修好后再启；不要打开 `baselineOnMigrate`。

### 4.4 新开空专库

无 history 表。Flyway 从 `V20260825.31` 快照跑到最新。不 baseline。

## 5. 运行时组件

不引入第二套 ORM/认证。Flyway 只通过 JDBC 执行 DDL。

| 组件 | 模块 | 职责 |
| --- | --- | --- |
| 主库 Flyway | `ktg-admin` 启动路径 | 绑 master DataSource；locations = `master` + `tenant`；启动期 migrate；失败抛错停机 |
| 专库 Flyway 调用 | `ktg-system`（替换 `TenantWarehouseSql` 执行段） | 解密 JDBC（`TENANT_JDBC_CIPHER_KEY`）→ 一次性连接 → locations = `tenant` → migrate |
| `TenantSchemaProvisioner` | `ktg-system` | 仍负责预算、开通并行 N≤2、`CREATE DATABASE`、角色模板、ping、`provision_status`；迁表改为调专库 Flyway |
| 启动补齐 | `ktg-system` ApplicationRunner（主库 Flyway **之后**） | 只处理 `READY` 的 DATABASE；一次性连接；并行 N≤2；失败拒启动（FLY6） |

约束：

- 专库 migrate **不得**注册 Druid 专池。ping / migrate 均一次性连接（与现网 P-D ping 一致）。
- lookup key 仍是 `TENANT_{id}`，禁止把 URL/口令打到日志。
- 开通迁表 SQL 失败关闭：不删 `sys_tenant` 行，不把该厂数据写入主库。
- 全局表检测：tenant location 的 migration 不得 `CREATE`/`ALTER` I8 名单表；实现期用单测扫脚本文本（延续 `assertNoGlobalCreates`）。
- `QRTZ_*` 只在主库；`sys_job` / `sys_job_log` 快照 DDL 可随租户表复制，但应用目录与日志只写主库（调度器 `selectJobAll` 只扫主库）。

Spring Boot 4.1：除 `flyway-core` 外必须加 `org.flywaydb:flyway-mysql`。不要让 Boot 默认 Flyway 再对专库自动跑一遍（只绑 primary/master）。专库用编程 API，避免第二套自动配置。

## 6. 新脚本写法

Flyway 对每个版本只执行一次，因此：

- 新文件写普通 `ALTER TABLE ... ADD COLUMN` / `CREATE TABLE`，**不要** `DELIMITER` 与临时存储过程。
- 不要靠 `IF NOT EXISTS` 掩盖「这版是否该在该库执行」；该执行而未执行应由 history 缺口暴露。
- 加 UNIQUE 前仍遵守 S4 窄口（脏数据检测）；检测 SQL 可放在同一 version 文件。MySQL DDL 常隐式提交：失败需人工修数后加后继修复版，禁止改已发布文件。
- **已发布的 Flyway 文件视为冻结（A9）。** checksum 漂移 → 启动失败。修正用新版本，不改旧文件（包括只改注释）。

## 7. 安全

- 迁移文件、配置、日志不得含口令、Token、真实 JDBC 主机。
- 专库连接串仅内存解密；异常信息剥连接串。
- 不扩大匿名 HTTP 面。
- 缺 `TENANT_JDBC_CIPHER_KEY` 且已有 DATABASE 租户：主库 Flyway 仍可能已跑完，但进程 **拒绝对外服务**（S6 / spec 36）。Catch-up **不得**把这些租户标 `FAILED` 后 `return`。READY 专库启动 **migrate 失败**同样拒启动（FLY6）。开通当场失败仍只挡该租户。开通/登录路径实际解密 JDBC 仍失败关闭。

## 8. 行为必须成立（实现 spec 再拆成测试）

下列是设计约束，不是本文件的可执行 task：

- 无 `flyway_schema_history` 且已有业务表的主库 → 启动失败；不得重放 `ry_*`。
- 主库显式 baseline 后启动 → history 含基线行；新增版本只执行一次。
- 改已发布 migration 字节 → 启动失败（validate）。
- 空专库开通 → 快照 + 后续版本全部 applied；库内无 `sys_menu` / `sys_tenant` / `QRTZ_*`。
- 已 baseline 的 READY 专库 → 启动只跑新版本。
- 任一 READY 专库启动迁失败 → 拒绝启动。无 READY DATABASE 则可启动。
- 无 READY 专库业务访问时，启动结束后专池数仍为 0。
- 开通与启动补齐均最多 2 路并行（独立限流）。

## 9. 非目标

- Liquibase、多套 Flyway 表名、启动 eager 建全部专池
- 把 Vue2、`ktg-generator` 行为、UReport 引擎迁到 Flyway
- ROW↔DATABASE 改档迁数（D8）
- 用 Flyway 跑实施 dump / 菜单种子重建现网
- 修改已提交的 `backend/sql/` 历史文件内容
- 登录路径跑 DDL（FLY7 只比 tenant 版本，落后 D9）
- 把坏专库留在 `READY` 上对外服务；启动补齐失败必须拒启动，不得标 `FAILED` 后继续
