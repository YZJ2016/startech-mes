## 1. 问题与目标

快格制造闭环在五处断点上「看起来有门禁/过账/业财/租户/追溯」，实际可跳过、可双过账、可账实分离、可漏组织条件、可假成功拆分。本设计按断点给出收口决定，供 spec 140–144 接住；**不是**成熟度评估报告，也**不**恢复已删的 `docs/03.design/17`/`18` 评估旧文。

### 1.1 目标

- 无策略（source `default_none`）时成品/来料/客供料入库被挡；source `material` 且 eff `none` 才放行；质量态与工单态契约稳定
- 库存增减可重试、可并发而不丢更新、不加两次量
- 库存与业财/成本同一成败；成品入库有会计事件；金蝶失败可见
- 经 API 可达的租户模型读和 queryset 写默认带组织条件；跨组织显式可审计
- 单据关系单一写入；拆分与关系同事务

### 1.2 非目标（本期）

- 第 6 项设备绩效 / OEE / 数采（用户未拍板）
- 上帝服务拆分；补 CI；APS；行业包空壳
- SPC / Cpk / 8D；实现工序拆分
- 把修法抄进 `startech-mes-basic`；把 Startech MyBatis 拦截器步骤堆成快格清单
- 本期不上 PostgreSQL RLS

### 1.3 依赖与合并顺序

```text
CL1 → CL2 → CL3
CL4 可与 CL1 并行设计；CL1–CL3 新查询合并前须满足 CL4
CL5 不挡 CL1–CL4（拆分关联写路径自身遵守 CL4）
```

**设计被 spec 接住的判定：** 对应 KR-CL 编号出现在 spec Related；验收标准覆盖本设计各节「落点」表中的行为，且不把非目标写进 In scope。可执行勾选步骤只在 `docs/04.specs/140`–`144`，本文不复制 Task Breakdown。

## 2. KR-CL1 — 检验门禁与状态契约

### 2.1 默认必检与 source

`resolve_inspection_policy`（`src/apps/kuaizhizao/services/inspection_policy_service.py` 810 行起）返回 `(eff, plan_id, source)`，代码第三项名叫 `reason`。eff 全集：`none`、`simple`、`plan`。

| source | 含义 | 入库门禁 |
| --- | --- | --- |
| `default_none` | 无策略：物料不存在、`inspection_stages` 为空，或 iqc/fqc/oqc 三环节 mode 都是 `none` | 必检，不得跳过。与全局开关存值无关 |
| `material` 且 eff 为 `none` | 物料级显式免检。`resolve_material_stage_policy_from_rows`（687 行）在 `inspection_stages` 非空且 `has_custom`（至少一环节 mode 不是 `none`）时返回 `material`；当前环节 mode 为 `none` 时 eff 仍是 `none` | 放行 |
| `material` / `material_legacy` / `material_group` 且 eff 为 `simple` 或 `plan` | 已配置要检。后两个 source 只在 mode 不是 `none` 时返回 | 必检 |
| `stage_disabled` / `module_disabled` | 组织环节或模块关闭，eff 为 `none` | 保持「该环节不启用」。不改判成 `default_none`，也不当作免检配置 |
| `work_order_override` / `work_order_operation` / `operation` / `operation_legacy` | IPQC 或工单覆盖 | 不作为物料免检口 |

现网 868–875 行在 eff 为 `none` 时丢弃全部内层 source——`material`、`stage_disabled`、`module_disabled` 统一收成 `default_none`（其间还有 `material_inspection_mode` legacy 回退分支，透传 source 时一并处理）。收口后必须保留 source 区分，调用方按 source 判定，不是删掉所有 `continue`。

`assert_fqc_for_finished_goods_receipt`（1213 行）今日在 1244–1245 行对 eff `none` `continue`。1225–1226 行在入参 `work_order_id` 为空时直接 `return`。收口后这段不得再绕开 FQC；无策略仍按 `default_none` 必检。调用点：成品 `FinishedGoodsReceiptService.confirm_receipt`（`warehouse_service.py` 5136 行）、半成品 `SemiFinishedGoodsReceiptService.confirm_receipt`（374 行）。

## 4. KR-CL3 — 业财与库存同一成败

### 4.1 同事务 / 同一成败

| 断点 | 证据（spec 142） | 决定 |
| --- | --- | --- |
| 财务事件吞异常 | `finance_integration_hooks.py` 约 111–121 | **不得**捕获全部异常只打日志后返回成功；销售出库→应收、采购入库→应付、退货、其他入出库等与库存同一成败 |
| 其他入库成本 | `warehouse_service.py` 约 15390–15394 `on_other_inbound_confirmed` | 失败不得只 `logger.warning`；与确认同一成败 |

| 预估工资 | `src/apps/kuaizhizao/services/reporting_service.py` 490 行 `_get_reporting_estimated_wage_rate` 回退 `Decimal("30")`，由 `get_reporting_statistics`（2384、2516 行）写入 `estimated_wages`。API 副本 `src/apps/kuaizhizao/api/productions/reporting.py` 122 行，由 `get_reporting_overview_statistics`（261 行）使用。两处都是统计/预估展示 | 缺 `estimated_wage_rate`：该字段 null 并带「未配置」，其余数据照常返回；禁止整端点报错；禁止回退 30。若同一数值被拿去记账，缺配置则该笔记账失败，与库存同一成败 |
| 金蝶 | `fail_on_error` 种子 False | 失败落可见「未推送」（或等价）；可重试；**本缺口收口，不另开** |

## 5. KR-CL4 — 租户查询强制隔离

### 5.1 一个机制

| 点 | 决定 |
| --- | --- |
| 入口 | 一个机制强制组织条件，覆盖租户模型的读，以及 queryset 写：`.filter(...).update()` / `.delete()`。机制不能只收读 |
| 数量 | **一个机制**，不按文件拆多个隔离需求/spec |
| 空上下文 | 失败关闭，不得查出或改到数据 |
| 收口范围 | 经 API handler 可达、作用于租户模型的读和写（含 `filter().update()` / `delete()`）。约 12509 处 `tenant_id=` 含写入赋值与注释，不是泄漏条数；本期不要求改完这些字面，也不上 RLS |

证据澄清（spec 143）：

- 约 12509 处 `tenant_id=` **含写入与注释，不是泄漏条数**
- 图上 `TenantQuerySet.filter` 高扇入是**方法名碰撞**，不是真实调用证据
- `get_tenant_queryset(` 约 5 处说明强制入口使用面仍窄
- 无 RLS，DB 层不兜底

### 5.2 超管跨组织与 DataScope

| 点 | 决定 |
| --- | --- |
| 超管跨组织 | 须显式 API/上下文开关 + 审计（谁、何时、哪个组织、哪个资源）；默认仍本组织 |
| `DataScopeService` | 保留为组织**内**行权限（全部/部门/本人/自定义）；**不**与组织间隔离混成一层 |

### 5.3 与 Startech / CL1–CL3

- `02.mes-multi-tenant-gaps.md` 与 Java `TenantLineInterceptor` **不是**本修法契约源；禁止把拦截器步骤抄成快格实现清单
- CL1–CL3 新查询合并前必须走本机制（或临时 `tenant_id` + 标注，合并时删临时）

**落点：** spec `143`。

不拆仓储/工单上帝服务。不挡 CL1–CL4；拆分路径查询遵守 CL4。
