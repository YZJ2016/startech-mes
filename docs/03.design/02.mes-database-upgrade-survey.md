# MES 数据库侧换壳调查

- 视角：仅数据库与 Mapper/SQL 静态对照，不评前端、不升级代码、不连远程库
- 业务仓库：`startech-mes-basic`（独立 git），读取分支 `upgrade/ruoyi-framework`
- 新若依参考：`RuoYi-Vue/sql/`（v3.9.2，`ry_20260417.sql` + `quartz.sql`）
- 当前 MES 初始化：`startech-mes-basic/backend/sql/`
- 设计/实施 SQL：`startech-mes-basic/backend/doc/`
- 抽出 worktree：检查 `.worktrees/extract-*` 是否已新增 `backend/sql` 增量脚本
- 调查日期：2026-08-20

本文件可独立阅读。不复述连接串、口令、内网地址或账号。历史脚本视为不可原地改写的记录；换壳只允许新增增量脚本。

## 1. 结论

1. **平台表没有删表，只有加列和新表。** `ry_20210908.sql` 与 `ry_20260417.sql` 同名 `sys_*` / `gen_*` 表集合一致；新若依多一张 `sys_notice_read`。没有从 MES 脚本里消失的 `sys_*` 表。
2. **现网用户/角色/菜单/字典不能靠跑新 `ry_*.sql` 重建。** 新脚本开头全部 `drop table if exists`。换壳必须「现网 dump + `ALTER` 补列」，禁止对已有库执行新初始化。
3. **Quartz 物理表不是两套。** MES 与新若依的 `quartz.sql` 字节级相同（同 MD5、同 11 张 `QRTZ_*`）。应用层另有 `sys_job` / `sys_job_log`（在 `ry_*.sql`），这是若依一贯的「调度元数据 + Quartz 运行表」，不是第二套调度库。
4. **误放在平台库的 MES 表必须留下、抽出后仍叫 `sys_*`。** `sys_auto_code_rule/part/result`、`sys_attachment`、`sys_message` 有设计 CREATE；`sys_notice_detail` 在当前业务分支无 CREATE，仅 Mapper/实体。它们与新若依 `sys_notice_read` 平行，不能当同一张表替换。
5. **业务表主链有设计 CREATE，定制表大量缺脚本。** `ktg-mes` 约 112 个 Mapper XML。设计文档覆盖 md/pro/qc/wm/dv/cal/tm 主链；至少 23 张表「有 Mapper、仓库无 CREATE」。
6. **菜单与字典的现网真相在实施 dump，不在 `ry_20210908.sql`。** 平台初始化只有若依菜单（含「苦糖果 MES 官网」外链）；MES 路由在 `backend/doc/实施文档/sys_menu.sql`，且该文件带 `DROP TABLE`。
7. **字符集未在平台建表语句里钉死。** `ry_*.sql`、`quartz.sql`、`mes-*.sql`、`mes_sys.sql` 均无 `CHARSET`；实施 dump 为 `utf8mb4_general_ci`；`turnplate.sql` 的 `md_turnplate_records` 写了 `DEFAULT CHARSET=utf8`。JDBC 配置含 `useUnicode` 与 `characterEncoding`，yml 中未出现 `utf8mb4`。
8. **抽出 spec `02`/`05`/`07` 直接绑表；其余单元基本不改库。** `05` 已要求补 `sys_notice_detail`。`.worktrees/extract-05` 已有草稿增量脚本，但 `upgrade/ruoyi-framework` 尚未纳入。
9. **最大迁移风险不是缺一张 Quartz 表，而是「对新库跑 drop 初始化」叠上「菜单/字典 ID 漂移」和「缺 CREATE 的定制表只能从现网导出」。**
10. **空实验室可以按新若依重建平台表；现网必须 dump。** 代码生成器表、登录/操作日志、Quartz 运行态可丢；用户、角色、菜单、字典、参数、自动编码流水、附件、消息、公告已读、全部 MES 业务表必须迁移。

## 2. 系统表漂移

对照对象：

| 来源 | 文件 | 角色 |
| --- | --- | --- |
| MES 平台初始化 | `backend/sql/ry_20210908.sql` | 19 张 `sys_*`/`gen_*` |
| 新若依 | `RuoYi-Vue/sql/ry_20260417.sql` | 上表 + `sys_notice_read` |
| MES Quartz | `backend/sql/quartz.sql` | 11 张 `QRTZ_*` |
| 新若依 Quartz | `RuoYi-Vue/sql/quartz.sql` | 与 MES 文件相同 |

引擎：两边建表均为 `engine=innodb`，脚本未写 `CHARSET`。主键名称两边一致。

### 2.2 列级：必须 `ALTER` 才能接新若依代码

下列差异已逐列比对主键与业务列，不只比表名。

| 表 | 主键 | 变更 | 现网迁法 |
| --- | --- | --- | --- |

| `sys_menu` | `menu_id` | 新列 `route_name varchar(50) default ''`，插在 `query` 与 `is_frame` 之间 | `ALTER TABLE sys_menu ADD route_name varchar(50) default '' COMMENT '路由名称' AFTER query;` 现网填空串即可。旧 `INSERT` 列数与新表不兼容，禁止把新 `ry_*.sql` 的菜单 seed 直接插入现网 |
| `sys_oper_log` | `oper_id` | 新列 `cost_time`；`method` `varchar(100)` → `varchar(200)` | `ADD cost_time`；`MODIFY method varchar(200)`。历史日志可保留，非用户资产 |

| `sys_notice_read` | `read_id` | 整表新增。列：`read_id`、`notice_id int(4)`、`user_id`、`read_time`，唯一键 `(user_id, notice_id)` | 新环境 `CREATE`。**不要**把 MES `sys_notice_detail` 行直接插入此表（列模型不同，见第 3 节） |

列结构与 MES 脚本**相同**的表（换壳时表结构可视为已对齐，仍须迁数据）：

`sys_dept`、`sys_post`、`sys_role`、`sys_user_role`、`sys_role_menu`、`sys_role_dept`、`sys_user_post`、`sys_dict_type`、`sys_dict_data`、`sys_config`、`sys_logininfor`、`sys_job`、`sys_notice`。

`sys_job` 主键两边都是 `(job_id, job_name, job_group)`。

### 2.3 种子数据漂移（空库可跟新脚本，现网禁止重放）

结构相同不等于种子相同。

| 对象 | MES `ry_20210908` | 新若依 `ry_20260417` | 现网含义 |
| --- | --- | --- | --- |
| `sys_menu` 行数 | 83 条 `insert` | 85 条 | 新若依在「缓存监控」后插入「缓存列表」（id=114），后续工具菜单 id 整体 +1 |
| 菜单 id=4 | 「苦糖果 MES 官网」 | 「若依官网」 | 外链不同；现网以库内为准 |
| 菜单 id=114 | 「表单构建」 | 「缓存列表」 | **ID 冲突**。把新 seed 打进现网会覆盖/错位 MES 与平台菜单 |
| `sys_dict_data` | 28 行；`dict_code=18` 起为操作类型「新增…」 | 29 行；插入「其他」操作（`dict_code=18`），后续 +1 | 字典主键漂移。现网 MES 业务字典从实施 dump 的 100+ 号段开始，不能用新 seed 重建 `sys_dict_*` |
| `sys_config` 结构 | 相同 10 列 | 相同 | 键有改名和新增 |
| `sys_config` 键 | `sys.account.captchaOnOff` 等 5 条 | 改为 `sys.account.captchaEnabled`，并新增登录黑名单、初始密码策略、密码周期、密码字符范围等键 | 现网要 `UPDATE`/`INSERT` 键名，不能 drop 后重灌。种子里的初始口令键不要写进增量脚本的值里，用占位或现网已有值 |
| `sys_notice` | 2 条演示公告 | 3 条 | 演示数据，现网已有公告以库为准 |

实施文档 `sys_dict_type.sql` 在平台 1–10 之外还有 `dict_id` 100–128 的 MES 类型（物料/工单/质检/条码/报工等）。这些只存在于实施 dump 与现网，不在 `ry_*.sql`。

### 2.4 保住现网用户/角色/菜单/字典的迁法

对**已有库**：

1. 全库逻辑备份（结构 + 数据），备份完成前不执行任何 `DROP`。
2. 只对第 2.2 节表做 `ALTER`（幂等：先 `INFORMATION_SCHEMA` 判断列是否存在）。
3. `sys_config`：把 `captchaOnOff` 迁到 `captchaEnabled`（保留原值），再插入新若依多出来的键；不要删除现网其它配置行。
4. `sys_menu` / `sys_role_menu` / `sys_dict_*`：**整表 dump 迁入**，不要执行新 `ry_*.sql` 的 `INSERT`。
5. `sys_user` / `sys_role` / 关联表：dump 迁入；`pwd_update_date` 允许 NULL。
6. 新表 `sys_notice_read`：空表创建，供新平台代码写入；MES 已读继续用 `sys_notice_detail`，直到另开合并单元。
7. `sys_logininfor` / `sys_oper_log` / `sys_job_log` / `QRTZ_*`：可迁可弃，不影响登录授权。建议迁 `sys_job` 行（若现场有自定义任务）。

对**空实验室**：

1. 执行新若依 `ry_20260417.sql` + `quartz.sql`（允许 drop，因为库是空的）。
2. **不要**再执行 MES 的 `ry_20210908.sql`（会把刚建的表 drop 掉，且缺新列）。
3. 再执行 MES 业务脚本与增量脚本（第 6、8 节）。菜单/字典用实施 dump 的**去 DROP 版本**或现网导出。

## 3. 误放在平台库的 MES 表

抽出后表名保持 `sys_*`（spec `02`/`05` 已冻结）。Mapper 当前仍在 `ktg-system`（抽出前）。新若依没有这些表。

### 3.1 `sys_auto_code_rule` / `sys_auto_code_part` / `sys_auto_code_result`

| 项 | 结论 |
| --- | --- |
| 设计 CREATE | 有。`backend/doc/设计文档/数据库设计/mes_sys.sql` |
| 实施 CREATE + 种子 | 有。`backend/doc/实施文档/sys_auto_code.sql` 以及拆开的 `sys_auto_code_rule.sql` / `part.sql` / `result.sql`（`utf8mb4`） |

### 3.4 `sys_notice_detail`

| 项 | 结论 |
| --- | --- |
| 设计 / `backend/sql/`（当前业务分支） | **无 CREATE** |
| Mapper | `SysNoticeDetailMapper.xml`：`id, notice_id, user_id, create_by, create_time, update_by, update_time, remark`；`INSERT ... ON DUPLICATE KEY UPDATE`（依赖 `(notice_id, user_id)` 一类唯一约束） |
| 实体 | `SysNoticeDetail`：`id` Integer，`noticeId` Integer，`userId` Long，继承审计字段 |
| 平台侵入 | `SysNoticeMapper.xml` `left join sys_notice_detail`（spec `05` 要求迁走后还原） |
| 与 `sys_notice_read` | **冲突的是产品语义，不是表名。** 若依：`read_id` + `read_time` + 唯一 `(user_id, notice_id)`，无审计列。MES：有审计/`remark`，无 `read_time`。禁止在换壳时把已读合并进若依表 |
| 抽出后表名 | 仍 `sys_notice_detail` |
| worktree | `.worktrees/extract-05/backend/sql/20260820_01_sys_notice_detail.sql` 已有按实体推断的 `CREATE TABLE IF NOT EXISTS`（含 `uk_notice_user`）。**尚未进入 `upgrade/ruoyi-framework`** |

上线前仍应用现网 `SHOW CREATE TABLE sys_notice_detail` 核对类型（尤其 `id`/`notice_id` 是否为 `int`），推断脚本不能代替现网 DDL。

### 3.5 其它带 `sys_` 前缀但属于 MES 的表

`sys_camera_configuration`：仅 `ktg-mes` `MdCameraMapper.xml` 使用，仓库无 CREATE。列含设备访问口令字段。抽出与换壳都不要把该表放进若依平台脚本；增量 CREATE 不要写入口令值。

## 6. 风险

| 风险 | 等级 | 说明 |
| --- | --- | --- |
| 对新库或现网执行带 `DROP TABLE` 的 `ry_*.sql` / 实施 dump | 高 | 用户、角色、菜单、字典、MES 业务表一并消失或被种子覆盖 |
| 菜单/字典主键与新若依种子冲突 | 高 | id=114 等错位；`sys_role_menu` 会指到错误菜单 |
| 23 张定制表无 CREATE | 高 | 空库无法上线销售/转运盘/工装采购/摄像头/售后等；现网只能 dump |
| `sys_notice_detail` 仅有推断 DDL | 高 | `01` 已按实体建表；现网类型仍须 `SHOW CREATE TABLE` 核对。与 `sys_notice_read` 误合并会丢 MES 已读语义 |
| 字符集混用 | 中高 | 设计/平台脚本未声明 charset；实施 dump 为 utf8mb4；`md_turnplate_records` 为 utf8；JDBC 未配置 utf8mb4。四字节字符与排序规则可能不一致 |
| `sys_messsage` DROP 拼写 | 中 | 设计脚本 drop 不到真实表；误导人工「删消息表」。真实表是 `sys_message` |
| `captchaOnOff` → `captchaEnabled` | 中 | 只改代码不改配置键则验证码开关失效 |
| `gen_table_column.table_id` 类型 | 中 | 改 bigint 前需确认无非数字 |
| `inital.sql` 写死虚拟仓 id=200 | 中 | 空库若自增起点不是 200，线边库种子会指错仓库 |
| 实施 `sys_menu.sql` 含 MES 路由 | 信息性 / 操作高 | 文件**有** `mes/md`、`mes/pro`、`mes/qc`、`mes/wm`、`mes/dv`、`mes/cal`、`mes/tm` 等 component；`ry_20210908.sql` **没有**这些路由。换壳菜单必须以现网或该 dump 为准 |
| Quartz「两套表」 | 低 | 只有一套 `QRTZ_*` + 一套 `sys_job*`。不要建第二套 scheduler 库 |
| `wm_*salse` / `wm_after_salse` 拼写 | 低 | 与代码一致，不要在换壳时改名 |
| 摄像头表口令列 | 中（安全） | dump/脚本不要打印或提交设备口令 |

未连现网，故「现网实际 charset/引擎/是否已有 `sys_notice_detail`」以 DBA 导出为准。本调查不声称现场库已核对。

## 9. 方法与边界

- 静态分析：`CREATE TABLE` 解析、Mapper XML 表名抽取、同名表列比对。
- 读取分支：`startech-mes-basic` 的 `upgrade/ruoyi-framework`；worktree 仅补充「是否已有增量 SQL」。
- 未执行：远程 SQL、现网 `SHOW CREATE TABLE`、数据抽样、前端路由核对。
- 未验证：现场 charset、引擎、表是否已有 `warehouse_type` 等补丁列。

以上缺口在拿到现网结构导出后，应用同一套增量文件名做一次「推断 DDL vs 现网 DDL」 diff，再冻结脚本。
