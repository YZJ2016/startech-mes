## 1. 问题与目标

开源仓有数采表、Edge Agent 和路线图，云侧服务不在槽位里。自研补云侧，现场采集程序不换栈。报表侧到最后一步才消费一条普通 HTTP 馈送。

### 1.1 目标

- 云侧能收 HTTP 入站、留最新快照、节流写回星制造设备状态
- 其后按六步补齐护栏、边缘运行时、物模型与趋势、事件与指令
- 最后把设备运营馈送登记为星报表已有的 HTTP 数据源类型

### 1.2 非目标

- 报表五段未完成时开工
- 在 W6 之前让星报表出现数采专用接口
- 在 W1–W6 内做 MQTT 订阅、ThingsBoard 或 JetLinks（见 KIO-D6，六步之后再做）
- 内置 MQTT Broker，或把 OPC UA / S7 做成可运行 Agent
- 没有 InfluxDB 时仍承诺趋势图
- 合并进 `startech-mes-basic` 或 UReport
- 新造一套数采表，或改已经进过库的迁移文件名

## 3. 六步边界

### 3.1 KIO-W1 入站闭环

设备 token、HTTP 入站、幂等（已有 `ingest_dedup`）、最新值快照（`tag_snapshots`）、按 `equipment.uuid` 写回设备状态。节流至少 5 秒一条，`data_source=sensor`。

本步不包含 MQTT 订阅、ThingsBoard、JetLinks、Influx 趋势、告警和指令。告警在 W2，趋势在 W4，指令在 W5。三条平台入站在六步收口之后，见 KIO-D6。

### 3.2 KIO-W2 护栏与预填

状态护栏：写回时尊重设备不可覆盖的状态（停用、报废、未闭环故障、进行中维修一类，细则沿用路线图已写的护栏语义）。点位模板。阈值告警（`alert_rules` / `alerts`）。报工与点检预填。

### 3.3 KIO-W3 边缘运行时

云侧下发边缘配置（`edge_configs`）、接收心跳、接受断网后的批量续传。OPC UA / S7 只做配置校验，不交付对应 Agent。可运行采集仍只是 Modbus TCP。

### 3.4 KIO-W4 物模型与趋势

产品物模型（`products`）、按产品批量建设备、离线告警。趋势只认租户自建 InfluxDB，见 **KIO-D8**。未配置 InfluxDB 时趋势不启用，不用 `tag_history` 顶上；W1 的最新值快照和设备状态写回仍然可用。

### 3.5 KIO-W5 事件与指令

事件、指令闭环（`device_commands`）、设备分组（`device_groups`）、消息追踪（`message_logs`）。MQTT Broker 仍不内置；要消息通道时外接。

### 3.6 KIO-W6 与报表的衔接

这是两边唯一的衔接点。数采提供 `equipment-ops-feed`。星报表把它登记为一条 HTTP 数据源（地址必须落在报表已有的登记表里）。登记时种入一张已绑定该源的设备运营大屏，组件指向 `ops_metrics` 等馈送字段（路径名沿用 `KUAIREPORT-LINK.md`），设计器仍可改布局。组件仍是普通大屏组件，数据源类型仍是 HTTP。

OEE 在本步随 `equipment-ops-feed` 一起计算，结果放进 `ops_metrics`（如 `oee_live`），见 **KIO-D7**。仅当同时有传感器状态分段和已审核报工良品率时才计算；缺一则该指标空着，不填默认值。馈送里的其它字段照常给出。状态分段来自 W1 已写回的设备状态。

W6 之前，星报表设计（18）不增加任何数采专用接口。

### 3.7 六步之后（KIO-D6）

MQTT 订阅、ThingsBoard 拉遥测、JetLinks 拉遥测在 W6 收口后另开，不插入 W1–W6。三条路都写入 W1 已有的同一条入站，不各建一套快照或写回。MQTT 只订阅现场自备的 Broker。本段是后续必做的能力边界，不是六步里的一步，也不写成可放弃。见 spec 156。

OEE 已由 **KIO-D7** 放在 KIO-W6，不在六步之后另开，也不在 W6 之前为了大屏提前造指标。

## 5. 2026-10-07 core 支持复核与修复设计增量

需求追溯：需求 19 的 KIO-R01–R13；实现单元：spec 178。此节记录职责、证据与设计边界，不列执行 task。前文「云侧服务不在槽位」「将来」为历史基线，当前服务已在仓。本节不是现场验收通过声明。

### 5.1 已选方案 A（KIO-D9）

```text
core IntegrationConfig：连接地址、凭据、启停、公共测试
        ↑ 同租户关联（具体字段及存量迁移待决策）
kuaiiot KuaiiotConnection：数采映射与采集运行
        → IoT 设备 / 点位 → 统一 IngestService → MES 设备绑定与护栏
```

职责原则：core 不承接点位、快照、补传、设备状态转换和 OEE；kuaiiot 不复制连接凭据。core 配置启停与 kuaiiot 采集启停的关系、删除引用行为必须在落地前定义。已有 core ThingsBoard / JetLinks 目录不等于协议适配已完成；MQTT 的公共类型归属尚未确定，不擅自新增类型或接口。

### 5.2 凭据沿用现状（KIO-D10）

`IntegrationConfig.config` 是普通 JSON；创建/更新和 `get_config()` 在已检查路径中没有加密转换。`build_integration_response()` 调用 `_mask_config_password()`，顶层名单字段显示 `****`；编辑时名单字段空值或占位符保留原凭据。token 和嵌套密码当前不在该脱敏处理范围。

本轮保持明文存储与后端原值读取，也保持已有接口脱敏和编辑行为；不新增加密或脱敏扩展。采集适配器读取组织内 core 原始配置，不能通过管理 API 获取连接凭据。日志和仓库不出现真实凭据。原审查提出的 token 脱敏扩展不列入本轮任务。

### 5.3 公共能力复用及缺口

- **R02**：公共 REST 测试目前把 `<500` 作为成功，不能据此证明认证和遥测可用；Influx 属于仅配置校验。设计须分清探测等级，平台协议与版本核对后才能确定测试路径。
- **R03**：复用 `BusinessNotificationService.dispatch()` 与既有业务规则。公共前端加载器已预留 kuaiiot，但应用常量/服务模块缺失，告警路径也未接派发。事件名、恢复状态与重试方案待选，不另造消息体系。
- **R04/R05**：core 已提供 Taskiq 入口，真实订阅、平台拉取、健康检查和留存仍由 kuaiiot 实现。现有占位不能作为健康或清理成功。保留任务名与已有周期，留存策略另行决策；不把平台地址写进仓库。
- **R10**：趋势继续租户自建 Influx，PG 不作历史趋势替身。入站与历史投递缺少衔接；同步双写和可靠异步都是待选方案，不把此前异步建议当已拍板。

### 5.4 数采可靠性及业务语义

- **R06/R07**：同次采样身份贯穿首次发送、缓冲、补传；快照不因旧样本倒退。采样时间与接收时间用途分开；同时刻冲突、质量值及补传是否影响当前告警/状态待定义。
- **R08/R09**：Agent 存活与 PLC 连通分开观测；采集失败不阻断心跳；配置失败、离线启动、缓存调度和指令回执恢复需选方案。设备写成功不能因回执网络失败被解释为执行失败。
- **R11**：ops feed 当前为可用率×良品率；制造域性能因子从实际工时反推，存在口径偏差。修复需共同定义班次、理想节拍、质量来源、窗口前状态及断采覆盖率。完整 OEE/过渡指标尚未选定，不新增默认性能值。
- **R12/R13**：接入和诊断围绕真实设备、原始值、转换值、质量、采样时间与业务落点；协议扩展依现场清单。现有 JSON 表单、消息页路由是源码事实，未作视觉或可访问性合规结论。

### 5.5 兼容与决策门槛

R01 已由用户选择推荐做法：KuaiiotConnection 新增可空 integration_id 外键，创建使用 integration_uuid，输出 integration_id；MQTT/ThingsBoard/JetLinks 必须引用同租户且启用的同类型公共连接，直接 HTTP 入站可不关联。数采 config 仅保存载荷映射，不重复保存服务器地址与凭据。系统未上线且无存量数据，仅迁移表结构，不做数据搬迁或兼容读取。公共连接停用后，云端入站、映射处理、订阅对齐、配置下发及指令领取均检查停用；存在未删除数采引用（含停用引用）时禁止软删除。关联创建与公共删除锁定同一公共连接行，避免删除与新增引用竞态。core 独立 MQTT 类型目前仅校验 host/port，返回 config_only 且不标记已连接。真实 Broker 通信及 Agent 本地轮询暂停仍由 R04/R08 跟踪，不能把云端拒绝入站理解为 PLC 已停止轮询。其他待选项见需求 19，不得凭惯例自动补齐。

不修改既有 URL、method、认证头或响应外层结构；涉及字段须核对 Web 调用方与 aerich。继续 FastAPI / Pydantic / Tortoise / PostgreSQL / Taskiq 与 React 现栈。迁移按 AGENTS 的 14 位时间戳序号规则，禁止重命名已执行迁移。历史 150–156 的占位边界保留为实现历史，后续修复由 178 跟踪，不将历史测试结论扩大到现场能力。

### 5.6 本轮选定设计与实施增量（2026-10-07）

本节为本轮选定后的设计，替代5.1–5.5中修复前的待选描述。方案授权见需求19。平台 REST 适配放 core/services/integration/iot_platform_client.py，公共测试只声明 authenticated；MQTT 公共测试仍是 config_only，数采订阅才记录连接健康。ThingsBoard 使用 4.4 JWT/最新时序/双向 RPC，JetLinks Community 2.10.0 使用 Access Token/最新属性/功能调用；HTTP 成功不覆盖设备返回的执行失败。平台指令发送前标记，响应丢失进入 uncertain，不自动重复设备动作。

入站事务锁设备行，维护包含事件的 latest_sampled_at 水位；各点位按采样时间保留首值。旧样本写历史待投递记录，不改变当前业务；坏/不确定质量不产生业务数值，历史保留质量标记。KuaiiotDelivery 负责租户内 Influx 和公共通知投递，外部失败保留重试，缺通知规则显示 blocked。通知按规则、收件人和通道检查已成功记录，部分失败只重试未完成投递。没有跨 PostgreSQL/外部服务原子事务保证。

Agent SQLite 保存采样、最后成功配置和指令结果；首次发送前建身份，单轮仅补一个批次，缓存满暂停新采样。心跳线程独立；禁用配置继续可诊断并下发停止采集。候选 PLC 连接验证后切换，坏点标 bad。试读回传真实原始寄存器、转换结果、质量和版本；心跳独立记录 Agent 已应用配置版本。

MQTT 按公共配置创建真实订阅，进程内串行对齐，数据库租约确保多任务实例归属；处理消息前验证租约，失效订阅不再写入；续期或消费任务退出时共同关闭并释放租约。健康检查分 MQTT、平台认证、HTTP 最近入站，清理参数未配置时明确报告。保留既有调度入口。

两个 OEE 服务共用 oee_calculator，设备已有 technical_parameters.oee 保存 ideal_cycle_seconds 和带时区 planned_windows，不新建第二套计划模型。运行状态最多延续五分钟，未知段不计覆盖；取窗口前状态；仅窗口内已审核报工进入产量；完整覆盖且三因子可用时才返回完整 OEE。Web 链路页维护参数并显示连接、设备、Agent 和待投递阶段；边缘页只发布已实现协议，现场未支持的寄存器区/字序/协议不能宣称已接通。

迁移20261007130000包含待投递表、恢复/处置审计、订阅租约、试读结果和设备水位。仅结构变化，尚未在真实 PostgreSQL 执行。
