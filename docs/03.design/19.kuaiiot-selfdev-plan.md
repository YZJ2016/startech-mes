## 1. 问题与目标

开源仓有数采表、Edge Agent 和路线图，云侧服务不在槽位里。自研补云侧，现场采集程序不换栈。报表侧到最后一步才消费一条普通 HTTP 馈送。

### 1.1 目标

- 云侧能收 HTTP 入站、留最新快照、节流写回星制造设备状态
- 其后按六步补齐护栏、边缘运行时、物模型与趋势、事件与指令
- 最后把设备运营馈送登记为星报表已有的 HTTP 数据源类型

### 1.2 非目标

- 报表五段未完成时开工
- 在 W6 之前让星报表出现数采专用接口
- 在 W1–W6 内做 MQTT 订阅、ThingsBoard 或 JetLinks（见 KIO-D6，六步之后再做）
- 内置 MQTT Broker，或把 OPC UA / S7 做成可运行 Agent
- 没有 InfluxDB 时仍承诺趋势图
- 合并进 `startech-mes-basic` 或 UReport
- 新造一套数采表，或改已经进过库的迁移文件名

## 2. 落点与依赖

```text
现场   edge-agent/（Modbus TCP，已在仓）
云侧   apps/kuaiiot
         入站、快照、写回、告警、边缘配置、物模型、事件与指令
写回   星制造设备状态（equipment.uuid，data_source=sensor，≥5 秒）
报表   仅 W6：星报表 HTTP 数据源读取 equipment-ops-feed
```

槽位收归与星报表同一取舍：忽略规则和 `PRO_APPS` 去掉 `kuaiiot`，不对这个目录做私仓组装。骨架对齐 `apps/kuaiai`。

依赖：

- 表：迁移 519–525 已有 `apps_kuaiiot_*`。迁移文件名里的 wave 编号与本文六步不一致（例如边缘配置、产品物模型所在文件的序号）。能力顺序以 KIO-W1–W6 为准，不按文件名重排，也不为此改迁移文件名。
- 现场运行时：`EDGE-AGENT-RUNTIME.md` 与已入库 Agent。W3 补的是云侧配置下发、心跳和批量续传；Agent 协议仍只跑 Modbus TCP。
- 写回：只写星制造已有设备状态，数采不维护第二套设备台账。
- 路线图与联动说明只提供字段与模块名。本文六步覆盖它们的能力时，以本文边界为准。MQTT 订阅、ThingsBoard、JetLinks 不拉进 KIO-W1，按 KIO-D6 放在六步收口之后。

租户沿用快格现有行级 `tenant_id`。无租户上下文不读数采表、不写回设备状态。设备 token 只在服务端校验，文档与日志不回显。

## 3. 六步边界

### 3.1 KIO-W1 入站闭环

设备 token、HTTP 入站、幂等（已有 `ingest_dedup`）、最新值快照（`tag_snapshots`）、按 `equipment.uuid` 写回设备状态。节流至少 5 秒一条，`data_source=sensor`。

本步不包含 MQTT 订阅、ThingsBoard、JetLinks、Influx 趋势、告警和指令。告警在 W2，趋势在 W4，指令在 W5。三条平台入站在六步收口之后，见 KIO-D6。

### 3.2 KIO-W2 护栏与预填

状态护栏：写回时尊重设备不可覆盖的状态（停用、报废、未闭环故障、进行中维修一类，细则沿用路线图已写的护栏语义）。点位模板。阈值告警（`alert_rules` / `alerts`）。报工与点检预填。

### 3.3 KIO-W3 边缘运行时

云侧下发边缘配置（`edge_configs`）、接收心跳、接受断网后的批量续传。OPC UA / S7 只做配置校验，不交付对应 Agent。可运行采集仍只是 Modbus TCP。

### 3.4 KIO-W4 物模型与趋势

产品物模型（`products`）、按产品批量建设备、离线告警。趋势只认租户自建 InfluxDB，见 **KIO-D8**。未配置 InfluxDB 时趋势不启用，不用 `tag_history` 顶上；W1 的最新值快照和设备状态写回仍然可用。

### 3.5 KIO-W5 事件与指令

事件、指令闭环（`device_commands`）、设备分组（`device_groups`）、消息追踪（`message_logs`）。MQTT Broker 仍不内置；要消息通道时外接。

### 3.6 KIO-W6 与报表的衔接

这是两边唯一的衔接点。数采提供 `equipment-ops-feed`。星报表把它登记为一条 HTTP 数据源（地址必须落在报表已有的登记表里）。大屏组件绑定 `ops_metrics` 等路径，路径名沿用 `KUAIREPORT-LINK.md` 已列的馈送字段。组件仍是普通大屏组件，数据源类型仍是 HTTP。

OEE 在本步随 `equipment-ops-feed` 一起计算，结果放进 `ops_metrics`（如 `oee_live`），见 **KIO-D7**。仅当同时有传感器状态分段和已审核报工良品率时才计算；缺一则该指标空着，不填默认值。馈送里的其它字段照常给出。状态分段来自 W1 已写回的设备状态。

W6 之前，星报表设计（18）不增加任何数采专用接口。

### 3.7 六步之后（KIO-D6）

MQTT 订阅、ThingsBoard 拉遥测、JetLinks 拉遥测在 W6 收口后另开，不插入 W1–W6。三条路都写入 W1 已有的同一条入站，不各建一套快照或写回。MQTT 只订阅现场自备的 Broker。本段是后续必做的能力边界，不是六步里的一步，也不写成可放弃。

OEE 已由 **KIO-D7** 放在 KIO-W6，不在六步之后另开，也不在 W6 之前为了大屏提前造指标。

`apps_kuaiiot_tag_history` 已在迁移 519。已由 **KIO-D8** 收口：不作为无 Influx 时的趋势数据源，不用于趋势折线，也不做降采样替身。本决定不删表、不改已经进过库的迁移文件名。未另拍板前，产品不往这张表追加采样来充当历史趋势。
