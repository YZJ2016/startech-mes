## 1. 问题与目标

六处现网可以在检查失败、未检验、补齐失败或关系直写时继续成功。本设计把它们收成硬约束。停机记录（`station_operation_downtime`）、安灯（`station_andon_call`）、出货检验（`assert_oqc_for_outbound_lines`）、先进先出（出库 `fifo_mode`）、有 BOM 时的下达缺料、租户强制隔离、库存幂等键均已有，本设计不改语义。

### 1.1 目标

- 入库在管理标志读失败时不过账；无 BOM 不下达成「不缺料」
- 委外收货与采购来料同一套 source 判定
- 预付补齐失败能在采购订单上看出未补齐
- 需求清单里的内部关系写只经统一入口，失败语义逐处固定
- 按序列号能查到出入库单据，撤回留痕
- 关键工序未检验不计报产出；简易模式不凭报工合格数完成

### 1.2 非目标

与需求「明确非目标」相同。金蝶、飞书、OA 只出现在这里：不设计迁法。不拆上帝服务，不做多级族谱，不新造 8D，不新造检验类型，不把无 BOM 拒绝扩到开工和报工。

### 1.3 设计依赖

```text
spec 140 的 inbound_inspection_required（代码已按 source 区分）
    └── PG2 必须先沿用这套判定，再谈委外确认

resolve_inspection_policy / resolve_ipqc_for_work_order_operation
    └── PG6 的关键工序定义依赖这套 eff 与 source，不依赖新标志

库存过账与 MaterialSerial 同一事务（spec 141 锁序）
    └── PG5 台账写入失败必须连同过账回滚

PG1、PG3、PG4 之间没有语义先后
```

这是语义依赖，不是排期。

## 2. KR-PG1 — 检查失败必须拒绝

### 2.1 仓库管理标志

证据：`inventory_service.py` 714–719 行捕获异常后把批号/序列号强制校验跳过。出库 1225 行没有这段捕获。

决定：

- 入库读标志失败：抛业务错误，本笔过账拒绝。不把标志降成 False。
- 读成功且两个开关为 False：仍按现网跳过强制校验。物料 `batch_managed` / `serial_managed` 与开关的组合不改。
- 出库读失败已经拒绝。不在出库再加一套降级或第二套校验。

失败语义：拒绝该笔库存过账（与所在单据确认同一事务则整单回滚）。不写「跳过校验仍入库」。

数据：不新表。

### 2.2 无 BOM 的下达缺料

证据：`check_material_shortage` 4204–4214 行把 `NotFoundError` 收成 `has_shortage: False`。`release_work_order` 4553–4571 行只在 `has_shortage` 时拒绝。有 BOM 且缺料时这段已经拒绝。

决定：

- `check_material_shortage` 在没有 BOM 时必须带出 `bom_missing: true`。这个结果不得再被下达路径当成不缺料。
- `release_work_order` 在 `check_shortage` 为真且缺料拦截级别命中「下达」时，见到 `bom_missing` 则 `BusinessLogicError` 拒绝下达。
- 有 BOM 的需求展开、`is_kitting_inventory_material` 跳过服务/委外/虚拟件及发料 none、缺料文案与拦截级别，不改。
- 开工、报工、生产管控、异常、缺料查询 API 仍只看 `has_shortage`。它们不因 `bom_missing` 拒绝。共享函数若仍把无 BOM 的 `has_shortage` 留成 False，这些调用方行为不变。

失败语义：拒绝这一次下达。不改工单状态。

数据：不新表。

## 3. KR-PG2 — 委外收货套用来料检验

### 3.1 现状

`create_material_receipt` 在事务里把 `OutsourceMaterialReceipt.status` 写成 `completed`（363 行），并增加委外工单已收数量（372–385 行），提交后 `_schedule_stock_for_outsource_receipt` 异步入库。`complete_material_receipt` 只把非 completed 改成 completed，不过账、不检验。模型注释里的状态是 `draft` / `completed` / `cancelled`，创建路径不经过 draft。`IncomingInspection` 没有委外收货字段。`_normalize_legacy_draft_receipts` 在列表和详情把 draft 改成 completed。

采购确认前的规则已经是 `assert_iqc_for_purchase_receipt_lines`：先 `inbound_inspection_required`，必检则查挂在该入库单上的来料检验，合格判定用 `iqc_inspection_passed_for_inbound`；让步用 `defect_accept_material_ids_for_purchase_receipt`（`DefectRecord.disposition == "accept"` 且 `incoming_inspection_id` 非空）。

### 3.2 决定

不新造检验类型，不复制一套 source 判断。

来料检验单增加可空的委外收货单关联（标识与编码快照，与 `purchase_receipt_id` / `customer_material_registration_id` 并列）。`source_type` 增加委外收货取值。确认前按收货物料调用已有 `inbound_inspection_required`（环节 `iqc`）。必检时，该收货单下必须已有来料检验，且 `iqc_inspection_passed_for_inbound` 为真。物料级显式免检与环节/模块关闭：不要求检验单，创建可以按现网完成并过账。

让步：不给 `DefectRecord` 再加委外外键。放行条件是不良单 `disposition == "accept"`、`status == "processed"`，且 `incoming_inspection_id` 指向本收货单的来料检验。draft 让步单不放行。这与采购「必须有单」同一口径，只是用检验单反查，不新造 8D。

挂载点不用异步过账任务。必检时 `create_material_receipt` 只落 `draft`：不过账、不增加委外工单已收/合格数量、不排库存与应付。检验单挂在这张 draft 上。`complete_material_receipt` 在改成 `completed` 并过账之前做上述断言；通过后才过账并回写委外工单数量。免检与环节关闭仍走创建即完成，避免多一次确认。

`_normalize_legacy_draft_receipts` 不得再把 draft 扫成 completed。否则列表查询会绕过确认门禁。历史「创建时已入库但状态仍是 draft」的补写停用；那些行的库存是否已入，不在本设计里重放。

失败语义：必检且无合格来料检验、也无已处理让步单时，拒绝确认。draft 保留，库存不动。断言失败不把单据写成 completed。

数据：来料检验单增加可空委外收货关联。不新检验单表，不新让步表。

## 4. KR-PG4 — 内部单据关系收口

入口只使用 `DocumentRelationNewService.create_relation` 与 `delete_relation`。`create_relation` 在四键已存在时抛「关联关系已存在」（158–159 行）。`delete_relation` 按主键删除时找不到抛 `NotFoundError`；按业务键删除要求四键齐全，0 行不抛（453–506 行）。`batch_create_relations` 失败跳过，本设计禁止用它迁移下列各处。

一侧全删（只知道 source 或只知道 target，或两侧分开删）不能一次业务键调用完成。决定：先按现有过滤查出命中行（读可以继续用 `DocumentRelation.filter`），再对每一行 `delete_relation(tenant_id, relation_id=行.id)`。不新增「按单据一侧批量删」的平行入口。0 行是显式幂等成功。删除进行中若主键已不存在，视为这一行已被删掉，显式幂等成功，不把整单打失败。

编码快照和分摊 `notes` 不是创建或删除。`create_relation` / `delete_relation` 不改已有行的 code 或 notes。删了再建会换主键并丢掉 notes、relation_desc。决定：在同一个 `DocumentRelationNewService` 上增加两件更新——按单据刷新 source/target 编码快照，按关系主键写 notes。调用方不得再 `filter().update()` 或 `rel.save()`。这是同一入口上的更新，不是第二套关系服务。

## 5. KR-PG5 — 序列号单据归属

### 5.1 与现有数据的关系

明细行 `serial_numbers` 是录入。过账时仍从行上读取，不从台账反写行。

`MaterialSerial` 继续是序列号主数据：身份是组织内 `serial_no`，当前状态仍由入库 832–875 行与 `_mark_serials_out_stock` 1105–1138 行维护。不新建第二套序列号主档，不把单据字段塞进 `MaterialSerial` 代替流水。

`MaterialStockMovement` 是数量流水，没有序列号。不往这张数量流水上塞序列号列表来冒充台账，避免一条数量行对多件货无法查询。

查询真相是新的出入库留痕台账：一件序列号在一次出入库动作上一行。

### 5.2 新实体职责与字段意图

职责：回答「这件序列号经过哪些出入库单据、当前归属哪一张」。不回答父子件、投料族谱、工序消耗。

关键字段意图：

- 组织、序列号、物料。序列号字符串与 `MaterialSerial.serial_no` 相同，不另编主键身份。
- 方向：入或出。
- 移动类型、来源单据类型、来源单据 id、来源单据编码。类型与库存过账已有的 `source_type` / `movement_type` 同一套词，不另起一套单据类型码。
- 库存幂等键，与序列号一起区分「同一过账重试」。同一幂等键加同一序列号已有行：显式幂等成功，不插第二行。
- 发生时间、操作人。
- 反向指针：撤回行指向被冲销的那一行。空表示正向流水。

不写迁移文件名。

### 5.3 哪些动作记一笔

凡是 `InventoryService` 入库或出库路径带了非空 `serial_nos` 的过账，每个序列号记一行，与 `MaterialSerial` 状态变更同一事务。覆盖现有增减库存调用点里实际传入序列号的单据，包括采购入库、成品与半成品入库、其他入出库、生产领退料、销售发货与退货、采购退货、借还料、客供料、委外收货、报废、装配拆卸。没传序列号的数量过账不记台账。

撤回（现网 `source_type` 带撤回，或出库冲入库）不删除、不改原行。追加一行相反方向，反向指针指向原行。再确认入库若现网允许把已在库序列号对齐（848–861 行的再确认容忍），台账同样只在没有对应正向行时追加；已有则幂等成功，避免重试双行。

失败语义：台账写入失败则该笔库存过账整笔回滚。不允许库存已变、台账没记。

当前在哪张单：按序列号取时间序，跳过已被反向指针指到的正向行之后，最后一笔正向行的来源单据。历史行保留可查。

## 6. KR-PG6 — 过程检验卡住报产出

### 6.1 关键工序

不新增关键工序标志。判定沿用 `resolve_ipqc_for_work_order_operation`（工单工序落章优先，否则工序主数据），其 eff / source 来自 `resolve_inspection_policy` 与 `resolve_ipqc_policy_from_stages`。

| eff | source 典型值 | 是不是关键工序 |
| --- | --- | --- |
| `plan` | `operation`、工单工序落章 | 是 |
| `simple` | 同上 | 是 |
| `none` | `default_none`、`stage_disabled`、`module_disabled` | 否。完成与报产出仍可用报工合格数 |

`work_order_override` 等把 eff 抬成 `simple` 或 `plan` 时，按抬高后的 eff，仍是关键工序。不把 `default_none` 改判成必检。

### 6.2 方案模式保留

`resolve_operation_transfer_qualified` 在 `mode == "plan"` 时继续调用 `resolve_ordered_plan_transfer_qualified`。未检完不得把工序标 `completed` 这条保持，函数仍是 `_effective_completion_quantity` → `_maybe_mark_operation_completed`。

不把让步数量加进可转下道。非末道的可转下道数量保持现网，避免改已经按检验放行数流转的在制。

### 6.3 简易模式完成

`mode == "simple"` 时，`resolve_operation_transfer_qualified` 不得返回 `woo.qualified_quantity`。

可计入完成的数量 = 本工序 `ProcessInspection` 上 `ipqc_inspection_passed_for_transfer` 为真的合格数量合计。检验单仍是过程检验单，创建仍走 `ProcessInspectionService.create_inspection_from_work_order`。不新造简易检验单。

该数量小于工单计划数量时，`_maybe_mark_operation_completed` 不得标 `completed`。状态报工（`reporting_service.py` 1640–1644 行）在关键工序上不得因报工数量大于 0 直接标完成，改走同一套完成数量。

报工自动建过程检验今天只在 eff 为 `plan`（`quality_automation_service.py` 80 行）。简易模式若永远不建单，完成条件无法达到。决定：同一自动建单函数在 eff 为 `simple` 时也建 `ProcessInspection`。建单失败不得把工序算完成；报工记录本身可以留下（现网自动建单失败只 warning，完成判定另看有没有放行单）。不因此新造单据类型。

`mode == "none"` 仍返回报工合格数。环节关闭和模块关闭保持可完成。

### 6.4 报产出与让步

报产出在本设计里两处：

- 工单头 `completed_quantity` / `qualified_quantity` 今天抄末道报工累计（`reporting_service.py` 1688–1692 行）
- 末道自动入库今天用报工 `qualified_quantity`（855–857 行）

末道不是关键工序：这两处保持报工合格数。

末道是关键工序（`simple` 或 `plan`）：这两处只认「过程检验放行合格数 + 已处理让步数量」。放行合格数用 `ipqc_inspection_passed_for_transfer`。让步数量是这些过程检验单上 `DefectRecord` 满足 `disposition == "accept"`、`status == "processed"`、`process_inspection_id` 指向该检验单的 `defect_quantity` 合计。没有这张已处理不良单，不合格数量不得进入报产出，也不得触发自动入库。draft 让步单不算。

方案模式末道的报产出可以含让步，可转下道数量不含让步。两者允许不一致：转下道服务的是后道在制，报产出服务的是末道能否记成产出。

放行合格数与让步合计为 0：不更新工单头产出为报工合格数，不自动入库。报工记录仍可保存，检验单仍可后补。后补放行后再计产出。

不新造 8D，不新造让步单据类型。FQC 成品入库门禁已有，本设计不改 `assert_fqc_for_finished_goods_receipt`。

失败语义：关键工序未检验且无已处理让步单时，拒绝把该数量记为产出、拒绝自动入库、拒绝把简易模式或状态报工标成工序完成。不是拒绝保存报工草稿或已审核报工行本身。

数据：不新表。让步用已有 `DefectRecord`，检验用已有 `ProcessInspection`。

## 7. 风险

| -------------------- | ---------------------------------------------------------------------- |
