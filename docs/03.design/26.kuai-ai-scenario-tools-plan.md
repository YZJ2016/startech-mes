# KU-AI 制造场景与 Tool 目录设计

- 日期：2026-10-23
- 需求：`docs/02.requirements/25.kuai-ai-scenario-tools-gaps.md`
- 上游基线：`docs/03.design/16.kuai-ai-rebuild-plan.md`、`docs/03.design/24.kuai-ai-operational-layer-plan.md`
- 设计性质：场景梳理 + Tool 粒度模型 + HITL 接入方向；不包含实现任务清单
- 证据边界：§2 现状均来自已读源码；§4 场景所列“可复用服务”按 `apps/*/services` 文件名与方法名初筛，**签名、数据范围、权限码未逐个核实**，实现 spec 必须逐项复核，不得直接当契约。

## 1. 设计结论

1. 场景按 ISA-95 / IEC 62264 Level 3（MOM）四类活动（生产、质量、维护、库存）加计划/供应链、工程/PLM 两域组织，再按工厂角色落到 26 个场景。
2. Tool 采用**业务对象中心 + 闭集枚举视图**粒度（用户已选 B）：一个 Tool 对应一个业务对象或一项分析能力，场景差异由 Agent 档案（提示词 + 勾选 Tool + 知识库）表达，不按场景增 Tool。按 SC-D7 权限边界拆分后，P1 为 23 个，全目录约 35–40 个，覆盖 26 场景（§5.2）。
3. 存量 11 个 Tool 按新目录合并/改名，并以 aerich 数据迁移改写 Agent 档案 `enabled_tools`（用户已选 B），不保留别名映射。
4. 写类 Tool 先接 HITL 确认闸再扩充（用户已选 C），本条推翻 KR-D15“本期不做”；机制沿用已收口的 KR-G3：LangGraph interrupt + checkpointer，确认后 `Command(resume)` 续跑同一 run，消息表仍写、checkpoint 只存执行现场。
5. Pulse 新领域 detector、页上下文摘要与 L1/L2 Tool 共享同一领域事实层与格式化函数，判定口径只有一处。
6. 能力矩阵能力卡绑定智能体库场景实例（用户已选 A），点击携带 `agentKey` + `agentId` 走既有档案装配与场景守卫；卡片状态与点击后实际执行路径一致。

## 3. 场景框架

- **活动轴**：计划/供应链、生产执行、质量、维护（设备/模具/工装）、库存、工程/PLM、管理汇总。
- **角色轴**：计划员、采购、销售、车间主任/班组长、操作工、质量工程师、设备工程师、仓管、工艺工程师、管理层。
- **交互形态**：问数（读事实）、诊断/归因（多源事实组合）、推荐（基于事实给建议，LLM 不参与判定）、知识问答（RAG）、录单（StructuredDraft）、执行（写，经 HITL）。

## 5. Tool 粒度模型

### 5.1 规则

1. **一个 Tool = 一个业务对象，或一项可复用分析能力**。视图/指标/模式差异用闭集 `enum` 参数表达；新增场景优先新增 Agent 档案，不新增 Tool。
2. **权限边界即 Tool 边界**（SC-D7）：`tool_bridge` 每 Tool 只挂一个 permission，同一 Tool 的全部视图共用该权限；视图需要不同权限码时拆为独立 Tool，handler 内不做按视图的二次权限判断。
3. **只读 Tool 返回有界摘要文本**（沿用 `limit ≤ 20`、只留编码/名称/数量/日期/状态/风险描述），service 不收用户的统一走 `_apply_scope` / `_scoped_row_ids` 补数据范围。
4. **LLM 不参与判定**：风险、严重度、计数、合格与否由领域 service 确定，Tool 只转述事实。
5. **写 Tool 全部受 HITL 确认闸**（§9）；无 HITL 不开放新增写 Tool。
6. **禁止**通用 SQL / 自然语言查库 Tool；kuaireport 系统报表数据集暂不开放给 AI（SC-D10），其用户级数据范围另立缺口。

### 5.3 预置智能体与 Tool 组合

spec 181 六个预置场景模板的 `enabled_tools` 随 §10 迁移改为新名。P1 模板组合见 spec 201（新增 `shift-lead` 班组长助手、`order-delivery` 订单交期助手、`work-instruction` 作业指导助手，并更新库存、采购、质量三个既有模板定义）。预置档案默认不含写 Tool（Y4=a 停用+空授权），唯一例外是 S10 异常上报（Y6=a）。P2/P3 每个 Tool spec 同单元登记其场景模板（Y3=a），模板 key 与能力矩阵场景卡 1:1（Y1=a），默认绑定同 key 预置实例（Y2=a）。

## 6. 知识语料分类

知识底座（`apps/kuaiai` knowledge/corpus）不变，按语料类型建库，由管理员在档案上显式选库（沿用设计 24 §5.3）：

| 类别 | 典型内容 | 服务场景 |

| SOP / 作业指导 / 工艺文件 | 受控 SOP、工艺卡、换型指导 | S11 S24 |
| 设备手册与维修经验 | 设备说明书、故障代码表、维修记录摘要 | S17 S19 |

| 系统操作指南 | MES 页面操作说明 | 智能实施（guide） |

SOP 已在 `master_data sop_control_service` 受控管理。按 SC-D11：`publish` / `obsolete` 成功后投递 Taskiq 异步任务，按 SOP 版本幂等入库或下架到配置的目标知识库；任务失败不回滚 SOP 发布，失败可见可重试。载体内容解析能力、目标库配置位置与 KU-AI 未安装时的处理在 S11 spec 核实。

- **Pulse**：inventory、quality、equipment 三个 detector 底层分别调用 `inventory_alert_service`、`exception_service`、`equipment_fault_service` 与 kuaiiot 告警等现有领域判定（待核签名），产出统一 `PulseItemOut`；`query_pulse_signals` 直接复用 `run_pulse` 结果，不另写判定。
- **页上下文**：`page_context._RESOURCE_READERS` 扩展时复用 L1 Tool 的单据格式化函数；`_SCREEN_PAGE_NAMES` 按需扩到销售单、采购单、检验单、设备台账等页面，仍只信服务端白名单。

## 8. 能力矩阵与档案打通

1. **入口统一**：能力矩阵与智能体库共用“场景实例 → Agent 档案”一条执行链。**矩阵按场景模板逐场景出卡**（Y1=a：2026-10-23 选定）：hub `capabilities[]` 由 `SCENE_TEMPLATES` 驱动，`capability_key` 即模板 key；原 `data_query` 泛卡移除（Y5=a），`guide`/`recommend` 落地时同规则。每卡下发绑定的实例 key 与 `agent_profile_id`（脱敏规则同设计 24 §11.2）。
2. **前端**：`openKuAsk` 对场景卡写入 `agentKey` + `agentId`（与智能体库“打开 KU-Ask”同一写法），`capabilityMode` 继续作为首问标识随附。
3. **后端发送**：请求携带 `agent_key` 即触发既有 `guard_scene_agent_key`，再进 `assemble`；不新增守卫、不改 `/core/ai/chat/completions` 契约。
4. **状态**：`_build_capabilities` 对每卡按当前用户计算：已解绑 / 模板或实例关闭 / 档案停用或删除 / 无使用权 / chat 未就绪 / 档案 `enabled_tools` 不含任何业务 Tool → 非 ready，并给具体 `disabled_reason`；移除以全局注册表判就绪的口径。
5. **绑定配置**（SC-D14）：存站点设置 `integrations.kuaiai` 槽，在 `/settings` 配置，复用既有版本锁与深合并保存，不改场景实例表结构。**默认绑定**（Y2=a）：`capability_bindings` 只存管理员覆盖；无条目时自动解析到同 key 预置实例，显式 `null` 为解绑——租户零配置即打通，仍可改绑。
6. **`ask` 卡**（SC-D15）：保持纯对话路径 A，不绑定档案。
7. **场景模板随 Tool 同单元交付**（Y3=a）：P2/P3 各 Tool spec 内登记其场景模板（key、Tool 组合、system_prompt、插画、`category`），预置档案停用 + 空授权（Y4=a）；模板落地即出卡并默认绑定，管理员只需“开模型 + 启用档案 + 授权”。例外：S10 异常上报模板预置档案含写 Tool（Y6=a，确认闸逐次兜底）。
8. **矩阵分组与检索**（Z1–Z3=a，spec 222）：模板带 `category` 闭集字段，hub 按业务域分组渲染、分类可收起且状态存 localStorage；页头检索框按卡名/描述/分类即时过滤，`ask` 卡不参与。

## 9. HITL 确认闸（方向）

机制按 KR-G3 已收口内容，不另选：

1. 写 Tool 在 manifest 声明为需确认（字段名由实现 spec 定），装配时转为 LangChain `HumanInTheLoopMiddleware(interrupt_on={tool: ...})`，与现有 `build_tool_guard_middleware` 并存，RBAC/审计仍在 guard 内。
2. `build_agent` 传入 checkpointer；thread_id 绑定会话（租户 + 会话 ID），中断时 SSE 下发待确认动作（Tool 名、参数摘要、业务对象）；用户确认/修改/拒绝后经新增端点 `Command(resume)` 续跑同一 run。新增端点为新增契约，不改既有 `/core/ai/chat/completions` URL、method 与响应外层。
3. 消息表照写（展示/审计真源），checkpoint 只存执行现场；确认/拒绝动作入 `core_ai_audit_logs`。
4. 存量两个写 Tool（报工、工单状态）同步纳入确认闸。
5. 信任中心 `_hitl_feature_state` 现以“`build_agent` 的 checkpointer 默认值非 None + 网关存在 propose/execute/approve/interrupt 路由”判定；HITL 落地须同步改为真实装配判定。
6. checkpointer 持久化（SC-D8）：基于 Tortoise 自实现 `BaseCheckpointSaver`，表结构走 aerich 迁移；不引入 psycopg 或 `langgraph-checkpoint-postgres`。saver 须有接口契约测试，并列为 langgraph 升级的必跑回归项。

## 11. 风险

| 风险 | 说明 | 处置 |
| --- | --- | --- |
| 数据范围遗漏 | 多数候选 service 不收 current_user | 每个 Tool spec 必须列出数据范围资源键并有越界测试 |
| 视图膨胀 | 枚举不断增长退化成“万能 Tool” | 单 Tool 视图上限由 spec 约定；超限或跨权限即拆分 |
| 上下文超长 | 诊断类 Tool 拼多源数据 | 沿用有界摘要与 `limit ≤ 20` |
| HITL saver 维护 | 自实现 saver 随 langgraph 接口演进 | SC-D8：契约测试 + 升级必跑回归 |
| 报表数据集越权 | 仅租户过滤 | SC-D10：不开放给 AI |
| Tool 数增长 | 按权限边界拆分后 P1 为 23 个、全目录约 35–40 个 | 每个 Tool 须对应单一业务对象 + 单一权限码；出现同对象同权限的两个 Tool 即视为按场景切分，需合并 |
