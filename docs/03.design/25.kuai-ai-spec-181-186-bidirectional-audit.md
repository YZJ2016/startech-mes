# KU-AI spec 181–186 双向实现审计报告

> 审计日期：2026-10-11  
> 审计范围：`docs/04.specs/181`～`186`、需求 24、设计 24，以及 `kuaigeyun-mes/riveredge-backend`、`riveredge-frontend` 中对应实现。  
> 审计性质：只读审计；本报告不包含代码修复。  
> 结论口径：测试通过仅证明已覆盖行为，不等于全部设计契约均已满足。

## 1. 结论摘要

181～186 已形成完整的前后端实现骨架：七页路由、operations API、场景实例、六场景只读 Tool、Pulse、Corpus、Trust/Insights、Settings、权限注册和迁移均有实际代码；前后端 manifest 的 40 个权限码完全一致，`menu_config` 也一致。本次重新执行 6 个后端专项测试文件，共 **189 passed**；前端 `opsData.test.ts` 共 **7 passed**；前端生产构建成功。

但当前不宜把 186 标记为“整体无遗留缺陷、已完成验收”。审计确认 2 个高优先级正确性问题、3 个中优先级设计偏离/并发风险，以及若干验证证据缺口：

- Pulse 每个已接领域只读取前 200 条，却把截断后的集合当作真实总数并继续分页，超过 200 条时汇总和后续页不正确。
- 智能体库把已经不再是运行时真源的模型目录行当成 chat 就绪兜底，可能把实际无法调用的场景标为可用。
- Hub 的“智能问数”没有核验“至少一个只读 Tool”，知识检索入口也从设计的 `/corpus` 偏到了 `/knowledge`。
- Settings 对连接器的校验不处于 SiteSetting 锁事务内，连接器在校验与提交之间被停用/改角色时可写入失效选择。
- 生产延期在“今天已过计划完成时刻”时把日期差 0 强行显示成“逾期 1 天”，与设计的日期差口径不一致。
- 186 明确要求的七页×四视口、键盘、真实三角色和真实 FAQ→RAG→审计→统计链没有完成；当前无 KU-AI E2E 用例，本次也因本地后端/可用凭据缺失无法补证。

因此本次审计结论为：**实现主体存在，但 spec 186 的整体验收结论应退回“有条件未通过”，待用户确认修复范围后处理。**

## 2. 审计方法与证据等级

### 2.1 双向检查

1. **spec → code**：逐项核对 181～186 的范围、公开接口、权限、事务、页面、迁移和验证策略是否有实现落点。
2. **code → spec**：检查新增模型、路由、字段、权限、业务行为和测试是否能追溯到需求 24、设计 24 或某一 spec。
3. **设计 → 实际**：以需求 24、设计 24 为上位约束，检查实现是否出现行为、入口、状态语义或布局偏离。
4. **重新验证**：不采信 spec 中既有“通过”文字，重新运行可执行测试与构建。

### 2.2 证据等级

- A：本次实际执行的命令或当前浏览器实测。
- B：当前源码、迁移、manifest 的直接证据。
- C：spec 自述、历史验证记录或无法复现的人工记录，仅作线索，不作为通过依据。

## 4. 审计发现

### F-01 [P1] Pulse 的 200 条 detector 截断被误当成真实总数和完整分页

**性质**：spec → code 漏实现；实际行为偏离 182 与设计 24。

**证据**：

- `production.py` 与 `sales.py` 都在 ORM 查询阶段固定 `.limit(ITEM_LIMIT)`，且 `ITEM_LIMIT = 200`。
- `registry.run_pulse()` 只对 detector 返回的内存数组计算 `domain_totals`、summary 和分页。
- 公开 API 允许任意 `page>=1`、`page_size<=100`，但没有 `truncated`、游标或真实 total 查询。
- 182 要求统一分页、真实汇总，失败领域不计为 0；设计 24 要求 LLM 不参与计数，意味着计数必须来自完整确定性数据。

**实际影响**：某领域有 250 条异常时，页面只显示总数 200；请求第 3 页永远拿不到第 201～250 条。Hub 的 `pulse_count` 同样读取这个截断结果，顶部指标也会偏小。

**建议修复方向（待用户确认后实施）**：detector 返回可分页查询/总数，或 registry 采用有界但显式 `truncated=true` 的契约并调整产品口径。因为会影响公开响应契约，不能直接自行选择。

### F-02 [P1] 智能体库用模型目录行兜底 chat 就绪，可能产生假 ready

**性质**：设计偏离；运行时真源不一致。

**证据**：

- `agent_scene_service.is_chat_ready()` 先检查 `AiRuntimeConfig.public_status()`；失败或未配置时，又查询 `KuaiaiLlmModel` 中启用的 chat 目录行并返回 true。
- 设计 24 明确“应用连接器仍是 chat/embed 等角色连接和密钥的唯一来源”，并指出现行运行时已转向应用连接角色，模型目录保留列不是当前模型真源。
- 场景卡随后仅基于这个布尔值决定是否因 chat 未配置而降级。

**实际影响**：租户有历史启用模型目录行、但没有有效 chat 应用连接时，场景可能不显示“未配置可用的对话模型连接”；用户点击后才在真实 runtime 失败，违反“不伪造就绪”。

**建议修复方向**：删除目录行兜底，统一复用 runtime/selected connection 的就绪判定。需要同时复核历史兼容数据迁移策略。

### F-03 [P2] Hub 的能力状态和入口有两处与设计矩阵不一致

**性质**：spec/设计 → code 偏离。

**证据**：

1. “智能数据查询”只检查 `tools_enabled`，没有检查设计 24 §4.2 规定的“至少一个只读 Tool”；甚至 chat 未配置时仍可显示 ready。
2. “知识检索”状态按 RAG + 启用知识库计算正确，但返回入口 `/apps/kuaiai/knowledge`，设计 24 §4.2 和 §4.3 均指定 `/corpus`。

**实际影响**：Hub 可能把不可执行的智能问数标为 ready；知识检索卡把业务用户带到治理底座而不是本轮新增的知识语料运营页，示例兼容路径产生偏差。

**建议修复方向**：按能力矩阵统一状态计算；知识检索入口需由用户确认维持设计 `/corpus`，还是正式修改设计为 `/knowledge`。

### F-04 [P2] Settings 的连接器校验与 SiteSetting 提交之间存在并发窗口

**性质**：并发一致性风险；185 的“原子保存”只覆盖 SiteSetting 行。

**证据**：

- `update_settings()` 在进入 `in_transaction()` 之前读取并校验 chat/vision connection。
- 事务中只锁 `SiteSetting`，没有锁定或重新读取 `IntegrationConfig`。
- version 只由 SiteSetting 行生成；连接器的启停、删除或角色变化不会使旧 version 冲突。

**实际影响**：连接器可在预校验之后、SiteSetting 提交之前被另一请求停用或改角色，最终保存一个提交时已经无效的 UUID。正常低并发下不易出现，但与“全部 UUID/角色/启用状态校验通过后原子提交”的强语义不完全一致。

**建议修复方向**：在同一事务内重新校验连接行，或把连接版本纳入提交条件。具体选择涉及跨表锁与并发成本，按 AGENTS.md 应由用户决策。

### F-05 [P2] 当天刚逾时的生产工单被显示为“逾期 1 天”

**性质**：业务规则偏差。

**证据**：

- 查询条件以 `planned_end_date < 当前站点时间` 判断已逾时，这是合理的。
- 随后按业务日期计算 `(today - planned).days`，但用 `max(1, ...)` 把同日日期差 0 强制改为 1。
- 设计 24 规定“逾期天数由日期差确定”。

**实际影响**：例如今天 10:00 计划完成、当前 11:00 的工单会显示“已逾期 1 天”，事实文本夸大。严重度也可能因此被抬高。

**建议修复方向**：同日显示“已逾时”或“逾期 0 天”，并将小时级/日级口径写回 182 后再改规则。

### F-06 [P2] spec 186 的验收结论超过了实际证据

**性质**：spec ↔ code/验证记录不一致，不是单一代码缺陷。

**证据**：

- 186 AC10 要求七页在 1280×720、1440×900、768×1024、390×844 的 28 组截图，并包含 DOM、键盘、溢出检查。
- 186 的自身记录承认真实浏览器、真实三角色、FAQ→RAG→审计→统计链未执行，但又写“本单元无遗留可修缺陷”和“整体整链一致”。
- 当前仓库没有命中 KU-AI 新七页的 E2E 用例；页面主要依赖源码审查和 build。
- 本次本地浏览器只能到达登录页；本地 PC 前端可启动，但没有可用后端/凭据，无法生成当前页面证据。

**实际影响**：响应式、键盘、焦点、请求取消、保存冲突提示和真实权限跳转仍可能存在未发现的集成问题。现有文档会让后续开发误以为这些已经验收。

**建议修复方向**：先把 186 状态降为“条件未通过/待环境验收”，补齐真实环境证据后再签收。

### F-07 [P3] 验证记录与当前测试资产发生漂移

**性质**：文档可追溯性问题。

**证据**：

- 181 的 Affected Modules/Verification Strategy 指定 `test_spec181_operations_hub_library.py`，当前文件不存在；相关测试分散在 `test_s5_agent_scenes.py` 与 186 测试中。
- 184 记录 `opsData.test.ts` 为 8 项通过；本次按文档同一命令实际为 7 项通过。
- 直接执行 `node --test opsData.test.ts` 会因 Node 不识别 `.ts` 失败，必须使用文档中的 `--experimental-strip-types`；项目 `package.json` 没有固定这个专项测试脚本。

**实际影响**：后续人员难以按 spec 一键复现，且容易把历史数量当成当前证明。

**建议修复方向**：修复阶段统一测试文件命名与命令入口，验证记录只保留可复现命令和当次输出。

## 5. 未发现问题的关键契约

- 前后端 manifest 权限集合均为 40 项，双向差集为空；`menu_config` 完全一致。
- operations 新接口均保留 `/api/v1/apps/kuaiai/operations/*` 命名空间；既有 `/agents`、`/knowledge`、`/chat`、`/mcp` 路由未被替换。
- Corpus 没有重复新增文件/文本上传接口；FAQ 复用既有知识文档表及索引生命周期。
- Trust 不伪称 HITL 已完成；没有新增第二套审计表或 stats API。
- Settings 保存只白名单深合并 `integrations.kuaiai`，SiteSetting 行具备 `select_for_update()` 和 version 冲突检查。
- 场景迁移文件名 `20261012120000_kuaiai_agent_scenes.py` 大于当前目录此前 14 位时间戳，位置符合单一 `models` app 规则。
- 六场景写 Tool 未作为预置默认项；场景 Tool 走租户、业务权限与 DataScope 约束的专项测试当前通过。
