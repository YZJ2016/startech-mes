## 1. 问题与目标

产线需要一台常亮的触屏工位电脑完成执行闭环。办公室 PC 页面继续给计划和管理用。现有后端已经能开工、暂停、结束、快捷报工、安灯、文档、SOP 确认、人脸、资质和交接班。前端已有若干触屏页，主终端路由处于下线，安灯、刷脸、资质、交接班还没有页面。Electron 壳尚未作为本产品的交付物放进部署说明。

### 1.1 目标

- 工位电脑打开的是服务器上的触屏入口。请求渠道按当前路径计算：`/apps/kuaizhizao/production-execution/station` 及其子路径为 `station`，其余为 `pc`
- 执行动作沿用已有接口，报工渠道记为「终端」，`device_info` 带 `workstation_id`
- 壳保持稳定：全屏常亮、开机自启、本机工位、扫码枪
- 第一期在上述闭环内交付；SOP 与上岗资质默认不拦截开工

### 1.2 留在本文之外

- 电视看板、小程序、企业微信的排期
- 标签装箱 `/label-station`
- 计划、主数据、审批、财务的工位页面
- 安装包内的整站副本，以及单独编译工位业务代码的流水线
- `fast-deploy` 的工位打包脚本（现状见第 5 节）
- 开工接口内部调用 SOP 或资质检查
- 刷脸签发登录会话

## 2. 落点与依赖

```text
办公室浏览器   riveredge-frontend 办公室入口
工位页面       riveredge-frontend 同一份构建里的工位入口
               路径 /apps/kuaizhizao/production-execution/station 及其子路径，请求头 station
               其余页面为 pc。开发模式 VITE_CLIENT_CHANNEL 只用于本地整站调试
               随 API 发布到服务器
Electron 壳    kuaigeyun-mes/kuaigeyun-client/riveredge-app-station（主进程）
               全屏常亮、开机自启、本机工位、扫码枪
               窗口打开服务器上的工位入口
写入           现有 riveredge-backend
               前缀 /api/v1/apps/kuaizhizao/station
               权限 production-execution-terminal
               头 X-Client-Channel: station
```

依赖：

- 工位主数据用星制造已有工位。壳的本机配置记下这台电脑绑定的工位，页面绑定与之相同。
- 工序开工、撤回开工（已开工且无报工）、设备上下机（on / off）走工单接口。
- 暂停（缺料、待料、设备故障、换刀换模、质量异常、休息、其他）、恢复、结束走 `StationService`。数量报工须合格数达到计划；状态报工按目标数量记合格；暂停可以直接结束并关闭停机。
- 快捷报工走 `POST /reporting/quick`：接口现状支持数量、合格、不合格、工时、人员或小组，代报能力要求 reporting assign。方案 C 的默认工位角色不授 reporting assign、不展示独立代报入口，只开放已确认当前操作员的本人报工与小组报工。可同事务记不良，其后可上料 / 下料绑定，并由报工生成报废。渠道落「终端」。交接班汇总使用 `workstation_id`。
- 文档、SOP 确认（工单 + 工序 + 修订号 + 操作员，换版重确认）、四类安灯及联动、人脸登记 / 查看自己的 / 删除 / 比对、上岗资质检查与维护、交接班汇总与确认，均以现有实现为准。细则见缺口文档的「后端已有」。
- 租户与组织隔离沿用快格现有实现。

侧聊已看到的前端事实，设计按此衔接，不另起第二套触屏模板：主终端文件还在而路由已注释下线；工单详情、报工、SOP、图纸、程序查看仍挂在星制造普通路由上；安灯、刷脸、上岗资质、交接班没有前端调用。工位入口要把这些收成壳能打开的在线地址。第一期包含已在路由上的程序查看（**STN-Q1**）。

## 3. 第一期能力边界

第一期使用缺口文档列出的执行闭环，不增加新的写入路径。同一工位入口铺满现有闭环（**STN-Q1**、**STN-Q4**）。

页面：

- 绑定工位
- 开工到结束
- 快捷报工：默认工位角色开放已确认当前操作员的本人报工与小组报工，不开放独立代报入口。都走现有 `POST /reporting/quick`，渠道记为终端
- 四类安灯
- ESOP、图纸、工序文档
- 设备上下机
- 刷脸切换操作员
- 交接班
- 上料下料
- 报废
- 已在路由上的程序查看

页面开关：

- SOP 硬卡控默认关闭。打开后，页面先调用 SOP 确认检查，通过后再放行开工。
- 上岗资质硬卡控默认关闭。打开后，页面先调用资质检查，通过后再放行开工。组织没有任何资质记录时，后端默认放行，页面尊重该结果。
- 这两项默认关闭，不挡开工。
- 开工、撤回、暂停、恢复、结束接口保持现有契约，不在服务端把这两项检查嵌进开工。

会话（**STN-Q2**）：每台工位一个长期登录的纯 `station` 终端账号。点选只产生候选人；刷脸或员工码确认结果与候选人一致后，服务端创建数据库操作员会话。当前操作员不签发登录、不继承个人角色权限。客户端凭据只保存在当前页面内存；刷新、Electron 重启、异常退出或断电后不恢复。第一期身份确认失败时不允许降级。

计划、主数据、审批、财务留在办公室浏览器入口。

## 3.1 工位专用访问边界

- 工位路径不渲染 `BasicLayout` 与 UniTabs，改用独立 `StationLayout`。界面只保留工位、终端账号、当前操作员、任务、扫码、锁屏与退出所需信息和动作。
- 纯工位账号从 Electron 或普通浏览器登录都进入 `/apps/kuaizhizao/production-execution/station`；访问其他 PC 路由时用 replace 重定向回来。
- Electron 只允许认证必需路径、锁屏与工位入口及其子路径。非纯 `station` 账号、混合角色账号、管理员账号在壳内均拒绝进入，并清理当前会话回登录页。
- `STATION_TERMINAL` 是管理员主动加载的正式预设角色；加载幂等，不由迁移静默创建。权限使用显式最小集合，不按生产模块宽泛前缀匹配。
- `X-Client-Channel`、`window.stationShell`、URL 和本机工位只提供客户端上下文，不能替代租户、登录用户和 RBAC。

## 3.2 操作员确认会话

```text
Electron / 浏览器工位入口
  -> 纯 station 终端账号（认证、租户、RBAC）
  -> 候选操作员
  -> 刷脸或员工码与候选人一致
  -> 数据库操作员会话（业务归属门禁）
  -> 现有工位写接口
```

- 会话绑定租户、终端账号、工位、操作员与确认方式；保存签发、最后活动、关闭时间、状态和关闭原因。人脸特征与员工码明文不入表、不入日志。
- 服务端返回随机不透明凭据，数据库只存哈希。凭据放独立工位业务头，不替换现有登录 Token，也不改变现有 URL、HTTP method、登录认证头或响应外层结构。
- 会话不设固定有效期和闲置超时。显式换人、终端账号退出或下一次确认关闭旧会话。页面刷新、Electron 重启、异常退出或断电后客户端不恢复凭据，必须重新确认；下次成功确认时关闭该终端遗留活动会话。
- 未确认操作员时允许查看工单、SOP、图纸和程序等当前任务资料；开工、暂停、恢复、结束、报工、安灯、交接等产生业务记录的动作必须通过服务端会话门禁。
- 当前操作员只决定业务与审计归属。权限始终取终端账号的 `STATION_TERMINAL`；第一期不提供身份失败降级，也不提供刷脸提权。

## 4. 长期原则

这些原则约束以后的端，本文不把它们拆成任务。

- 壳保持稳定，页面跟随后端发布。执行数据只有一条写入路径：工位、以后的移动端，都打现有报工和安灯接口。
- 以后移动端上的仓库、巡检复用这套报工和安灯接口，工位触屏页留在工位入口，移动端不复制一份工位页面。
- 电视看板只读工位已经写入的事件。
- 将来部署只增加两件事：托管工位静态页，分发已经打好的 exe。业务代码仍走现有前后端发布。
- `kuaigeyun-mes/kuaigeyun-client/riveredge-app-station` 只放 Electron 主进程。业务 UI 留在 `riveredge-frontend`，避免两套页面分叉。改一个按钮，改前端仓库，随服务器发布。

## 5. 部署缺口（已知，本文不实现）

`fast-deploy` 现有相关脚本是 `install-h5` 与 `build.mobile.web.sh`。仓库说明把终端仓写成手机端加工位机，脚本侧只有手机端 Web。工位机 `.exe`（安装向导或便携）的打包不在本仓，也不在这些脚本里。

设计取舍：继续由现有发布流程交出工位静态页和 API。exe 在仓外打好再分发。本文不新增工位编译流水线，也不修改 `fast-deploy`。
