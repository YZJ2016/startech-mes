## 1. Spec

### Capability

- Name: 七页运营层整链、权限升级、回归与示例差异验收。
- Module: `kuaigeyun-mes/riveredge-backend`、`riveredge-frontend`；验收记录在本 spec。
- Priority: P0；181 → 185 → 182 → 183 → 184 全部完成后执行。
- Related requirement/design documents: `docs/02.requirements/24.kuai-ai-operational-layer-gaps.md`（KO-01～KO-08、§7～§8）；`docs/03.design/24.kuai-ai-operational-layer-plan.md`（§3、§15～§16）；spec 181～185。

### Business Goal

避免各单元单独通过但菜单、权限、设置、知识检索和审计链不一致；用真实租户、真实 API 与可复核证据关闭剩余差异。仅允许修复本验收发现且归属 181～185 的缺陷，写回原单元记录；新功能另立需求/spec。

### Scope

In scope:

- 七页 `/hub`、`/agent-library`、`/pulse`、`/corpus`、`/trust`、`/insights`、`/settings` 菜单、路由、权限、响应式和交互整合；原 `/agents`、`/knowledge`、`/chat`、`/mcp` 回归。
- 两端 manifest 权限一致性，应用安装/升级权限注册、预设角色与存量租户的最小授权核对。
- KU-AI 安装/存量升级六模板→本租户六份停用、空授权的真实 Agent 档案→六实例绑定、六场景只读 Tool/无连接待配置，以及管理员在既有 `/agents` 手工配置 ROLE/USER 并启用、后续复制/定制整链；自动首问→知识检索→审计→调用分析更新；Settings 总开关与实例单项开关对 hub/智能体库/RAG 的实际影响。
- 后端全量 pytest、前端 build、四视口浏览器截图与示例系统差异表；失败项归属原 spec 并复验。

Out of scope:

- 新建业务页面/接口、第二套认证/知识体系、HITL 实现、示例系统不可见私有 API 或未知算法复制。
- 无授权批量授予存量自定义角色、新建 FAQ 表、自动新增 Pulse detector。

### Acceptance Criteria

1. 七个菜单各指向唯一新路由，直接刷新不 404；两个菜单分组与旧四路径均可用，未授权菜单/URL/API 都按 181 矩阵处理。
2. 前后端 manifest 注册同一组 7 display + library:manage + corpus create/update/delete/export + settings:update 权限；根 entry 不变；安装/升级后 `core_permissions` 可查，角色权限页可分配，默认预设按 181 的最小策略。存量自定义角色不自动获得权限，管理员逐项授权后才可使用。
3. 检验三类岗位/角色：租户管理员可访问获授七页与操作；知识运营人员只可访问获授 corpus 操作及既有知识库授权范围；普通员工只可访问获授 hub/library/pulse，不能因运营展示权限读取治理数据。无对应预设 code 时使用管理员显式配置的测试角色而不臆造内置角色。
4. 仅拥有 `kuaiai:insights:display` 或 `kuaiai:trust:display` 而没有 `kuaiai:entry:read` 的账号不能进入对应页面/请求数据；具备两码可调用现有 stats/audit，不改 core 权限。
5. 新安装和已安装升级租户各自确有六份与六卡逐一绑定的 Agent 档案，初始均为停用、`grant_mode=ROLE`、`default_model_id=null`、无 grants；重复同步不重复建、覆盖定制/改绑/授权/停用或恢复手工软删；预置失败不报告成功，重试可补缺。安装后未配置授权前任何用户都不能使用六档案，也不得被误判已就绪；管理员在 `/agents` 选择 ROLE/USER、配置名单并启用后，获授用户才可发问，未获授员工仍失败关闭。额外从本租户源档案复制的档案仍停用、无 grants，跨租户绑定/复制拒绝；后续新增模板不改前端固定数组。
6. 六场景分别调用有业务权限与数据范围校验的最小只读 Tool，实际库存/工单风险/采购/排程/质量/供应商事实有来源；写 Tool 默认不可用，无数据时为空态、不猜答。安装不自动建空库/绑定全部库，管理员显式选库后才测试知识检索；没有 chat 连接时展示待配置，不得以六份档案行存在宣称开箱可对话。
7. 有权限的用户从已绑定并获使用权的场景点击“打开并发送”只发送一次样例问题；启用 RAG 且同租户知识库含已索引 FAQ/文档时实际命中知识检索并产生可关联的审计记录，调用分析在统计窗口内最终反映调用（考虑异步索引/聚合延迟）；不得以 mock 响应代替此验收。
8. Settings 缺省六模板总开关为 true 仅代表可发现；未授权/未启用档案或 chat 未就绪仍 not_ready。模板总开关与租户实例 enabled 任一关闭时基础/复制卡仍可见但不能发送；重新打开后还需档案使用权。RAG 关闭时新会话不检索知识内容，开启并就绪后恢复；切换选中 chat/vision 及能力设置的失败事务不留下部分保存。
9. `/knowledge` 独占文件/文本添加、解析、切块与技术详情；`/corpus` 跨库搜索、FAQ、状态、批量重试/删除、JSONL、跳 `/knowledge`。FAQ 与普通文档使用同一知识库检索/软删除生命周期；跨租户 ID 不泄露。
10. 四档 1280×720、1440×900、768×1024、390×844 的七页截图对比记录布局、动作顺序、空态/失败态；无整页横向溢出、焦点可见且按键可达；截图不替代 DOM/键盘测试或宣称完全一致。
11. 后端 `uv run pytest`、前端 `npm run build` 实跑并记录命令、exit code、失败详情；未执行或环境阻断不得写通过。
12. 输出逐页示例系统/本地最终差异表：示例可见事实、本地实测、差异、是否符合兼容优先决策、责任 spec/剩余缺口；不能把未知服务端实现描述为事实。

### Rules and Constraints

Tenant isolation:

- 使用至少两个租户及不同授权用户验证所有跨库、Pulse、设置、审计和详情的隔离；平台超管的租户切换只沿用原有约定。

Security and masking:

- 截图、日志、下载、API 响应与测试证据不含 key/cipher/JWT、租户内部路径、完整异常栈；分别检验菜单权限与接口权限，不靠隐藏按钮作为鉴权。

Audit and lineage:

- 核对自动首问与搜索的既有审计字段、统计窗口与调用分析数据来源；不能只凭 UI 卡片数断言审计闭环。

AI/rule-engine rules:

- 自动首问在携带 agent_key 时须由服务端复核模板/实例绑定、双开关与档案授权；伪造 key、改写 agent_id 或绕过前端直调原 chat API 不得绕过，普通无 agent_key 对话仍按既有流程。RAG 是否检索以实际调用/审计或可验证测试替身证明，Pulse 不由 LLM 生成业务事实；HITL 未交付仍 not_ready。

Database rules:

- 验收不主动建表/改迁移；验证 181 场景实例迁移在新租户与已安装租户都补出六条物理实例和六份真实档案，克隆场景/停用档案同事务且不拷授权。FAQ 与现有知识文档、切块同生命周期，Settings 使用 SiteSetting 同行事务，Pulse 阈值在 TenantConfig，均按原 spec 验证。

## 2. Plan

### Implementation Approach

- 先核对 181～185 的实施/验证记录与需求 KO-01～KO-08；未交付前不签整体验收。
- 构建七页×三角色×四视口验证台账，覆盖旧入口、权限注册/授权/升级，缺失场景回填所属 spec。
- 使用隔离测试租户中的可清理测试数据完成设置、FAQ 索引、自动首问、审计和统计链；记录操作前后状态和异步等待判据，不能对生产数据执行破坏性清理。
- 汇总示例/本地最终差异，明确接受的兼容差异与未通过项；每个修复归属原 spec 并重跑相关回归。

### Affected Modules

- Modify: `docs/04.specs/181～185` 各自 §4 验证记录（仅对应单元存在需修复的缺口时）；本 spec §4/§5 记录实际结果和差异。
- Conditional modify: 验收暴露的问题只改对应 `riveredge-backend/src/apps/kuaiai`、`riveredge-frontend/src/apps/kuaiai` 或既有权限/设置接线，并按所属 spec 回归；没有缺陷时无业务代码改动。

### Public Contracts

- 不新增 API；逐项对照设计 §11、§12、181 权限矩阵；现有 `/agents`、`/knowledge-bases`、`/documents`、`/chat/completions`、`/mcp-servers`、core stats/audit 的 URL、method、认证头、响应外层维持不变。

### Persistence Changes

- 验收自身无迁移；若发现 schema 需求超出既定 spec，登记缺口并另走决策，不为通过验收临时加表。

### Transaction Boundaries

- 验证 Settings 版本冲突、连接无效和保存失败时 SiteSetting 角色/能力项均保持原值；FAQ 创建/索引/删除及批量部分成功按 183 的逐项语义。

### Risks

- 存量租户菜单缓存/权限注册未同步导致“可见但 403”；先检查权限注册，再核对授权，不通过给全员开放绕过。
- 审计/统计异步延迟使瞬时读不到最新数据；记录观测窗口与结果，不制造零值或“通过”。
- 示例系统只提供可见 UI 证据；差异表不推断未知服务端行为。

### Verification Strategy

- 后端全量测试、前端 build 加专项权限/升级/旧入口回归；真实浏览器四视口截图、DOM 与键盘操作记录；人工完成端到端链并查 API/审计/统计一致性。
- 记录每项预期与实际、租户/角色（脱敏）、测试数据边界、截图标识、命令退出码、未验证原因；阻断项不签收。
