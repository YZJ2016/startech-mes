### Business Goal

平台租户（`tenant_id=0`）像工厂一样用角色权限表决定回家侧栏与接口权限字，并能管理本租户的组织 / 机构 / 角色 / 用户。不再因「是平台运营」就加载全量菜单、发放 `*:*:*`。进入工厂（runAs）与 `/platform/**` 身份门禁保持现状。

### Scope

In scope:

- `SysMenuServiceImpl.selectMenuTreeByUserId` / `selectMenuList`：平台回家（`isPlatformOperator` 且非 runAs）按 `sys_role_menu` 取菜单，与工厂用户同一分支
- `SysPermissionService.getMenuPermission` / `getRolePermission`：平台回家不写 `*:*:*`、不注入 `SUPER_ADMIN`（`admin`）；角色与权限字来自本租户角色行
- 许可：租户 0 仍 `selectValidModuleCodes(0)==null`（不裁）；工厂许可语义不变
- runAs：仍 `selectMenuTreeAll` ∩ 目标厂有效许可；不读 `platform_admin` 的角色菜单当厂内菜单
- `/platform/**` 仍 `@PreAuthorize("@ss.isPlatformOperator()")` + `PlatformAccess.assertPlatformOperator()`（认 `tenantId==0`，不是只认角色名）
- 增量 SQL：克隆租户 1 部门树与岗位到租户 0（新 id、重写 `ancestors`）；`platform` 用户挂到对应研发部门；给 `platform_admin@tenant_id=0` 补 `system`、`monitor`（含 job）、`platform` 菜单（保留已有 9000/9001 与已赋 AI 行）
- 夹具测试覆盖回家 vs runAs 分叉

Out of scope:

- 改 Vue2 / Vue3 页面与路由契约；`GET /getRouters` 信封不变
- 重开 F3（平台模块永不许可给工厂；租户管理只挂 Vue3 PC）
- 改 runAs HTTP、DS 路由、揭明文、许可写接口
- 给租户 0 赋 MES 业务模块（`mes/md`、`mes/wm`、`mes/pro`、`mes/qc`、`mes/dv`、`cal`、`tm` 等）
- 改 `DataScopeAspect` 对平台运营跳过部门过滤的现行为（租户谓词仍在）
- 改 `ry_*.sql` / `20260821_09` / `10` / `12` / `26` / `34`
- 克隆 `sys_menu` 行；把部门种子打进专库开通 catalog
- 跨租户报表（D5）

### Acceptance Criteria

- 平台回家：角色仅绑 `platform`（9000/9001）时，`selectMenuTreeByUserId` **不**调用 `selectMenuTreeAll`；树无 `system`、无 `mes/md`
- 平台回家：`getMenuPermission` 不含 `*:*:*`；含已赋菜单的 `perms`（如 `system:user:list` 仅当角色勾了该按钮）
- 平台回家：`getRolePermission` 含 `platform_admin`，不含因短路注入的 `admin`
- runAs 到租户 1：仍调用 `selectMenuTreeAll`，结果按该厂许可过滤；不依赖 `platform_admin` 的 `sys_role_menu`
- 工厂会话行为与 39 一致（许可裁剪、无 `platform`、无工厂自助 `job`）
- 增量 SQL 幂等：租户 0 在岗部门已达完整树（`COUNT(*)>=10`）则不再插第二棵树；`ancestors` 不含租户 1 的 `100`–`109`
- `platform`（`tenant_id=0`）的 `dept_id` 指向本树「研发部门」节点
- 岗位 `ceo/se/hr/user` 在 `tenant_id=0` 各有一行（`uk_tenant_post_code` 不冲突）
- `platform_admin@tenant_id=0` 的 `sys_role_menu` 覆盖 `system` 子树、`monitor` 子树（含 job）、`platform` 子树；**不**新增 `mes/*` / `cal` / `tm` 业务目录
- 已有 AI 菜单授权不删除
- 文档无凭据、无生产主机；不改接口 URL / `code/msg/data`

### Rules and Constraints

Tenant isolation:

- SQL 永不跳过 `tenant_id`（含 `user_id=1`）
- 部门 `ancestors` 不得跨租户；禁止 `parent_id` 指向另一租户的 `dept_id`
- 身份表写入带当前上下文 `tenant_id`；平台回家只看见 `tenant_id=0`
- 登录后只信 JWT/`LoginUser`，忽略客户端租户头
- 平台强制 `ROW`；本单元不切 DS

Security and masking:

- 不引入第二套认证
- `/platform/**` 身份门禁保留；工厂 403
- 不发 `*:*:*` 给平台回家会话
- 日志不打印 token / 口令 / JDBC
- 菜单管理仍改全局 `sys_menu`；工厂不得获 `system:menu:add` 给自己加平台模块（F3 第二道闸不变）

Audit and lineage:

- 增量 SQL 接 `backend/sql/` 最大 `NN`（当前 34 → `20260827_35_platform_dept_post_role_menu.sql`）
- 不原地改 09/10/12/26/34 / `ry_*.sql`
- 回滚注释只删本脚本插入的租户 0 部门/岗位/本脚本新增的 `sys_role_menu` 行，不删 26 的 9000/9001、不删 AI 授权

AI/rule-engine rules:

- 不改 `/ai/**` 契约。已赋给 `platform_admin` 的 AI 菜单行保留；本单元不新插 AI 菜单

Database rules:

- `dept_id` / `post_id` 全局自增主键：克隆必须新行
- `sys_post` 唯一 `(tenant_id, post_code)`；租户 0 可与租户 1 同码
- `sys_role_menu.tenant_id=0` 与角色 `tenant_id` 一致
- 不把本种子打进 `TenantDedicatedSchema` / 专库开通 catalog

### Persistence Changes

新文件 `20260827_35_platform_dept_post_role_menu.sql`（名称若目录已有 35 则顺延 `NN`）：

1. **部门树（S7）。** 若租户 0 在岗部门 `COUNT(*)>=10`（完整 10 节点树）则整段跳过。否则过程内 `START TRANSACTION` 插入 10 行后 `COMMIT`（失败 `ROLLBACK`，避免半棵树导致永久跳过）。按租户 1 种子结构插入 10 行（名称与 `ry_20210908.sql` 100–109 相同：若依科技 / 深圳总公司 / 长沙分公司 / 研发部门 / …），`tenant_id=0`，`dept_id` 自增。插入顺序保证父先于子；每层用变量记下新 id，子行 `parent_id` 与 `ancestors` 只用新 id（根 `parent_id=0`、`ancestors='0'`；深圳 `ancestors='0,{根id}'`；研发 `ancestors='0,{根id},{深圳id}'`）。**禁止** `INSERT ... SELECT` 原 100–109 的 `dept_id`/`parent_id`/`ancestors`。
2. **挂用户。** `UPDATE sys_user SET dept_id=<新研发id> WHERE user_name='platform' AND tenant_id=0 AND (dept_id IS NULL OR dept_id NOT IN (SELECT dept_id FROM sys_dept WHERE tenant_id=0))`。不要改租户 1 的 `admin`。
3. **岗位。** 对 `ceo/se/hr/user` 四码 `INSERT ... WHERE NOT EXISTS (tenant_id=0 AND post_code=?)`；`post_id` 自增。
4. **角色菜单。** 对 `role_key='platform_admin' AND tenant_id=0`，插入满足下列之一且尚未绑定的 `sys_menu.menu_id`（`sys_role_menu.tenant_id=0`）。本仓 `sys_menu` **无** `ancestors` 列（`ry_20210908.sql` 该列只在 `sys_dept`），用 `parent_id` 子树 walk + `CROSS JOIN`（MySQL 8 禁止无 `ON` 的 `INNER JOIN`）；**禁止** `FIND_IN_SET` on `sys_menu.ancestors`：
   - `menu_id IN (1, 2)`，或 `parent_id` 为 1/2，或其下最多三层子节点（系统管理 / 系统监控整树，**含 job**）
   - `menu_id IN (9000, 9001)` 或 `parent_id IN (9000, 9001)`（与 26 幂等重叠则 `NOT EXISTS` 跳过）
   - **不**按 `mes/`、`cal`、`tm` 顶级 path 插入新行
   - **不** `DELETE` 已有 AI（9100 段等）授权
5. 不含明文口令、不含生产主机 / JDBC。回滚注释只覆盖本脚本新插入的部门/岗位/本脚本新增 role_menu。

### Transaction Boundaries

- 种子 SQL 按脚本顺序执行；部门树 10 行插入在过程内同一事务；挂用户在 CALL 成功之后
- 菜单/权限读取只读，无新写事务
- 不把种子打进专库开通事务

### Risks

- 先改代码后补种子 → 平台登录侧栏只剩租户管理，用户/部门页 403
- runAs 误改成角色菜单 → 进厂看不到该厂 MES
- 克隆部门时复制 `dept_id` 100–109 → 主键冲突或跨租户 `ancestors`
- 10 号脚本曾把关系表 `tenant_id` 回填为 1：本脚本写 `sys_role_menu.tenant_id=0`，与 26/34 一致
- 去掉 `*:*:*` 后未赋按钮权限字 → 有菜单点不开；种子必须含子按钮（随 system/monitor 子树一起绑）
- `getRolePermission` 不再注入 `admin` 后，若仍有 `@ss.hasRole('admin')` 的平台接口会 403 → 本单元不得把平台接口改回 `hasRole('admin')`；保持 `isPlatformOperator`
