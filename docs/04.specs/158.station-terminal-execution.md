# 触屏工位机 — 开工到结束

本文件可实施。页面落在 spec 157 的工位入口内。业务只打现有工单与工位接口。本单元不改这些接口的契约。

## 1. Spec

### Capability

- Name: 工位入口内的工单执行
- Module: `kuaigeyun-mes/riveredge-frontend` 工位入口。写入走现有 `riveredge-backend` 工单接口与 `StationService`。
- Priority: STN-D7、STN-D9、STN-D10、STN-Q1。依赖 157。
- Related requirement/design documents:
  - 缺口：`docs/02.requirements/20.station-terminal-gaps.md`（**STN-D7**、**STN-D9**、**STN-D10**、**STN-Q1**）
  - 设计：`docs/03.design/20.station-terminal-plan.md`（§2、§3）
  - 入口：`docs/04.specs/157.station-terminal-entry.md`

### Business Goal

操作员在工位入口里看待产工单，对工序开工、撤回开工、暂停、恢复、结束，并做设备上机、下机。SOP 确认与上岗资质默认不挡开工；现场打开页面开关后，页面先查现有检查接口，通过后再放行。

### Scope

In scope:

- 工单列表沿用现有工单查询，在 157 入口内用触屏列表展示。
- 开工：`POST /api/v1/apps/kuaizhizao/work-orders/{work_order_id}/operations/{operation_id}/start`。
- 撤回开工：`POST /api/v1/apps/kuaizhizao/work-orders/{work_order_id}/operations/{operation_id}/withdraw-start`。现有规则：工序已开工且尚无报工。
- 暂停：`POST .../pause`，请求体为现有 `OperationPauseRequest`。原因码沿用 `StationService` 的 `DOWNTIME_REASON_LABELS`：`material_shortage` 缺料、`material_wait` 待料、`equipment_fault` 设备故障、`tool_change` 换刀/换模、`quality_issue` 质量异常、`break` 休息、`other` 其他。暂停请求带上入口已绑定的 `workstation_id`。
- 恢复：`POST .../resume`。
- 结束：`POST .../complete`。数量报工须合格数达到计划；状态报工按目标数量记合格。暂停中可以直接结束，现有实现会关闭未结束的停机。页面展示接口返回的结果与错误，不在页面里另写一套数量判断。
- 设备上下机：`POST .../machine-session`，`action` 为 `on` 或 `off`。
- SOP 确认与上岗资质是页面开关，默认关闭，关闭时开工请求直接发出。
- 开关打开时，开工前先调用现有检查，通过后再调用开工接口：
  - SOP：先 `GET /api/v1/apps/kuaizhizao/station/work-orders/{work_order_id}/operations/{operation_id}/documents`。该响应没有 `sop.uuid` 时，不调用 `sop-acknowledgments/check`，也不 `POST` 确认，直接开工。有 `sop.uuid` 时，用该响应的 `sop.uuid` 与 `current_revision` 调用 `GET /api/v1/apps/kuaizhizao/station/sop-acknowledgments/check`。未确认时页面可调用 `POST /api/v1/apps/kuaizhizao/station/sop-acknowledgments`（工单 + 工序 + 修订号 + 操作员）。不改用工单 documents 接口，也不用工序列表上的 `sop_uuid`。换版后的重新确认以该检查结果为准。
  - 上岗资质：`POST /api/v1/apps/kuaizhizao/station/skill-check`。`qualified` 为真才放行。组织没有任何资质记录时，现有实现返回放行及说明「组织尚未配置上岗资质，默认放行」。页面尊重该结果，照常放行开工。
- 上述检查留在页面。开工、撤回、暂停、恢复、结束接口保持现有契约。

Out of scope:

- 新的开工、暂停、资质或 SOP 接口；把 SOP 确认或资质检查嵌进开工 API
- 资质维护页面（`POST/GET /station/operator-skills` 不在本单元）
- 快捷报工、上料、下料、报废（159）、安灯（160）、刷脸与交接班（161）
- 标签工位、电视看板、小程序、企业微信、移动端复制页面
- 新后端表；改 `startech-mes-basic`；把页面烤进 exe

### Acceptance Criteria

1. 入口内可以列出工单，并对工序执行开工、撤回开工、暂停、恢复、结束、设备上机与下机，调用的都是上列现有 URL。
2. 两个页面开关默认关闭。关闭时，开工请求前没有 SOP 检查，也没有资质检查。
3. 打开 SOP 开关后，工序文档没有 `sop.uuid` 时页面不调用确认检查或确认写入，直接开工。有 `sop.uuid` 时，检查未通过则不调用开工；确认成功或检查已通过后才调用开工。`sop.uuid` 与 `current_revision` 只取工位文档接口。
4. 打开资质开关后，`qualified` 为假时页面不调用开工。组织无资质记录、接口返回放行时，页面调用开工。
5. 开工接口的实现仍不调用 SOP 确认或资质检查。本单元没有新表、新迁移。

### Rules and Constraints

Tenant isolation:

- 列表与工序动作沿用现有租户隔离。终端账号会话决定租户。

Security and masking:

- 沿用现有登录与工单、工位模块权限。页面不输出令牌。
- 部署前提：终端角色除 `production-execution-terminal` 外须授 `kuaizhizao:work-order:read`（工单列表与工序选择）。

Audit and lineage:

- 停机、开工时间沿用现有工序与停机记录。页面不另建执行日志表。

AI/rule-engine rules:

- 不涉及。

Database rules:

- 无新表，无迁移。页面开关不写入新的后端配置项，默认关闭。

## 2. Plan

### Implementation Approach

1. 在 157 入口内做工单列表和工序动作，按钮调用上列现有接口。
2. 暂停原因用现有七个原因码。结束与撤回的失败提示直接用接口错误。
3. 页面上放两个默认关闭的开关。打开时先检查再开工。关闭时开工路径不经过这两个接口。

### 依赖

- 依赖 157 的在线入口、已绑定工位、当前操作员。
- 与 159、160、161 可先后实现。端到端冒烟在 162，那时入口须已能被壳打开。

### Affected Modules

- 157 的工位入口页（工单列表与工序动作放在该入口内）
- 只调用：`riveredge-backend` 已有工单工序路由与 `api/station/station.py` 的 SOP、资质检查
- 不改 `station_service.py` 的开工链路，不改 `start_work_order_operation`

### Public Contracts

- 工序动作 URL 与请求体保持现有契约：`start`、`withdraw-start`、`pause`、`resume`、`complete`、`machine-session`（`action` 为 `on` / `off`）。
- 检查 URL 保持现有契约：`GET /station/sop-acknowledgments/check`、`POST /station/sop-acknowledgments`、`POST /station/skill-check`。
- SOP 的 `sop.uuid` 与 `current_revision` 只取 `GET /station/work-orders/{work_order_id}/operations/{operation_id}/documents`。该响应没有 `sop.uuid` 时，不调用上述确认检查与确认写入，直接开工。
- 应用前缀为现有 `/api/v1/apps/kuaizhizao`。

### Persistence Changes

- 无。

### Transaction Boundaries

- 每次按钮对应现有接口自己的事务。页面不把检查与开工并成一个新事务。

### Risks

- 在开工服务里调用 SOP 或资质，会改变 **STN-D9** 已拍板的契约。
- 页面在开关关闭时仍先请求检查，会把默认不挡开工做成事实卡控。
- 组织无资质记录时页面若忽略 `qualified=true`，产线会被空库挡住。

### Verification Strategy

- 见 §3。§4 在命令实跑后填写。本文件写下时未跑测试或构建。

Behavior delivered:

- `index.ts` 导出 `StationExecutionPage`。157 传入 `workstationId` 与 `operator`。
- 工单列表打现有 `GET /api/v1/apps/kuaizhizao/work-orders`，分别带 `status=released` 与 `status=in_progress`（列表筛选是单值相等）。点选后打 `GET .../work-orders/{id}/operations`。
- 开工、撤回开工走现有 `workOrderApi.startOperation` / `withdrawOperationStart`。暂停、恢复、结束、上下机走对应 POST。暂停体为 `reason_code`，有工位 ID 时再带 `workstation_id`。上下机体只有 `action`：`on` 或 `off`。结束失败展示接口错误。
- SOP 确认、上岗资质两个开关默认关闭，且不写入后端。关闭时开工前不请求这两项检查。
- 资质开关打开时先 `POST /station/skill-check`。`qualified` 为真（含「组织尚未配置上岗资质，默认放行」）才开工，并显示接口 `message`。
- SOP 开关打开时先读工位文档 `GET /api/v1/apps/kuaizhizao/station/work-orders/{id}/operations/{operation_id}/documents`。没有 `sop.uuid` 时不调用 `sop-acknowledgments/check`，也不 POST 确认，直接开工。有 `sop.uuid` 时用该响应的 `sop.uuid` 与 `current_revision` 做 check / acknowledge，通过后才开工。
