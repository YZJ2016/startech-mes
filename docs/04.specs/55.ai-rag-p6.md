## 1. Spec

### Capability

- Name: P6 对话挂载本租户知识库
- Module: `ktg-ai` chat + retrieval；`startech-mes-front` 对话页可选知识库
- Priority: P6
- Related requirement/design documents:
  - 设计：`docs/03.design/06.mes-ai-platform-plan.md` §6–§8
  - 缺口：`docs/02.requirements/03.mes-ai-platform-gaps.md`（A5、A24、I-A3）
  - 总控：`docs/04.specs/48.mes-ai-platform-program.md`
  - 上一单元：`docs/04.specs/54.ai-vector-oss-p5.md`
  - 下一单元：`docs/04.specs/56.ai-dashvector-p7.md`
  - ChatModel 工厂：`docs/04.specs/61.ai-chatmodel-factory.md`

### Business Goal

发消息时可带本租户 `knowledgeId`：检索片段写入提示词再流式生成。无 knowledgeId 时行为与 51 相同。

### Scope

In scope:

- `POST /ai/chat/send` 增加可选 `knowledgeId`
- 检索强制当前 `tenantId` + 该 knowledge 所有权
- 提示词拼装：系统或用户前缀含检索片段；片段条数/上限在实现写死小默认（如 topK=5），不做复杂 rerank
- 对话页下拉本租户知识库

Out of scope:

- 百炼托管知识库
- rerank 产品化
- Agent 选库
- DashVector（56 只换存储，本单元契约不变）

### Acceptance Criteria

- 他租户 `knowledgeId` → 失败，不检索、不调上游
- 检索空结果仍可纯对话（或明确提示「无命中」；实现选一种并写进第 4 节）
- 提示词与日志不含模型 key
- 前端不引入新 UI 套件

### Rules and Constraints

Tenant isolation:

- 检索入口只接受 `TenantContext` + 校验过的 kid
- 禁止客户端传 `tenantId`

Security and masking:

- 片段只来自本租户向量命中 + fragment 表回表（回表也带 tenant_id）

Audit and lineage:

- 可选在 message 记 `knowledge_id`

AI/rule-engine rules:

- 不做自动 SQL

Database rules:

- 不改向量 schema 语义

## 2. Plan

### Implementation Approach

- ChatService 在调上游前：若有 kid → search → 拼 context → 51 的流式路径
- 回表 fragment 防向量库只存 id
- 流式出站仍按 A24 取 `(tenantId, modelId)` 对应凭证，不改用全局模型

### Affected Modules

- `ktg-ai` chat service、front chat 页

### Public Contracts

- `/ai/chat/send` 增补可选 `knowledgeId`（兼容 51 客户端）
- `/ai/knowledge/options` 供下拉

### Persistence Changes

- `ai_message` 可空 `knowledge_id`（若 51 未留列则本单元 ALTER）

### Transaction Boundaries

- 检索只读；不与用户消息同一事务强绑

### Risks

- 把向量命中 text 当权威却未回表，串到错误 kid
- topK 过大撑爆上下文

### Verification Strategy

- 单测：错租户 kid 不调 VectorStore
- 有前端改动则 `build:prod`
