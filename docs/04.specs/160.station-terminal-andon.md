# 触屏工位机 — 四类安灯

本文件可实施。只做前端页面，调用现有 `/api/v1/apps/kuaizhizao/station/andon`。不改安灯状态机。

## 1. Spec

### Capability

- Name: 工位四类安灯
- Module: `kuaigeyun-mes/riveredge-frontend` 工位入口内的安灯页。后端为现有 `api/station/station.py` 与 `StationService`。
- Priority: STN-Q1。依赖 157。
- Related requirement/design documents:
  - 缺口：`docs/02.requirements/20.station-terminal-gaps.md`（**STN-Q1**，以及「后端已有」安灯行）
  - 设计：`docs/03.design/20.station-terminal-plan.md`（§3）
  - 入口：`docs/04.specs/157.station-terminal-entry.md`

### Business Goal

操作员在工位上发起质量、物料、设备、班长四类安灯，并按现有状态机响应、关闭或撤销。联动仍由现有服务完成。

### Scope

In scope:

- 页面调用现有接口，前缀 `/api/v1/apps/kuaizhizao/station`，权限模块 `production-execution-terminal`：
  - `POST /andon` 发起
  - `GET /andon`、`GET /andon/open` 列表
  - `POST /andon/{andon_id}/acknowledge` 响应
  - `POST /andon/{andon_id}/close` 关闭
  - `POST /andon/{andon_id}/cancel` 撤销
- `call_type` 为 `quality`、`material`、`equipment`、`supervisor`。请求带上 157 已绑定的 `workstation_id`。
- 发起时页面按现有服务的必填项收齐字段：
  - 质量：关联工单与工序。现有联动创建过程检验。
  - 物料：必须带工单，`material_call_mode` 为 `FULL_ORDER`。现有联动只做齐套叫料。
  - 设备：必须带 `equipment_uuid`，故障级别由操作员选择：轻微、一般、严重、紧急。现有联动创建故障单。
  - 班长：必须带 `supervisor_user_id`。现有联动发站内消息。
- 状态沿用现有实现：发起为 `open`，响应后为 `acknowledged`，关闭后为 `closed`。`open` 与 `acknowledged` 可以关闭。撤销只对发起人、且只在 `open`（未响应）时提交；现有实现把撤销记为 `closed` 并在备注附上撤销标记。页面在条件不符时不发撤销请求。

Out of scope:

- 新的安灯类型、新的状态、新的联动服务
- 改过程检验、叫料、故障单、站内消息的实现
- 标签工位、电视看板、小程序、企业微信、移动端复制页面
- 新后端表；开工 API 内嵌 SOP 或资质；改 `startech-mes-basic`；把页面烤进 exe

### Acceptance Criteria

1. 工位入口可以发起四类安灯。质量须带工单与工序，物料须带工单且 `material_call_mode` 为 `FULL_ORDER`，设备须带设备与级别，班长须指定通知人。缺这些字段时页面不提交。
2. 列表可以响应、关闭。未响应的记录可以由发起人撤销。其他用户或已响应的记录，页面不调用撤销。
3. 质量、物料、设备、班长的后续单据仍由现有 `StationService` 联动生成。本单元没有新的安灯 URL。
4. 安灯请求使用终端账号的现有登录会话。

### Rules and Constraints

Tenant isolation:

- 安灯查询与写入沿用现有租户隔离。

Security and masking:

- 沿用 `production-execution-terminal`。页面不输出令牌或站内消息以外的内部路径。

Audit and lineage:

- 安灯行、关联单据类型与单号沿用现有字段（`related_doc_type`、`related_doc_uuid`、`related_doc_code`）。

AI/rule-engine rules:

- 不涉及。

Database rules:

- 无新表，无迁移。

## 2. Plan

### Implementation Approach

1. 在 157 入口内增加安灯触屏页，四类表单各自收集上列必填项。页从 `station/andon` 导出 `StationAndonPage`。工位与当前操作员由入口 props 传入，页面不读 URL。
2. `GET /andon/open` 在服务里只返回 `status=open`，页面把该列表标成未响应。`GET /andon` 展示该工位最近记录，已响应的行在这里关闭。动作成功后按接口响应再刷新列表。
3. 撤销按钮只出现在当前登录用户等于 `caller_id` 且状态为 `open` 的行上。

已拍板：

- 质量安灯的 `operation_id` 送工单工序行 `id`（开工路径用的那个 ID），不送主数据工序模板 ID。
- 班长通知人用 `GET /api/v1/core/users/display-search`（前端 `searchUserDisplay` 打 `/core/users/display-search`）。不用 `GET /api/v1/core/users`。
- `StationAndonPage` 的 props 为 `workstationId`、`workstationName`、`operatorId`、`operatorName`。缺工位时只提示「等待工位入口传入当前工位」。

### 依赖

- 依赖 157 的入口与已绑定工位。当前操作员用于展示；撤销判定用的是登录用户，与现有 `cancel_andon` 的 `caller_id` 一致。
- 与 158、159、161 可先后实现。端到端冒烟在 162。

### Affected Modules

- 157 工位入口内的新安灯页
- 只调用 `riveredge-backend/src/apps/kuaizhizao/api/station/station.py` 已有安灯路由
- 不改 `StationService.create_andon_call` 及四类联动

### Public Contracts

- 上列 `/station/andon` 路由与 `StationAndonCreate` 字段保持现有契约。请求体不带 `caller_id`。
- `call_type`：`quality` / `material` / `equipment` / `supervisor`。
- 质量 `operation_id` 为工单工序行 `id`。物料 `material_call_mode` 固定 `FULL_ORDER`。设备 `fault_level` 为 `轻微` / `一般` / `严重` / `紧急`。班长 `supervisor_user_id` 来自人员展示搜索的 `id`。
- 状态：`open` → `acknowledged` → `closed`。撤销仅 `open` 且仅发起人。
- 页面 props：`workstationId`、`workstationName`、`operatorId`、`operatorName`。后三者可缺。`operatorId` / `operatorName` 只展示。

### Persistence Changes

- 无。

### Transaction Boundaries

- 发起、响应、关闭、撤销各沿用 `StationService` 现有事务。页面一次按钮一次请求。

### Risks

- 页面若允许物料使用 `FULL_ORDER` 以外的模式，会被现有服务拒绝。
- 设备级别若由页面留空，现有服务会把级别落成「一般」。页面仍要求操作员选出四级之一再提交。
- 在前端再写一套状态机并提前改状态，会和列表刷新结果不一致。按钮成功后再按接口响应更新。
