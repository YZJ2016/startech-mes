## 1. Spec

### Capability

- Name: Flyway 地基（starter、目录命名、tenant 快照、主库自动 migrate）
- Module: `startech-mes-basic/backend/ktg-system`（依赖 + `db/migration` + 命名/快照单测）；`ktg-framework`（`DruidConfig.masterDataSource` 标 `@FlywayDataSource`）；`ktg-admin`（`application*.yml` 的 `spring.flyway.*`，启动路径）
- Priority: P0
- Related requirement/design documents:
  - 设计：`docs/03.design/05.mes-flyway-integration.md`（§3 命名、§4.1–4.2 基线、§5 主库组件与 Boot 4.1 starter）
  - 缺口：`docs/02.requirements/02.mes-multi-tenant-gaps.md`（I10）
  - 总控：`docs/04.specs/75.mes-flyway-program.md`
  - 上一单元：`docs/04.specs/75.mes-flyway-program.md`
  - 下一单元：`docs/04.specs/77.mes-flyway-dedicated-provision.md`

### Business Goal

让主库在启动时按 Flyway 自动 migrate（失败拒启动），并落下可给空专库建表的 tenant 快照。开通路径本单元仍走既有 `TenantWarehouseSql`；不在本单元补齐已 READY 专库、不改登录。

### Scope

In scope:

- 按 75 的基线规则钉死版本号（撰写时候选 `20260825.31`；开工核对 `incrementalSqlFiles()` 最后一项与 `sql/` 后续文件分类后写入本文件第 4 节）
- `ktg-system/pom.xml` 增加 `spring-boot-starter-flyway` + `flyway-mysql`（不写 version，不单独声明 `flyway-core`）
- 目录：`ktg-system/src/main/resources/db/migration/master/`、`.../tenant/`。禁止在 `ktg-admin` 再拷一份
- 命名单测：两目录 `VyyyyMMdd.nn` 无重复；slug 前缀与目录一致（`__master_` / `__tenant_`）
- tenant 快照：`V{基线}__tenant_schema_snapshot.sql`。对 `TenantDedicatedSchema.tenantTables()` 做 `CREATE TABLE`（无 `DROP`、无口令、无 `DELIMITER`、无 `CREATE TABLE IF NOT EXISTS` 当现网可重跑的替代）。结构对齐切线当日（含 `tenant_id` 与复合 UNIQUE，含 `AI_TABLES`）
- 快照不得 `CREATE`/`ALTER` I8 全局表（`GLOBAL_TABLES`、`QRTZ_*`、`sys_dict_*`、`gen_*`）
- `master/` 切线日可以没有 versioned 文件
- `DruidConfig.masterDataSource` 增加 `@FlywayDataSource`；不要绑 `@Primary` 的 `dynamicDataSource`
- yml：`spring.flyway.enabled=true`；`baseline-on-migrate=false`；`validate-on-migrate=true`；`locations` 为 master + tenant；不设 `outOfOrder`
- 无 `flyway_schema_history` 且已有业务表的库：启动应失败（fail-closed）。已 baseline 的库：启动只写基线行，不重放 `ry_*`

Out of scope:

- 替换 `TenantSchemaProvisioner` / 删除 `TenantWarehouseSql`（77）
- READY 专库启动补齐、登录版本比较（78）
- 把历史 `sql/` 改写成多版 Flyway 链；菜单种子 / xinhe dump 进 `db/migration`
- 改 Vue；改登录 HTTP；扩大匿名面
- 默认打开 `baselineOnMigrate`
- 在 77 完成前往 `tenant/` 追加快照之后的新版本（75 交付窗口）

### Acceptance Criteria

- `mvn -pl ktg-system,ktg-framework -am test` 含本单元新建测试（见第 4 节；撰写时 **未执行**）
- 命名扫描测试失败条件：同一 `yyyyMMdd.nn` 出现在两个目录，或 slug 前缀与目录不符
- 快照扫描：每个 `tenantTables()` 名出现一次 `CREATE TABLE`；无 I8 全局表；文件内无 JDBC 口令/生产主机
- 多 DataSource 下 Flyway 使用 master 池（测试或配置证据：`@FlywayDataSource` 在 `masterDataSource` 上）
- 未 baseline 的「已有表」夹具启动失败；baseline 到切线版本后启动不执行快照 SQL
- 不改 `POST /login` / `/platform/tenant/{id}/schema` 契约
- 仓库无真实 JDBC 凭据新增

### Rules and Constraints

Tenant isolation:

- 主库 locations 含 tenant，因此主库也会应用快照（仅当 history 中无该版本）。已有主库必须先 baseline，否则 `CREATE` 撞表
- ROW/平台无独立 schema，不循环租户

Security and masking:

- 快照与 yml 不得含口令、真实主机
- 不把 `TENANT_JDBC_CIPHER_KEY` 写入 yml

Audit and lineage:

- `backend/sql/` 本单元不追加发布 DDL、不原地改历史文件
- 快照一经合并视为冻结

AI/rule-engine rules:

- 快照必须包含 `AI_TABLES` 当前列，与 `incrementalSqlFiles()` 末段对齐

Database rules:

- Boot 4.1：starter 提供自动配置；MySQL 必须有 `flyway-mysql`
- Flyway 版本比较只认 `V` 与 `__` 之间的号；目录不去重

## 2. Plan

### Implementation Approach

1. 核对 `incrementalSqlFiles()` 最后一项与 `sql/` 更大号文件；钉基线；写入本文件第 4 节。
2. `ktg-system` 加 starter + `flyway-mysql`。
3. 先写命名/快照扫描失败测试，再加目录与快照文件。
4. 从现行 `TenantWarehouseSql.dedicatedCreates()` 所能表达的结构生成无 `DROP` 的快照（可手工整理，禁止把 `DELIMITER` 增量原样拷入）。缺表不得 silently `IF NOT EXISTS`。
5. `masterDataSource` 标 `@FlywayDataSource`；yml 配 locations 与 FLY8 开关。
6. 用 H2 或 Testcontainers（交付时写明）覆盖：无 history 已有表 → 失败；baseline 后 → 不跑快照。

### Affected Modules

- `ktg-system/pom.xml`
- `ktg-system/src/main/resources/db/migration/master/`（可空占位 `.gitkeep` 或无文件）
- `ktg-system/src/main/resources/db/migration/tenant/V{基线}__tenant_schema_snapshot.sql`
- `ktg-system` 测试：如 `com.ktg.system.tenant.FlywayMigrationNamingTest`、`FlywayTenantSnapshotTest`
- `ktg-framework/.../DruidConfig.java`：`masterDataSource` 的 `@FlywayDataSource`
- `ktg-admin/src/main/resources/application.yml`（及现有 profile yml 若覆盖 datasource）：`spring.flyway`

### Public Contracts

- 无新 HTTP
- 启动失败方式：进程起不来（主库 migrate 失败），不是改登录文案

### Persistence Changes

- 主库新增 `flyway_schema_history`（运维 baseline 或首次空库 migrate）
- tenant 快照 `CREATE` 全套 `tenantTables()`；`master/` 切线日无 DDL

### Transaction Boundaries

- Flyway 自身管理每条 versioned migration；MySQL DDL 隐式提交。失败即停在该版本，进程退出

### Risks

- 基线钉错：已有库缺 AI 表或启动撞 `CREATE`
- 快照用 `IF NOT EXISTS` 掩盖缺列
- 漏 `@FlywayDataSource` 导致启动失败或误用路由源
- 实验室未 baseline 就拉 76 的代码 → 无法启动（预期，须手册）

### Verification Strategy

- 单测扫文件；模块 `mvn test`
- 启动夹具：无 history / 已 baseline
- 不连现网；第 4 节写明是否跳过 Testcontainers
