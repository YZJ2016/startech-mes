Use this template before each implementation unit.

## 1. Spec

### Capability

- Name: Vue3 管理端与换壳后后端 API 对齐（总控）
- Module: `startech-mes-basic/startech-mes-front` + 只读对照 `startech-mes-basic/backend`；默认不改 Java
- Priority: P0
- Related requirement/design documents:
  - 缺口清单：`docs/02.requirements/01.vue3-backend-api-gaps.md`
  - 调研：`docs/03.design/03.vue3-backend-api-align-survey.md`
  - 第一开发单元：`docs/04.specs/28.vue3-platform-api-align.md`
  - 后端换壳（只读背景）：`docs/04.specs/11.backend-shell-swap-program.md`、`19.backend-shell-swap-phase2-program.md`、`23.phase2-rewire-security-and-five-gates.md`
  - 历史 Vue3 迁移（不再当契约）：`docs/superpowers/specs/2026-08-21-mes-vue3-front-upgrade.md`

### Business Goal

避免 Vue3 壳按 3.8.2 假设调用不存在的接口、或关掉后端换壳后已经提供的平台能力，导致登录后锁屏、改密、公告铃铛、上传异常。平台 HTTP 跟换壳后的若依；MES 定制继续走 mes 五项接线。第一刀完成缺口清单和平台冒烟；MES 领域 API 后续按目录拆单元。

本文件约束原则、文档落点、单元顺序和完成定义，不写业务代码。

### Scope

In scope:

- 规定原则 C：层 1 平台 / 层 2 MES 定制 / 层 3 禁止覆盖
- 规定验收 B：静态 URL+method 清单 + 平台冒烟（有环境才勾）
- 规定缺口分类 `P` `M` `D` `X` `K` 与清单文件
- 规定第一单元为 `28`（平台壳）；领域 `D-*` 在 `28` 之后拆 spec
- 规定 git 边界：文档在外层；代码在 nested `startech-mes-basic`

Out of scope:

- 在本总控内改 Vue3 或 Java（实现属于 `28` 及后续领域单元）
- 改 Vue2 `frontend/`
- 改 MES 业务 URL、工单/库存状态机、历史 SQL 原地文件
- 在 admin 挂 `listTop`/`markRead` 或把 `GET /system/notice/list` 从 mes 移走
- 用 OSS 默认上传替换 MinIO
- 模块改名 `ruoyi-*`、包名改 `com.ruoyi`
- 把历史 `docs/superpowers/specs/` 当成现行契约去改后端

### Acceptance Criteria

- `01` 缺口清单存在且含 `P`/`M`/`D`/`X`/`K`；开放项为 `[ ]`
- `03` 调研与本文件原则一致
- `28` 使用本模板章节，且 In scope 仅平台壳 + 清单中的 `P`/`X1`
- 领域单元未创建前，`D-*` 允许以目录占位存在于清单，不得当成 `28` 未完成
- 文档、补丁、日志不出现真实密码、Token、生产地址、数据库连接串

### Rules and Constraints

Tenant isolation:

- 不引入租户字段，不改变现有数据隔离方式

Security and masking:

- 不在 spec、补丁、日志中复述 Token、Minio/OSS 密钥、数据库口令或内网地址
- 新增配置只用环境变量或占位符
- 不得扩大匿名访问面
- 锁屏解锁走 `POST /unlockscreen`；与 `GET /monitor/logininfor/unlock/{userName}` 分开

Audit and lineage:

- 不改历史 SQL 文件
- 对齐是接契约，不是借机改 MES 状态机
- Vue3 历史 spec 保留为历史，不在本轨道重写后端假设

AI/rule-engine rules:

- 本批不涉及规则引擎或 AI

Database rules:

- 不改表结构；不把若依公告已读表接到 mes 的 `userId1`/`readStatus`

## 2. Plan

### Implementation Approach

1. 写并维持缺口清单与调研（本批文档）
2. 执行 `28`：只改 `startech-mes-front` 平台壳；静态清单回填 `P8` 与 `D-*` 的具体 URL
3. `28` 收口后再按 md/pro/wm/qc/cal-dv/rest 拆领域 spec，每份链到清单 `D-*`

默认不改后端。若 `P8` 发现层 1 HTTP 与 3.9 壳不一致且必须改 Java，停在清单里单列，不在 `28` 擅自改五项接线。

### Affected Modules

- 文档：外层 `docs/02.requirements/`、`docs/03.design/`、`docs/04.specs/27`–`28`
- 实现（`28`）：`startech-mes-basic/startech-mes-front`
- 只读对照：`startech-mes-basic/backend`
- 禁止：`startech-mes-basic/frontend/`

### Public Contracts

- 层 1：`POST /login`、`GET /getInfo`（含密码字段）、`GET /getRouters`、`GET /captchaImage`、`POST /unlockscreen`、`GET /system/user/deptTree`；`Authorization: Bearer`；`code/msg/data`；列表 `rows/total`
- 层 2：`GET /system/notice/list`（mes）、`GET /system/notice/detail/message`、`POST /system/notice/detail`、`POST /common/uploadMinio`、`GET /loginOuth`、`/system/autocode/**`、`/ureportM/**`
- 层 3：禁止 admin `GET /system/notice/list`；禁止 `listTop`/`markRead` HTTP 替代层 2

### Persistence Changes

- 无

### Transaction Boundaries

- 无

### Risks

- 打开初始/过期改密后，测试号可能被拦去个人中心；用可改密账号，不记录口令
- 铃铛改接 MES 后已读字段与 3.9 壳不同
- `pwdChrtype` vs session `pwrChrtype` 接错则密码规则不生效
- 静态 diff 误报 CRUD 详情路径
- 无本地后端时冒烟不完整

### Verification Strategy

总控本身只验收文档完整性。运行时与静态检索的命令证据写在 `28` 第 4 节。未跑通不得写通过。
