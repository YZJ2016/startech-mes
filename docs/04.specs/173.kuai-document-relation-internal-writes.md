## 1. Spec

### Capability

- Name: 内部单据关系的删除、更新和创建收口
- Module: `kuaigeyun-mes/riveredge-backend`：`document_relation_new_service` 与第 4 节列出的内部调用方
- Priority: P0（KR-PG4）
- Related requirement/design documents:
  - 缺口：`docs/02.requirements/22.kuai-production-grade-closeout-gaps.md`（**KR-PG4**）
  - 设计：`docs/03.design/22.kuai-production-grade-closeout-plan.md` 第 4 节
  - 入口：`docs/04.specs/144.kuai-document-relation-single-entry.md`

### Business Goal

需求、仓储、销售、财务、半成品、采购、发票合并上仍在直写的内部单据关系，改走 `create_relation`、`delete_relation`，或同一个 `DocumentRelationNewService` 上的编码/notes 更新。关系没写成或没删掉时，业务单据不能单独成功。

### Scope

In scope:

- 第 3 节任务表里的每一处内部直写。
- 在 `DocumentRelationNewService` 上增加两件更新：按单据刷新 source/target 编码快照；按关系主键写 `notes`。

Out of scope:

- 金蝶、飞书、OA 推送上的 `DocumentRelation.create` 不迁。含销售订单、采购订单、生产订单、库存、飞书工单、OA 单据推送。spec 144 已迁的报工推送不在本单元重做。
- 不使用 `batch_create_relations`（447–449 行逐条 warning 后继续）来迁移下列各处。
- 不新增「按单据一侧批量删」的平行入口。
- 不改 `create_relation` 四键已存在时抛「关联关系已存在」（158–159 行），不改 `delete_relation` 按主键找不到抛 `NotFoundError`、按业务键 0 行不抛（453–506 行）。幂等由调用方处理。
- 读关系（`filter` 后只查询）不迁。旧 `document_relation_service` 的追溯读不改。
- 不拆 `warehouse_service` / `work_order_service`。
- 不改 URL、method、认证头、响应外层结构。

### Acceptance Criteria

1. 任务表每一处不再调用 `DocumentRelation.get_or_create`、`DocumentRelation.create`、`DocumentRelation.filter(...).delete()`、`filter(...).update()` 或 `rel.save()` 写关系。读过滤可以继续用 `DocumentRelation.filter`。
2. 一侧全删：先按现有过滤查出命中行，再对每一行 `delete_relation(tenant_id, relation_id=行.id)`。查出 0 行是显式幂等成功。删除进行中该主键已不存在（`NotFoundError`）时，这一行显式幂等成功，不把整单打失败。其他删除失败按该行任务回滚。
3. 四键齐全的删除走 `delete_relation` 业务键。返回 0 是显式幂等成功。
4. 需求计算创建：关系已存在时计算继续；其他失败整单回滚。
5. 采购订单删除：关系删除失败则订单不得留下软删。该删除现网没有事务，收口后必须与软删同一事务。
6. 销售订单编码刷新只改 source 侧。非销售订单才同时刷新 source 与 target。销售订单不得再走进 `sync_document_code_snapshots` 219–228 行。刷新失败与新编号同一事务回滚。0 行显式幂等成功。
7. 发票合并修复：notes 已等于目标金额时显式幂等成功。缺关系时 `create_relation`；已存在则显式幂等成功后再把 notes 写成目标分摊。其他失败拒绝这一张发票的修复并上抛，不跳过。
8. 金蝶、飞书、OA 推送文件无本单元改动。`batch_create_relations` 仍保持逐条跳过，且不被本单元拿来当收口入口。

### Rules and Constraints

Tenant isolation:

- 更新与删除都带调用方已有的 `tenant_id`。不放宽组织条件。

Security and masking:

- 不在日志中新增凭据或内部路径。

Audit and lineage:

- 不删了再建。编码刷新与 notes 更新保持原主键，不丢 `notes`、`relation_desc`。

AI/rule-engine rules:

- 不涉及。

Database rules:

- 不新表。不改 `DocumentRelation` 字段。

## 2. Plan

### Implementation Approach

- 先在 `DocumentRelationNewService` 增加编码快照刷新与按主键写 notes。调用方不得再 `filter().update()` 或 `rel.save()`。
- 一侧全删保持「先查后按主键删」。四键齐全的删除直接用业务键。
- `create_relation` 抛出的「关联关系已存在」只在需求计算创建和发票修复这两处收成显式幂等成功。其他已有调用方仍按抛错处理。
- 调用方所在事务失败时，关系写入一起回滚。入口函数不吞异常。

### Affected Modules

- `src/apps/kuaizhizao/services/document_relation_new_service.py`
- 第 3 节点名的调用方文件
- 对应单测

### Public Contracts

- 不改单据关系 HTTP 的 URL、method、认证头、响应外层结构。
- 新增的是服务方法，不是第二套关系服务，也不是新的批量删除 API。

### Persistence Changes

- 无新表、无迁移。

### Transaction Boundaries

- 已在事务内的删除/创建：失败继续把该事务打回滚。
- `delete_purchase_order` 现网无事务：能力校验之后，申请回滚、关系删除、明细硬删、订单软删放进同一个事务。
- 编码刷新与单据新编号同一事务。
- 发票修复失败只拒绝这一张发票，上抛。

### Risks

- 0 行被当成失败。查出 0 行或业务键删除返回 0，都是显式幂等成功。
- 发票修复把「关联关系已存在」当成失败。该文案改成幂等成功后再写 notes。
- 主键删除的 `NotFoundError` 被收成整单失败。并发下这一行已删掉，只跳过这一行。

### Verification Strategy

- 在 `kuaigeyun-mes/riveredge-backend` 用 `uv run pytest` 覆盖：0 行删除成功、关系已存在时需求计算与发票修复继续、采购订单删除失败时 `deleted_at` 仍空、发票 notes 写失败上抛。未跑通不得声称通过。
