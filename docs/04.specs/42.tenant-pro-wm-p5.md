### Business Goal

在第二 `ROW` 工厂已由 P4（40）开门之后，把生产工单与仓储库存事务纳入同一套失败关闭的 `tenant_id` 隔离。库存事务依赖物料与工单，故本单元**先 pro 再 wm**，同一开发单元、**两批增量 SQL**、退出标准**分开勾选**。跨租户允许相同工单号/仓码（S4）；`workshop_id` / `warehouse_id` 继续是车间与仓库维度，**不能**替代 `tenant_id`。`DATABASE` 租户由应用打同一套增量（I6）；未迁成功则该租户本波不可用，禁止回落主库。

### Scope

In scope:

- 设计表（`mes-pro.sql` / `mes-wm.sql`）全部 `ADD tenant_id bigint not null`（加列 `DEFAULT 1` 再回填），并列入拦截器 include
- 本波 S1 表（产品已分类为租户表）：`pro_assessment`、`pro_evaluation`、`pro_maintenance_records`、`pro_sales_invoice`、`pro_sales_order`、`pro_sales_order_item`、`pro_task_auto`、`pro_task_turnplate`、`pro_workorder_tool`、`wm_after_salse`、`wm_tool_position`
- 两批追加脚本：先 `tenant_pro`，再 `tenant_wm`；路径仅 `startech-mes-basic/backend/sql/YYYYMMDD_NN_*.sql`
- S4：业务单号/仓码唯一键改为 `(tenant_id, 业务键)`；`DATABASE` 同一套 DDL，不改为仅业务键
- S4 窄：加 UNIQUE 前仍跑 `GROUP BY tenant_id, 业务键 HAVING COUNT(*) > 1`（空库也跑）；0 则直接加；非 0 才改键/软删，禁止未清时加索引，不自动合并工单/库存
- S1 缺 CREATE 的表：现网 `SHOW CREATE TABLE` 后再写增量；**禁止**执行仓库空的 `20260820_05_mes_missing_tables.sql`
- I6/I7：应用把本波两批增量打到每个已启用 `DATABASE` 租户；失败则该租户本波阻断、登记保留未就绪、不可用本波业务 SQL，**禁止**回落主库、禁止把该厂数据写入共享主库
- 应用层 `check*Unique`（工单号、仓码、单据号等）语义改为按租户；拦截器对 include 表 SQL **永不跳过 `tenant_id`**
- Mapper 级或领域夹具：两租户工单/库存互不可见；仓库查询仍带 `warehouse_id` 且受 `tenant_id` 约束

Out of scope:

- 实现 Java/SQL 之外的本文件编写范围：本 spec **不在本任务落地代码**；实现时仍不得做下列事项
- 改写 `mes-pro.sql` / `mes-wm.sql` / `mes-qc.sql` / `mes-cal.sql` / `mes-dv.sql` / `mes-tm.sql` 或其它历史初始化 SQL
- 把 `pro_trans_consume` 加入 include（有 CREATE、无 Mapper XML → 废弃候选）
- 用 `workshop_id` / `warehouse_id` 当租户键，或删掉这两列
- 跨租户报表（D5）；克隆 `sys_menu`；引入 MyBatis-Plus / `@DS` / 第二套认证
- 专库失败回落主库；为对齐 schema 把未迁成功的 `DATABASE` 租户写入共享主库
- P6/P7/P8 表、Vue2 `frontend/`、菜单许可改动、P-D 路由实现（依赖 41 已完成）
- 一次 ALTER 全部 MES 表

### Rules and Constraints

Tenant isolation:

- 全部本波 include 表加 `tenant_id`；拦截器失败关闭；INSERT 填充/校验上下文
- `workshop_id` / `warehouse_id` **不是**租户键：保留原列，查询必须同时被 `tenant_id` 约束
- 两档隔离共用同一拦截器与同一套 `(tenant_id, 业务键)` DDL
- 第二 `ROW` 工厂门禁已在 40（P4）；本单元只扩大 include，不重开门禁讨论
- 不进 v1 的跨租户报表（D5）；本波查询仅当前租户

Security and masking:

- 不引入 MyBatis-Plus、第二套认证、按表名回切 DS
- 拦截器漏表风险高于一切：JOIN（如 `pro_task_turnplate` 联 `pro_task` / `wm_rt_issue`）中每个 include 表都必须带租户谓词
- 禁止只按 `item_id` / `workorder_id` / `warehouse_id` 且无租户上下文读他厂数据（物料侧依赖 P4 已覆盖 `md_item`）
- 日志、异常、增量脚本注释不得出现真实 JDBC URL、口令、生产主机
- `DATABASE` 专库不可用禁止回落主库（I5/I6）

Audit and lineage:

- 增量只追加，不改 `mes-pro.sql` / `mes-wm.sql`
- 现网行回填 `tenant_id=1`；种子工厂仍为租户 1
- S1 表 DDL 必须可追溯到现网 `SHOW CREATE TABLE` 输出（证据写第 4 节，不把 dump 全文贴进仓库）

AI/rule-engine rules:

- 本单元不涉及规则引擎或 AI

Database rules:

- 脚本只放 `startech-mes-basic/backend/sql/`，命名 `YYYYMMDD_NN_<topic>.sql`，NN 接目录现有最大序号（实现时取号；建议主题 `tenant_pro` 与 `tenant_wm` 两批）
- `tenant_id bigint not null`，加列 `DEFAULT 1`
- 加 UNIQUE 前：`GROUP BY tenant_id, 业务键 HAVING COUNT(*) > 1`；空库计数为 0 也必须跑完再 `ADD UNIQUE`（S4 窄）
- 仅对「唯一性边界」加复合唯一：主数据编码与单据号；**不要**给行表上的冗余 `item_code` / `workorder_code` 副本加 UNIQUE
- SQL **永不跳过 `tenant_id`**
- 禁止跑空的 `20260820_05_mes_missing_tables.sql`

## 2. Plan

### Implementation Approach

1. 依赖：40（P4 md include）已完成；若目标含 `DATABASE` 租户，41（P-D）必须已完成。本单元不实现路由。
2. 现网对 S1 P5 表执行 `SHOW CREATE TABLE`（只读）；把列类型写入本波增量，**不**跑 `20260820_05_mes_missing_tables.sql`。
3. 第一批 SQL：pro 设计表 + S1 `pro_*`：加列、回填 1、S4 窄检测、复合 UNIQUE。应用（I6）把该批打到每个 `DATABASE` 租户后再扩大 include。
4. 夹具验证 P5a 退出项。
5. 第二批 SQL：wm 设计表 + S1 `wm_*`：同样加列/回填/S4/UNIQUE；DROP 全局仓码 UNIQUE 后再加复合键。I6 再打专库。
6. 扩大 include 到 wm；夹具验证库存互不可见与「`warehouse_id` AND `tenant_id`」。
7. 未迁成功的 `DATABASE` 租户：本波业务失败关闭，不回落主库。

### Affected Modules

- `ktg-mes`：`com.ktg.mes.pro`、`com.ktg.mes.wm`；`src/main/resources/mapper/pro`、`mapper/wm`；以及现位于 `mapper/md` 的 `ProTaskTurnplateMapper.xml`、`WmToolPositionMapper.xml`
- `ktg-framework`：仅扩大 `TenantLineInterceptor` include 名单（不改拦截器算法、不引入 Plus）
- 应用侧 I6 迁表入口（41 已落地的「同一套增量打专库」路径）；本单元只追加脚本文件名到该入口识别的目录约定
- 禁止：`ktg-admin` 塞业务逻辑；`frontend/`；`docs/superpowers/`

### Public Contracts

APIs, facades, DTOs, events, or database contracts:

- HTTP 路径、method、`code/msg/data`、`Authorization` **不变**
- 请求体不新增可伪造的租户字段；租户只来自 JWT/`TenantContext`
- 数据库契约：本波 include 表必有 `tenant_id`；单据号/仓码唯一性变为 `(tenant_id, 业务键)`，跨租户允许相同编码（S4）
- 不新增跨租户列表/汇总接口（D5）

### Persistence Changes

Tables, indexes, migrations, mapper XML, and lifecycle rules:

- 两批增量，追加-only；实现时按 `backend/sql/` 现有最大 `YYYYMMDD_NN` 取号
- 建议：`YYYYMMDD_NN_tenant_pro.sql`、`YYYYMMDD_NN_tenant_wm.sql`（NN 不相等、pro 序号更小）
- 每张 include 表：`ADD COLUMN tenant_id bigint not null default 1`（列已存在则跳过，脚本须可重复审查）
- `UPDATE ... SET tenant_id = 1 WHERE tenant_id IS NULL`（若允许过 NULL 过渡）
- S4 窄检测 → `ADD UNIQUE`
- wm 三张主数据先删除设计脚本中的全局 `UNIQUE`，再加复合唯一
- Mapper XML 不手写拼接租户 ID；依赖拦截器占位符。若某条原生 SQL 绕过拦截器，本单元必须改掉或纳入拦截
- 行表（`*_line`、BOM、报工）只加列进 include，不加单据号 UNIQUE
- `pro_trans_consume`：不加列到 include 名单；本波脚本可不碰该表

### Transaction Boundaries

- DDL 批不包在业务事务里；专库 I6 迁表失败不回滚租户登记（I6：保留未就绪）
- 业务写入保持现有 service 事务；拦截器在 SQL 层，不扩大事务
- 不得在同一事务里先写主库再「失败后当专库」——专库失败即整请求失败

### Risks

- 拦截器漏表（尤其 S1 与 `mapper/md` 下的 pro/wm XML、以及 JOIN）导致跨租户读写
- 只按 `warehouse_id` 过滤库存，串到他厂同 ID 仓库
- 全局 `UNIQUE(warehouse_code)` 未 DROP 导致两厂不能同码（违背 S4）
- 空库跳过 `HAVING` 直接加 UNIQUE，与 S4 窄拍板冲突
- I6 未打专库却让该 `DATABASE` 租户继续跑本波 SQL → 缺列或误打主库
- 误把 `pro_trans_consume` 加进 include

### Verification Strategy

- 静态：include 名单与本 spec 表清单对账；禁止名单含 `pro_trans_consume`
- SQL：审查两批脚本含 HAVING 门禁与复合 UNIQUE；无真实连接串
- 夹具（主库两个 `tenant_id`，模拟 ROW）：工单列表互不可见；库存列表互不可见；同 `warehouse_id` 不同 `tenant_id` 互不可见
- 应用层：两租户可保存相同 `workorder_code` / `warehouse_code`
- I6：对一个夹具 `DATABASE` 租户跑应用迁表；故意跳过迁表的专库访问本波表必须失败且主库无该租户新行
- 命令：`mvn -pl ktg-mes -am test`（进入 `startech-mes-basic/backend`）；无测则编译 + 新建测试类。未跑不得写通过
