### Rules and Constraints

Tenant isolation:

- 主库一次 migrate 覆盖全部 `ROW` + 平台；不要按租户循环打主库（FLY3）
- `DATABASE` 专库只跑 `tenant/` location；I8 全局表不得出现在 tenant 脚本
- 专库不可用禁止回落主库；主库 migrate 失败拒启动，专库补齐失败只标 `FAILED`（FLY2 vs FLY6）

Security and masking:

- 不引入第二套认证或 ORM
- 专库连接仍解密 `TENANT_JDBC_CIPHER_KEY`；日志/异常剥 URL 与口令
- 不扩大匿名 HTTP 面；不把密钥写入 yml
- 登录失败文案仍「用户名或密码错误」（D9）；FLY7 不在登录时跑 DDL

Audit and lineage:

- `backend/sql/` 切线后只作历史；新发布 DDL 只进 `ktg-system/.../db/migration/{master,tenant}/`
- 已发布 Flyway 文件冻结；修正用新版本，不改旧文件 checksum

AI/rule-engine rules:

- AI 租户表已在 `TenantDedicatedSchema.AI_TABLES` / `incrementalSqlFiles()` 末段；快照必须含这些表。不在本切线重开 AI 需求

Database rules:

- 依赖：`org.springframework.boot:spring-boot-starter-flyway` + `org.flywaydb:flyway-mysql`（version 由 Boot 4.1.0 BOM 管）。不要单独声明 `flyway-core`
- `spring.flyway.baseline-on-migrate=false`；`validate-on-migrate=true`；禁止 `outOfOrder=true`
- 主库 locations = `classpath:db/migration/master` + `classpath:db/migration/tenant`；绑 `@FlywayDataSource` 的 `masterDataSource`
- 专库编程 API locations = 仅 `tenant/`；一次性 JDBC，不注册 Druid 专池

1. 以 `TenantDedicatedSchema.incrementalSqlFiles()` **最后一项**为租户 catalog 尽头。撰写时最后一项为 `20260825_31_ai_tool_audit.sql` → 候选基线 **`20260825.31`**。

3. 快照文件：`tenant/V{基线}__tenant_schema_snapshot.sql`（slug 前缀 `tenant_`）。已有库由运维 `baseline` 到同一版本，不跑快照。
4. 设计文原 `20260822.20` 仅记录当时意图；catalog 已超过则 **作废该号**。

**开通 schema 只跑一套 DDL（禁止 `sql/` 与 Flyway 叠跑）：**

「基线」有两个不同动作，不要混成「先跑基线 SQL 再跑 Flyway」：

| 名字 | 是什么 | 谁执行 | 会不会跑 SQL |
| --- | --- | --- | --- |
| 历史 `backend/sql/`（含 catalog 里的增量） | 切线前手工/warehouse 清单 | **切线后开通不再执行** | 否（只当历史） |
| `tenant/V{基线}__tenant_schema_snapshot.sql` | Flyway **普通 versioned 文件**，内容是切线当日全套 `CREATE TABLE` | 空专库的 `Flyway.migrate()` | **会。** 这就是新厂的建表 |
| 运维命令 `flyway baseline` | 只往 `flyway_schema_history` 插一行「已处于该版本」 | 已有主库 / 已有 READY 专库，启动应用**之前** | **不会。** 不执行快照、不执行 `sql/` |

`POST /platform/tenant/{id}/schema`（76 之后）完整顺序：

```text
1. 预算 + 并行槽 N≤2
2. CREATE DATABASE IF NOT EXISTS          ← 仍是 JDBC，不是 Flyway 文件
3. Flyway.migrate(locations = tenant/)    ← 空库无 history，因此：
     先执行 V{基线}__tenant_schema_snapshot.sql   （建全套租户表）
     再按版本序执行 tenant/ 里所有更高号文件         （切线后的增量；切线日可以没有）
     不扫描 master/，不读 backend/sql/，不调 TenantWarehouseSql
4. 复制角色 / 角色菜单模板                 ← 仍是 Java，不是 SQL 文件
5. ping → READY
```

对照：

- **新开空专库：** 不 baseline。快照必须被执行，否则空库没有表。禁止 `baselineOnMigrate`（否则会跳过快照）。
- **已有主库 / 已有 READY 专库：** 运维先 `baseline` 到同一版本号，启动后 Flyway **跳过**快照，只跑更高号。schema 按钮不是给这类库「从零建表」用的。
- 快照 = 把 `dedicatedCreates()` + `incrementalSqlFiles()` 折成的**一份** CREATE，不是在开通时再把那些历史文件跑一遍。

**交付窗口：** 75 打开 `spring.flyway.enabled=true` 之后、77 完成之前，禁止往 `tenant/` 追加新版本（否则已 READY 专库会落后且无人补齐）。

### Affected Modules

- 文档：`docs/02.requirements/02.mes-multi-tenant-gaps.md`、`docs/03.design/05.mes-flyway-integration.md`、`docs/04.specs/35` / `41` / `74`–`77`、`AGENTS.md` 增量 SQL 一句
- 后端（75–77）：`ktg-system`、`ktg-framework`、`ktg-admin`
- 禁止：`startech-mes-basic/frontend/`；`docs/superpowers/`；`ktg-generator` 业务行为

### Public Contracts

- 不改 HTTP 契约（含 `POST /login`、`POST /platform/tenant/{id}/schema` 的 URL/method/信封）
- `provision_status` / D9 文案不变
- 不新增客户端租户头

### Persistence Changes

- 新增 `flyway_schema_history`（Flyway 默认表名，主库与各专库各一份）
- 新增 `db/migration/master/`、`db/migration/tenant/`
- 不改业务表列（快照只 `CREATE` 切线当日结构）

### Transaction Boundaries

- 主库 migrate 在应用上下文刷新期，失败则进程退出
- 开通：登记已存在；CREATE DATABASE + migrate + 角色模板 + ping 仍一次开通步骤，失败标 FAILED、不回滚 `sys_tenant` 行
- 启动补齐：每租户独立连接；失败只更新该行

### Risks

- 未 baseline 的已有库启动时重放快照 `CREATE` → 拒启动（符合 FLY8，须运维前置）
- 基线号钉低会导致已应用的 AI/租户增量被当成「未发布」或快照缺表
- 多 `DataSource` 未标 `@FlywayDataSource` → `Flyway migration DataSource missing` 或打到路由源
- 76–77 窗口追加 tenant 版本 → READY 专库落后

### Verification Strategy

- 总控只验收文档完整性与 TOC
- 75–77 第 4 节：未执行前写「未执行」；实现后写实际命令
- 优先模块测试 + 占位 JDBC；真实 MySQL / 现网 baseline 写明是否跳过
