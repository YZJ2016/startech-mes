## 1. Spec

### Capability

### Business Goal

有设备权限的人查看设备、做点检、换线、巡检、报修和保养提醒。待处理故障数和逾期保养数只读 bootstrap，不在手机上重算。

### Scope

In scope:

- 下表 8 个工作台入口。
- `badge`：读取函数只返回 `GET /api/v1/apps/kuaizhizao/mobile/bootstrap` 的 `pending_fault_count`、`overdue_maintenance_reminder_count`。壳按 164 显示这两个数。
- 两条深链：`/equipment/detail`、`/equipment/spot-check-conduct`。声明 `in_workbench: false`。Caddy 已经把旧链接指到这里。
- 报修页读查询参数 `uuid`，用已有故障详情打开对应记录，并仍能创建一条故障。

Out of scope:

- 在客户端计算故障数或逾期数。
- 改 Caddy。
- 模具。模具在 `docs/04.specs/169.mobile-mold.md`。
- 校准、备件、导出。

| `route-patrols` | 路线巡检 | `/equipment/route-patrols` | `GET /api/v1/apps/kuaizhizao/equipment-route-patrols` | `POST /api/v1/apps/kuaizhizao/equipment-route-patrols`（`routePatrolsApi.create` / `create_route_patrol`） |
| `faults` | 报修维修 | `/equipment/faults` | `GET /api/v1/apps/kuaizhizao/equipment-faults` | 创建一条故障。查询参数有 `uuid` 时另打开 `GET /api/v1/apps/kuaizhizao/equipment-faults/{uuid}` |

| `maintenance-reminders` | 维护提醒 | `/equipment/maintenance-reminders` | `GET /api/v1/apps/kuaizhizao/maintenance-reminders` | `POST /api/v1/apps/kuaizhizao/maintenance-reminders/mark-handled` |

设备点检页主按钮是新建：`spot-checks/index.tsx` 的 `onCreate` 提交时调用 `spotChecksApi.create`。同资源其余写方法本单元不做：`update_spot_check`、`delete_spot_check`、`approve_spot_check`、`reject_spot_check`。

路线巡检页主按钮同样是新建：`route-patrols/index.tsx` 的 `onCreate` 提交时调用 `routePatrolsApi.create`。同资源其余写方法本单元不做：`update_route_patrol`、`delete_route_patrol`。`spotChecksApi` 与 `routePatrolsApi` 都展开了 `crudFactory.ts` 里 `crudApi` 的 `create`。后端对应 `documents.py` 的 `create_spot_check`、`create_route_patrol`。

深链声明 `in_workbench: false`，不进宫格：

- `/equipment/detail` 读查询参数 `uuid`，`GET /api/v1/apps/kuaizhizao/equipment/{uuid}`（`get_equipment`）。
- `/equipment/spot-check-conduct` 是 Caddy `@m_equip_spot_check_legacy`、`@m_equip_uuid_spot` 的 H5 目标，不是接口。PC 没有「执行点检」页，点检资源也没有名为 conduct 的路径。该页读查询参数 `uuid`（设备 uuid），先 `GET /api/v1/apps/kuaizhizao/equipment/{uuid}`（`get_equipment`），再调用与点检主按钮相同的 `spotChecksApi.create`。

报修页仍在宫格里。Caddy `@m_equip_uuid_fault` 把 `/m/kuaizhizao/equipment/{uuid}/fault` 重定向到 `/mobile/equipment/faults?uuid=`。该页读查询参数 `uuid`，用已有 `GET /api/v1/apps/kuaizhizao/equipment-faults/{uuid}`（`get_equipment_fault`）打开这条故障，并保留创建一条故障（`POST /api/v1/apps/kuaizhizao/equipment-faults`，`create_equipment_fault`）。不新造接口。

### Acceptance Criteria

1. 八个工作台入口都能打开，请求路径与表一致。点检主操作是 `create_spot_check`，巡检主操作是 `create_route_patrol`。
2. 本包 `badge` 只返回 bootstrap 的两个字段。页面代码里没有另一套计数。壳按 164 显示，本单元不改壳的渲染实现。
3. `/equipment/detail` 与 `/equipment/spot-check-conduct` 的 `in_workbench` 为 `false`。H5 地址 `/mobile/equipment/detail` 与 `/mobile/equipment/spot-check-conduct` 能打开，且不出现在宫格。点检深链调用 `create_spot_check`，不调用名为 conduct 的路径。`/mobile/equipment/faults?uuid=` 打开 `GET /api/v1/apps/kuaizhizao/equipment-faults/{uuid}` 的那条故障，创建一条故障仍可用。Caddy 模板未改。
4. 去掉本包导入后，工作台入口回到空态；深链不再进入业务页。
5. 页面在三端的 registry 与 `pages.json` 都注册。业务操作的验收只在已登录 H5 上进行。小程序和 App 因取码未接通，不要求走通业务页。

## 2. Plan

### Implementation Approach

`features/equipment/` 放八个入口和两个深链页。声明 `badge` 与两条深链的 `in_workbench: false`。报修页读 `uuid` 并调用已有故障详情。registry 与 `pages.json` 只追加这些页面，三端都登记。不改壳的渲染实现。

### Affected Modules

- `features/equipment/`
- 壳 registry 与 `pages.json` 的追加

### Public Contracts

- 上表路径与 bootstrap 的两个字段。不新增 URL。

### Persistence Changes

- 无。

### Transaction Boundaries

- 点检创建、巡检创建、报修、完工、标记已处理各调用一次现有接口。带 `uuid` 的报修页先读一次已有故障详情。

### Risks

- 点检深链若写成名为 conduct 的路径，会离开现有 `create_spot_check`。报修深链的 `uuid` 必须走已有 `get_equipment_fault`，不另做查询接口。

### Verification Strategy

- 在已登录 H5 上打开扫码、报修、提醒，并直接访问两条深链。带 `uuid` 的报修地址能打开对应故障。核对角标与 bootstrap 响应一致。小程序和 App 不要求走通这些页。§4 实跑后填写。
