### Business Goal

批量补齐某一张采购订单的预付失败时，这张订单标成未补齐，然后才处理下一张。已经有预付关联的订单标成已补齐并跳过生成。失败不能只打日志，让单据看起来和还没跑过一样。

### Scope

In scope:

- `backfill_missing_purchase_order_prepayments` 按单循环时写下补齐标记。
- 采购订单增加补齐状态，空着表示还没跑过。
- 采购订单既有读响应带出该状态。PC 端已有采购订单预付款展示处显示它。

Out of scope:

- 不因此回滚本批已经成功的其他订单。
- 不改单笔 `ensure_prepayment_payment_for_purchase_order` 已有的抛错（484–492 行仍抛 `BusinessLogicError`）。
- 不把销售预收批量补齐写进本单元。现网没有对称的销售批量函数，不新增。
- 不改预付余额页 URL、method、认证头、响应外层结构。调用点仍是 `get_prepayment_balances` 310–312 行。

### Acceptance Criteria

1. 批量中某一单 `ensure_prepayment_payment_for_purchase_order` 抛错：该采购订单补齐状态为未补齐，循环继续下一单。本批此前已成功的订单保持已补齐，不被回滚。
2. 已有 `purchase_order` → `payment` 关联的订单：标成已补齐，不调用生成。
3. 本单生成成功并得到付款单：同一轮标成已补齐。
4. 未进入本循环的订单（未确认，或预付金额不大于 0）补齐状态仍为空，与未补齐可区分。
5. 把未补齐标记写入采购订单失败：本批上抛，不再处理后续订单。已经写成功的订单保持原标记。
6. 单笔 `ensure_prepayment_payment_for_purchase_order` 在金额不大于 0 或已有关联时的返回，以及失败时抛 `BusinessLogicError`，保持。销售订单不增加对称批量函数，也不增加本状态字段。

### Rules and Constraints

Tenant isolation:

- 标记只写当前 `tenant_id` 下的采购订单。

Security and masking:

- 日志与接口不新增凭据或内部路径。现有 warning 可以保留，但不能代替单据标记。

Audit and lineage:

- 标记在采购订单上，不另建补齐日志表。

AI/rule-engine rules:

- 不涉及。

Database rules:

- `PurchaseOrder` 在 `prepayment_amount` / `prepayment_bank_account_id`（`purchase_order.py` 93–96 行）旁增加可空 `prepayment_backfill_status`。空：还没跑过。`missing`：未补齐。`backfilled`：已补齐。
- 需要一条 Tortoise app `models` 的 aerich 迁移。文件放 `migrations/models/`。文件名第一段为 14 位时间戳，且大于该目录已有迁移文件名里出现过的最大时间戳。不要接开源仓序号（如 793）。本 spec 不指定文件名。

## 2. Plan

### Implementation Approach

- 生成失败仍由批量函数捕获，捕获后先把该订单写成 `missing` 并提交这一笔标记，再继续下一单。
- 标记本身写失败不捕获成 warning，向 `get_prepayment_balances` 上抛。
- 已有关联或本轮生成成功，写成 `backfilled`。

### Affected Modules

- `src/apps/kuaicaiwu/services/finance_integration_hooks.py`
- `src/apps/kuaizhizao/models/purchase_order.py`
- 采购订单 schema 与既有读接口（加字段，不改外层）
- `riveredge-frontend` 采购订单已有预付款展示
- 对应单测

### Public Contracts

- 预付余额接口与采购订单接口的 URL、method、认证头、响应外层结构不变。
- 采购订单对象增加可空 `prepayment_backfill_status`。

### Persistence Changes

- 见 Database rules。存量行该字段为空。

### Transaction Boundaries

- 每一张订单的生成与标记各自提交后再处理下一张。
- 生成失败：该订单的 `missing` 标记提交成功后才进入下一张。
- 标记写失败：上抛，不回滚本批已经提交的其他订单。

### Risks

- 标记写失败被批量 except 吃掉。生成失败的 except 只包生成，不包标记写入。
- 把销售订单预收卷进来。本单元只改采购批量函数。

### Verification Strategy

- 在 `kuaigeyun-mes/riveredge-backend` 用 `uv run pytest` 覆盖单笔失败留标记、已有关联跳过、标记写失败上抛、其他订单不回滚。前端改了采购订单展示时，在浏览器确认未补齐与已补齐能看出来。未跑通不得声称通过。
