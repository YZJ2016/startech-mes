# 触屏工位机 — 快捷报工

本文件可实施。页面落在 spec 157 的工位入口能打开的触屏页上。写入只走现有报工接口。

## 1. Spec

### Capability

- Name: 工位快捷报工与报工附属动作
- Module: `kuaigeyun-mes/riveredge-frontend`。接口为现有 `POST /api/v1/apps/kuaizhizao/reporting/quick` 及报工附属路由。
- Priority: STN-D7、STN-Q1、STN-Q4。依赖 157。
- Related requirement/design documents:
  - 缺口：`docs/02.requirements/20.station-terminal-gaps.md`（**STN-D7**、**STN-Q1**、**STN-Q4**）
  - 设计：`docs/03.design/20.station-terminal-plan.md`（§2、§3）
  - 入口：`docs/04.specs/157.station-terminal-entry.md`

### Business Goal

操作员在工位上完成本人、代报、小组三种快捷报工，并在报工之后做上料、下料和报废。报工来源落成「终端」，`device_info` 带上当前工位。

### Scope

In scope:

- 三种快捷报工都调用现有 `POST /api/v1/apps/kuaizhizao/reporting/quick`。数量、合格、不合格、工时可在该请求里提交。有不合格数量时，沿用请求体里已有的 `defect` 字段，与报工同一事务记不良。
- 本人：`worker_id` 与 `worker_name` 只用工位入口上的当前操作员（点选或刷脸切换后的那个人）。登录会话只负责认证。未传入 `operator` 时，不改用登录用户，也不改用工序派工人员，本人报工不调用 `POST /reporting/quick`。入口挂载 `StationReportingPage` 时传入这份当前操作员和 `workstationId`。没有当前操作员时页面仍可打开，但不提交本人报工。
- 代报：指定另一名生产人员。页面在提交前确认登录会话具备 `kuaizhizao:production-execution-reporting:assign`，没有该权限时不提交。
- 小组：提交 `team_id` 与 `team_name`。现有创建校验要求小组名称必填，且须指定生产人员或工作小组。
- `POST /reporting/quick` 的代报权限按渠道区分。请求头渠道是 `station` 时，操作员和登录用户不是同一人仍算本人报工，不因为 `worker_id != current_user.id` 要求 `kuaizhizao:production-execution-reporting:assign`。小组报工在 `station` 渠道下也不被这条办公室代报权限拦住。`recorded_by` 仍是登录用户（终端账号）。渠道不是 `station` 时，保持原判断：`team_id` 有值，或 `worker_id` 为空，或 `worker_id` 不等于当前登录用户，才要求该权限。渠道仍读 `resolve_client_channel_code_from_request` / `_resolve_reporting_client_channel`，不新造请求头。
- 工位报工页：本人模式只提交入口当前操作员，不把登录用户写入 `worker_id`。小组不因缺少 `assign` 被页面禁用。代报（明确指定另一名生产人员，且不是入口当前操作员）仍要 `assign`，没有该权限时不提交。
- 报工成功后的附属动作走现有接口：
  - 上料 `POST /api/v1/apps/kuaizhizao/reporting/{record_id}/material-binding/feeding`
  - 下料 `POST /api/v1/apps/kuaizhizao/reporting/{record_id}/material-binding/discharging`
  - 报废 `POST /api/v1/apps/kuaizhizao/reporting/{record_id}/scrap`
- `device_info.workstation_id` 为 157 已绑定的工位。工位构建的 `X-Client-Channel: station` 由现有报工来源映射落成「终端」（`client_channel.py` 中 `station` → `终端`）。
- 157 的工位入口「报工」打开 `production-execution/station/reporting` 上的 `StationReportingPage`，并传入当前操作员与 `workstationId`。入口报工按钮不指向 `station/reporting/kiosk`。办公室的 `production-execution/reporting/kiosk` 路径不改。

Out of scope:

- 新的报工 URL、新的渠道码、新的报工表字段
- 报工审核、撤回、金蝶重推
- 开工 API 内嵌 SOP 或资质；标签工位
- 电视看板、小程序、企业微信、移动端复制页面
- 改 `startech-mes-basic`；把页面烤进 exe

### Acceptance Criteria

1. 工位入口可以提交本人、代报、小组三种快捷报工，三次都是 `POST /reporting/quick`。本人的 `worker_id`、`worker_name` 是入口当前操作员。没有当前操作员时，本人报工不提交。
2. 无 `kuaizhizao:production-execution-reporting:assign` 时，代报请求不会发出。`station` 渠道下，本人（`worker_id` 为入口操作员，可以不等于登录用户）和小组报工不被这条权限拒绝。非 `station` 渠道仍按原代报判断要求该权限。
3. 工位构建下产生的报工，`client_channel` 为 `station`，来源展示为「终端」。`device_info.workstation_id` 等于入口当前绑定的工位。
4. 一条报工记录之后可以上料、下料、报废，URL 为上列三个附属接口。
5. 本单元没有新的报工路由，也没有新表。

### Rules and Constraints

Tenant isolation:

- 报工、绑定与报废沿用现有租户隔离。

Security and masking:

- 代报权限码为 `kuaizhizao:production-execution-reporting:assign`。页面不输出令牌。
- 渠道由当前路径计算的 `X-Client-Channel` 携带。工位入口及其子路径为 `station`。页面不另造渠道字段去覆盖服务端判定。
- `X-Client-Channel` 为可伪造请求头。`station` 渠道的 assign 豁免信任面限于内网部署，已接受该风险。

Audit and lineage:

- 报工记录、不良、上料、下料、报废都写在现有表。交接班按工位汇总依赖这里的 `workstation_id`（汇总页面在 161）。
- `station` 渠道下 `report_mode` 仍按 `worker_id≠recorded_by` 落 `proxy`（维持现状，不随 assign 豁免改）。

AI/rule-engine rules:

- 不涉及。

Database rules:

- 无新表，无迁移。

## 2. Plan

### Implementation Approach

1. 在工位可达的触屏页上做三种提交，请求体差别只在人员、小组和 `device_info`。
2. 代报按钮依据指派权限显示或在提交前拦截。
3. 报工成功后用返回的记录 ID 调用上料、下料、报废。

### 依赖

- 依赖 157 的入口、绑定工位、当前操作员，以及工位构建的 `station` 渠道。
- 与 158、160、161 可先后实现。端到端冒烟在 162。

### Affected Modules

- 工位入口「报工」打开的 `StationReportingPage`（`station/reporting`）
- 只调用现有 `api/productions/reporting.py`
- 不改 `reporting_service.py` 的渠道映射

### Public Contracts

- `POST /api/v1/apps/kuaizhizao/reporting/quick`
- `POST /api/v1/apps/kuaizhizao/reporting/{record_id}/material-binding/feeding`
- `POST /api/v1/apps/kuaizhizao/reporting/{record_id}/material-binding/discharging`
- `POST /api/v1/apps/kuaizhizao/reporting/{record_id}/scrap`
- 请求头 `X-Client-Channel: station`
- 权限码 `kuaizhizao:production-execution-reporting:assign`

### Persistence Changes

- 无新结构。`device_info` 使用报工记录已有字段。

### Transaction Boundaries

- 快捷报工与可选 `defect` 沿用该接口现有的同一事务。
- 上料、下料、报废各为报工成功之后的独立现有事务。

### Risks

- 另写报工 URL 会离开 **STN-Q4**。
- 页面若自行把渠道字段写成「终端」汉字，会和现有来源聚合不一致。来源由请求头 `station` 经服务端映射。
- 漏带 `workstation_id` 时，161 的交接班汇总对不上这台工位。

### Verification Strategy

- 见 §3。§4 在命令实跑后填写。本文件写下时未跑测试或构建。

Behavior delivered:

- `index.ts` 导出 `StationReportingPage`。
- 代报、小组、以及挂载方传入 `operator` 时的本人，都调用现有 `reportingApi.quickCreate`（`POST /api/v1/apps/kuaizhizao/reporting/quick`）。请求体不写渠道。`X-Client-Channel` 仍由 `apiRequest` → `webClientChannelHeaders` 按当前路径注入。
- 本人的 `worker_id`、`worker_name` 只来自 props `operator`（入口当前操作员）。未传 `operator` 时 `buildQuickReportingBody` 返回 `missing-operator`，页面不调用 quick。不改用登录用户，也不改用工序派工人员。`useCurrentUser` 只用于代报权限 `hasModulePermission`。
- 入口不再把登录用户写成当前操作员。没有点选或刷脸切换时，`operator` 为 null，本人报工不提交。
- 代报权限沿用报工页 `hasModulePermission(user, 'kuaizhizao:production-execution-reporting', 'assign')`。无权限时不调用 quick。小组不在页面拦截，接口错误用 `error.message` 展示。
- 工位 ID：props `workstationId` 为正整数时使用，否则读 URL query `workstationId`，写入 `device_info.workstation_id`。入口传入的是入口状态里的工位 ID。
- 报工成功后上料、下料、报废分别调用现有 `materialBindingApi.createFeeding`、`createDischarging`、`reportingApi.recordScrap`。上料/下料 body 按 `MaterialBindingCreateFromReporting`（`material_id`、`quantity`、`binding_type`）。有不合格数量时，`defect` 与报工同一请求提交（`defect_quantity`、`defect_reason`）。
