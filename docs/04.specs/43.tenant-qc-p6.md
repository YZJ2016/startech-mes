### Capability

- Name: P6 质量 `qc` 行级租户隔离
- Module: `startech-mes-basic/backend/ktg-mes` 包 `com.ktg.mes.qc` 及 `mapper/qc`
- Priority: P6（设计 §4.4；总控 43）
- Related requirement/design documents:

  - 下一单元：`docs/04.specs/44.tenant-cal-dv-tm-p7.md`

### Business Goal

把质量域（检验项、模板、来料检 IQC、过程检 IPQC、出货检 OQC、缺陷）纳入与 P4/P5 同一套失败关闭的 `tenant_id` 隔离。检验单、模板、缺陷记录按租户互不可见。QC 行上的 `item_id` **不得**只按主键、不按租户读到他厂物料——这依赖 P4 拦截器已覆盖 `md_item`，本单元不得回退该覆盖，也不得新增「按 id 裸查物料」的旁路。`DATABASE` 租户由应用打与主库同一套本波增量（I6）；未迁成功则该租户本波不可用，禁止回落主库。

### Scope

In scope:

- `mes-qc.sql` 设计表全部加 `tenant_id` 并列入拦截器 include：`qc_index`、`qc_template`、`qc_template_index`、`qc_template_product`、`qc_defect`、`qc_iqc`、`qc_iqc_line`、`qc_defect_record`、`qc_ipqc`、`qc_ipqc_line`、`qc_oqc`、`qc_oqc_line`
- 增量脚本仅追加到 `startech-mes-basic/backend/sql/YYYYMMDD_NN_*.sql`；禁止原地改 `mes-qc.sql`
- S4：检验项编码、模板编码、缺陷编码、IQC/IPQC/OQC 单号唯一性改为 `(tenant_id, 业务键)`；专库同一套 DDL
- S4 窄：加 UNIQUE 前仍 `GROUP BY tenant_id, 业务键 HAVING COUNT(*) > 1`（空库也跑）
- 应用层 `checkIndexCodeUnique` / `checkTemplateCodeUnique` / `checkIqcCodeUnique` / `checkIpqcCodeUnique` / `checkOqcCodeUnique` 等按租户语义
- 引用 `item_id` / `workorder_id` 的 QC 查询必须落在已 include 的表上，并依赖 P4 的 `md_item` 租户谓词；禁止新增 id-only 且跳过拦截器的查询
- I6：应用把本波增量打到每个已启用 `DATABASE` 租户；失败则该租户本波阻断，无主库回落
- SQL 永不跳过 `tenant_id`；不引入 MyBatis-Plus；不克隆菜单；无跨租户质量报表

Out of scope:

- 本任务不实现 Java/SQL（只写 spec）
- 改写 `mes-qc.sql` 或其它历史 `mes-*.sql`
- P5 未完成的 pro/wm 表；P7 cal/dv/tm；P8 报表/UReport（D5：v1 无跨租户报表）
- 把 `workshop_id` / `warehouse_id` 当租户键
- 为 QC 单独引入第二套 ORM/认证；菜单复制进租户
- 跑空的 `20260820_05_mes_missing_tables.sql`（本波无 S1 qc 表，仍禁止误跑）
- 专库失败回落主库；未迁 schema 的 `DATABASE` 租户继续写共享库

### Rules and Constraints

Tenant isolation:

- QC 表全部为租户表；无上下文不得访问
- 引用完整性按租户：`item_id` 指向的 `md_item` 必须同 `tenant_id`（拦截器保证读不到他租行，等于失败关闭）
- IPQC 上的 `workorder_code` / `task_code` 是冗余展示列，**不是**租户键；隔离仍靠 `tenant_id` + P5 已 include 的工单/任务表
- 不进跨租户质量汇总（D5）

Security and masking:

- 最大风险：检验详情按 `item_id` 裸查物料或供应商，绕过租户谓词
- 其次：模板绑定产品（`qc_template_product`）按 `item_id` 串到他厂物料
- 日志与脚本不得含真实 JDBC/口令/生产主机
- 不引入 Plus `@DS`；忽略名单 Mapper 仍走 41 的主库绑定（本单元不改 I8 名单）

Audit and lineage:

- 增量追加-only；回填租户 1
- 唯一键变更可审查、可回滚（DROP INDEX 回退说明写在脚本注释，不含敏感值）

AI/rule-engine rules:

- 本单元不涉及规则引擎或 AI

Database rules:

- `startech-mes-basic/backend/sql/YYYYMMDD_NN_tenant_qc.sql`（NN 接现有最大号）
- `tenant_id bigint not null default 1`
- S4 窄：空库也先 `HAVING` 再 UNIQUE
- 只给唯一性边界加复合键；行表不加检验单号 UNIQUE
- SQL 永不跳过 `tenant_id`
- 禁止改写 `mes-qc.sql`

## 2. Plan

### Implementation Approach

1. 依赖：40 已覆盖 `md_item`；建议 42 已完成（IPQC 引用工单/任务时避免半隔离窗口）。可与 42 部分并行，但 `item_id` 退出项**不能**在 P4 include 缺失时勾选。
2. 追加 `YYYYMMDD_NN_tenant_qc.sql`：设计表加列、回填 1、S4 窄、复合 UNIQUE。
3. I6：应用把该脚本打到每个已启用 `DATABASE` 租户；失败则该租户本波 QC 不可用，不回落主库。
4. 扩大拦截器 include 到上表全集。
5. 审查 qc Mapper：所有按 `item_id` 查物料必须走已 include 的 `md_item`（拦截器加 `tenant_id`），禁止新建跳过拦截的原生 SQL。
6. 夹具：两租户模板/检验单/缺陷互不可见；租户 A 的 IQC 使用租户 B 的 `item_id` 不得读到物料行。

### Affected Modules

- `ktg-mes`：`com.ktg.mes.qc` 与 `src/main/resources/mapper/qc/*.xml`
- `ktg-framework`：仅扩大 include 名单
- I6 迁表入口（41）识别新脚本
- 禁止改 `frontend/`、禁止改历史 `mes-qc.sql`

### Public Contracts

APIs, facades, DTOs, events, or database contracts:

- 既有 QC HTTP 契约不变（路径、method、`code/msg/data`）
- 单号唯一性从「全局应用层检查」变为「按租户」；跨租户允许相同 `iqc_code` 等（S4）
- 无跨租户检验报表接口（D5）

### Persistence Changes

Tables, indexes, migrations, mapper XML, and lifecycle rules:

- 一批增量覆盖 `mes-qc.sql` 12 张表
- 行表只加 `tenant_id` 进 include
- Mapper 不手拼租户 ID；拦截器占位符绑定
- 不改 `mes-qc.sql`

### Transaction Boundaries

- DDL 与 I6 迁表失败不回滚租户登记（保留未就绪）
- 业务事务范围保持现有 QC service；不扩大

### Risks

- `item_id` 旁路读他租物料（高于本波其它风险）
- include 漏行表或 `qc_defect_record`，缺陷记录串租户
- 未迁专库却开放 QC API → 缺列或打到主库
- 给行表冗余 `item_code` 加 UNIQUE，误伤合法多行

### Verification Strategy

- 夹具两 `tenant_id`：列表/详情互不可见
- 夹具：租户 A 会话查询 `item_id` = 租户 B 物料主键 → 空或业务失败，不得返回他厂物料
- S4：两租户可保存相同 `template_code` / `iqc_code`
- I6：跳过迁表的 `DATABASE` 租户访问 qc 表失败，主库无该厂 QC 新行
- `mvn -pl ktg-mes -am test`；未跑不得写通过
