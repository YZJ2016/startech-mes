## 1. Spec

### Capability

- Name: 星AI 双层菜单、能力矩阵与智能体库。
- Module: `kuaigeyun-mes/riveredge-frontend/src/apps/kuaiai`、`riveredge-backend/src/apps/kuaiai`。
- Priority: P0；后续 185→182→183→184 的导航、权限注册和共享视觉基线。
- Related requirement/design documents: `docs/02.requirements/24.kuai-ai-operational-layer-gaps.md`（KO-01～KO-03）；`docs/03.design/24.kuai-ai-operational-layer-plan.md`（§2～§5、§11.1～11.2）。

### Business Goal

保留既有 AI 对话、Agent 档案、知识库与 MCP 管理入口：安装 KU-AI 即按租户幂等预置六个制造场景模板、六份真实 Agent 档案及一一对应的场景实例；补齐安全的领域只读 Tool。模板卡是运营入口，现有 Agent 档案/授权、模型连接与业务 service 是唯一执行底座；管理员可以随后授权员工、定制或复制。

### Scope

In scope:

- `manifest.json` 新增“智能运营”“智能治理”无路径分组；保留 `/chat`、`/agents`、`/knowledge`、`/mcp`。
- 新增 `/hub`、`/agent-library` 路由、页面、共享页头和指标卡。
- 新增 `GET /api/v1/apps/kuaiai/operations/hub` 与 `/agent-library`。
- 八能力状态聚合、六个后端预置场景模板及安装/存量升级时的六租户档案+实例一一绑定、场景总/单项开关读取、业务路由可用性；前端从 API 渲染模板与租户复制项，不内嵌固定六卡数据。
- 安装时幂等建六份 `status=停用`、`grant_mode=ROLE`、`default_model_id=null`、空授权名单的 Agent 档案并逐一绑定实例；不自动授予任何管理员/角色/员工，也不自动启用，管理员随后在既有 `/agents` 选择 ROLE/USER、配置名单并启用；初始六档案配场景提示词和经过真实业务权限/数据范围约束的只读 Tool，不预置任何写 Tool、MCP 密钥、空知识库或未经确认的知识库关联。
- 租户管理员仍可改绑/定制以及从本租户已有档案按需克隆停用档案、创建额外场景副本；无权限/无模型/无语料/无业务数据时按原因显示待配置或空态，不编造就绪。
- 复用现有助手抽屉与 `/core/ai/chat/completions` 自动发送样例问题。
- 页面加载、空、部分失败、403、窄屏和键盘行为。
- 一次性建立七个新页面及写操作的权限矩阵、两端 manifest 权限注册和预设角色授权规则；后续各单元实现对应接口鉴权，186 验证存量租户升级。

Out of scope:

- Pulse detector、语料 CRUD、信任/分析、设置写入；分别属于 182–185。
- 修改现有 `/agents` 管理页、Agent REST 或 `/knowledge` 管理页；场景按需复制通过现有 `agent_service.create_profile` 校验链完成，不绕开其禁直接启用/授权约束。
- 复制示例系统插图；本单元只接入项目自有/经确认可使用的六张图片资产。
- 新建聊天协议、模型目录或第二套权限体系；默认开放写工具、自动造真实业务知识文档，或在安装/升级时给任何用户/角色自动写档案使用权。

### Acceptance Criteria

1. 星AI菜单按设计形成两个分组，已有四个路径和书签继续有效。
2. 1280×720 下内页内容宽约 951 px；标准页头标题 24/32、动作高 32；移动端无整页横向溢出。
3. hub 展示八个能力标签、四项真实指标、品牌视觉卡和八张能力卡；失败数据为 `—`/部分失败，不伪造 0。
4. 状态只使用 `ready|partial|not_ready`；按钮根据目标路由、权限和配置真实启停。
5. KU-AI 安装后当前租户实际存在六份 `KuaiaiAgentProfile` 和六个绑定实例，按模板 key 一一对应；重复安装/启用/升级不重复建档或覆盖租户自定义；初始页面六卡两列，允许额外复制项，客户端不写死六卡闭集。预置失败必须报告/可重试，不以无档案虚拟卡宣称“已装好”。
6. 安装时档案默认停用、授权名单为空；应用启用或后续升级同步都不自动写 grant、不自动启用档案。管理员在现有 Agent 档案页把授权模式保持 ROLE 或改为 USER、配置非空名单后才能启用；普通员工不会因安装动作获得使用权。管理员可改绑现有档案、复制出附加停用档案/场景副本；复制不得继承授权名单、凭据或跨租户对象，失败不得留下孤立档案/实例。
7. 六预置档案分别配备经过审查的场景提示词和设计 §5.3 的最小只读 Tool；库存/生产风险/采购/排程/质量/供应商各自有真实只读服务与业务权限/数据范围边界。写 Tool 默认均不启用；无已授权业务数据给出真实空态、不由 LLM 填造事实。知识库不自动建空库、也不一键绑定全租户知识；管理员在 `/agents` 按场景显式选择允许的知识库与 search_knowledge。
8. 没有 chat 连接/密钥时六份档案仍已创建但显示 not_ready 和配置指引；知识检索需要管理员选库、可用 embed 与已索引文档，不得因为预置档案存在就展示假知识答案。
9. “打开并发送 KU-Ask”在模板总开关、实例单项开关均开启且档案/chat/使用权就绪时打开既有抽屉并发送一次样例问题；无档案使用权时显示 403，不降级；未绑定、档案停用/删除时状态 not_ready，不发送。
10. “查看场景”只跳服务端白名单路由；目标不存在或无权限时禁用；复制/定制项也受相同白名单约束。
11. 接口不返回 system prompt、授权名单、密钥、cipher 或 tenant_id；既无使用权也无 `kuaiai:agent:read` 的用户不泄露真实档案 ID；有管理读权但无使用权者只能看绑定不能运行。

### Rules and Constraints

Tenant isolation:

- 所有聚合以 `get_current_tenant` 为唯一租户来源；安装/升级预置传本租户 tenant_id，新增档案与场景实例同租户且幂等，不写 grant。每次绑定、克隆、读取实例按 tenant_id 过滤；发送时复核档案启用和当前用户使用权，跨租户/软删档案一律按不存在处理。

Security and masking:

- 星AI 根菜单现要求 `kuaiai:entry:read`，core stats/audit 也要求该码；七个新菜单/页面均同时要求 `kuaiai:entry:read` 与本页 display，后端运营读取接口采用相同组合，避免菜单可见却加载 403。单靠新 display 不足以访问 trust/insights 的 core stats/audit。对话另需现有 `kuaiai:act:execute`，业务跳转继续检查目标页面权限。
- 权限矩阵（181 统一注册，后续单元按行落地接口鉴权；`+` 表示同时具备）：

| 页面/动作 | 菜单与读取 API | 写/导出附加权限 |
| --- | --- | --- |
| hub | `entry:read` + `hub:display` | 无 |
| agent-library | `entry:read` + `library:display` | 绑定/定制/启停另需 `library:manage`；绑定/克隆还需 `agent:read`，克隆另需 `agent:create`；自动首问另需 `act:execute` 和档案使用权 |
| pulse | `entry:read` + `pulse:display` | 各 detector 另需领域读权限 |
| corpus | `entry:read` + `corpus:display` | FAQ/种子 `corpus:create`；批量重试 `corpus:update`；删除 `corpus:delete`；JSONL `corpus:export`；跳 `/knowledge` 另需 `knowledge:display` |
| trust | `entry:read` + `trust:display` | 既有 core audit 继续 `entry:read` |
| insights | `entry:read` + `insights:display` | 既有 core stats/audit 继续 `entry:read` |
| settings | `entry:read` + `settings:display` | PUT 另需 `settings:update`；连接器选项读取经 settings facade 鉴权 |

- 表内 `entry:read` 等省略前缀 `kuaiai:`；两端 manifest `permissions` 必须注册完整码，菜单节点使用对应 display 且根菜单维持 entry；后端读取/写入依矩阵复核，不仅依赖菜单隐藏。安装与升级调用既有权限同步服务写入 `core_permissions`，验证新增权限出现在角色权限页；不得仅改前端权限列表。
- 授权策略是本单元新增规则，不将“知识运营人员”“普通员工”臆称现有预设角色 code：租户管理员的预设角色获 entry、七项 display、library:manage、corpus 四项操作 + settings:update（克隆档案仍需现有 agent:read/create）；知识运营岗位若有对应预设角色，仅授 entry、corpus display/create/update/delete/export；普通员工岗位若有对应预设角色，仅授 entry、hub/library/pulse display。实施时先核对现有预设角色 code 与授权入口，未配置对应预设角色的岗位由租户管理员显式创建/授权，不能把这些权限加进所有角色的基线或按模糊前缀批量放权；已有自定义/存量角色保持原授权，升级只注册权限不自动放权，由管理员逐个核对授予。这只是页面/API 权限：六份系统预置 Agent 不在安装/升级中写任何使用名单，使用权完全由管理员在既有 `/agents` 按 ROLE/USER 显式配置，且不等同于任何 display 权限；186 负责存量租户升级验收。
- `disabled_reason` 只能返回用户可理解的配置/权限原因，不含内部路径与异常栈。

Audit and lineage:

- 页面读取不新增业务审计；实际对话继续由现有 AI 审计链记录。场景 key 进入上下文但不得替代 route/capability 审计。

AI/rule-engine rules:

- 首期业务 Tool 逐项见设计 §5.3：`query_inventory_balance`、`query_delivery_risk`、`query_purchase_followup`、`query_published_schedule`、`query_quality_anomalies`、`query_supplier_orders` 为新增只读 Tool；计划员还复用现有 `query_workorder`/`list_workorder_tasks`。闭集、manifest ai_tools、Tool 注册 guard 同步扩展；禁止默认勾选 `submit_production_feedback`/`update_workorder_status`。Tool handler 使用有界结果/租户与当前用户业务读权限/数据范围，底层 service 没有 current_user 入参时适配层不能直接透出全租户数据。没有业务事实不得猜答。管理员须明确选择知识库后才将 search_knowledge 用于相应档案。
- 自动首问请求使用既有 ChatCompletionRequest；`capability_mode` 只允许 ask/query/guide。现有 chat_service 仅按 `context.agent_id` 组装档案，不消费 `extra.agent_key`；本单元新增内部场景守卫：携带 agent_key 时服务端核验同租户模板/实例、总/单项开关、绑定 agent_id 一致、档案使用权和 chat 可用后再沿原执行链发送；缺少 agent_key 的普通 `/chat` 不受场景总开关影响。不改请求/响应外层，不信任客户端业务路由。

Database rules:

- 六个出厂模板在后端代码定义（首期键集稳定，但实例可扩），新增一个 Tortoise 租户场景实例/档案映射表 `apps_kuaiai_agent_scenes`（`tenant_id,instance_key,template_key,origin(system_seed|copy),agent_profile_id?,overrides JSON,enabled,deleted_at` 及审计字段），`(tenant_id,instance_key)` 非软删唯一、`(tenant_id,template_key)` 查询索引；复用已有 Agent 档案和授权表，不新建 Agent 引擎。安装时同事务真实建六份 `status=停用`、`grant_mode=ROLE`、`default_model_id=null`、空授权名单的档案及绑定六行，升级/扫描幂等补缺；系统档案默认取模板中文名，重名时追加 `（预置）` 及必要的递增序号；不根据档案同名猜种子身份，不覆盖用户修改或恢复手动删除的实例。安装失败显式未就绪并支持安全重试；不允许仅虚拟六模板卡冒充已建档。
- 六个模板总开关仍读现有 `SiteSetting.settings.integrations.kuaiai.agent_switches`（185 写入），缺失 key 默认 true；实例默认 enabled=true，复制项沿用 `template_key` 的总开关。最终可发送条件是总开关 ∧ 实例 enabled ∧ 有可用档案/使用权 ∧ chat 就绪。185 显式六键 map 仅覆盖总开关，不改实例 enabled；任一关闭仍展示卡片但禁发送。

## 2. Plan

### Implementation Approach

1. 后端新增 operations schema/service/router；hub 聚合 `AiRuntimeConfig.public_status`、`AiStatsService`、知识文档数和 Pulse 可用状态，不复制统计 SQL。
2. 场景 service 以稳定模板 key 定义后端展示元数据、专用提示词和只读 Tool 清单；新增 `seed_kuaiai_agent_scenes_on_lifecycle(tenant_id)`（沿用 `install_application` 中 `kuaireport` 的 `seed_system_reports_on_lifecycle` 先例，`app_code == "kuaiai"` 时调用，并在 enable 与已安装扫描/同步路径重复执行），安装时以同租户事务预置六个停用、空授权、`grant_mode=ROLE` 的档案+六绑定实例，升级/同步只补缺，保留自定义/改绑/授权/停用/软删痕迹。生命周期无用户上下文，种子行审计字段写 `created_by=0`、`created_by_name="系统"`，不冒名管理员。安装或启用应用都不写 grant、不启用档案，管理员后续在 `/agents` 手工配置名单并启用。安装标记与预置事务不是同一连接，`install`/`enable` 预置失败须向调用方失败且可重试；扫描路径被现有异常策略捕获时，也必须由 `provisioning.complete=false` 显示未就绪，不能假报已就绪。
3. 按设计 §5.3 扩展六种领域只读 Tool 并用真实 MES service/业务权限与数据范围约束；注册表和 manifest 同步，禁止预设写工具。无聊天连接、无业务授权或知识语料时显示相应待配置/空态，不生成虚假业务答案。
4. 场景 service 合并租户实例覆盖字段；读取目标路由/资源白名单、模板总开关、实例 enabled、绑定档案使用权与 chat 配置，返回真实运行状态。管理入口绑定已有档案/按需复制时校验租户、管理员权限与字段白名单；克隆复用 `agent_service.create_profile` 的停用建档规则，源档案有 default_model_id 时另复用现有本租户 chat 模型校验并在事务内复制（当前 create_profile 忽略该字段），授权名单不复制；新档案仍通过原 `/agents` 授权/启用。
5. 前端先建立共享 header/metric/card token，再实现 hub 和由后端数据驱动的 agent-library；管理员能管理场景绑定、定制、单项开关和按需复制；共享件只留在 kuaiai 应用内。
6. 助手按钮复用 `AiContext`/现有 drawer；加入防双击与一次发送标记。

### Transaction Boundaries

- 两个 GET 为只读聚合；安装/升级预置六个停用、空授权档案+六实例在同一 Tortoise 事务提交，不写 grant、不启用档案，失败不能留半数就绪。应用安装标记由独立 DB 连接提交，预置故障必须报告未就绪、可幂等重试，不能声称整个安装原子。绑定/定制/开关写入只更新本租户实例；按需克隆新停用档案与复制场景实例在同一 Tortoise 事务提交，失败全回滚且不复制 grants。打开助手后的会话与消息事务沿用现有 chat service。

### Risks

- hub 同时依赖多个统计源；必须局部降级，不能一个源失败整页 500。
- 菜单分组会改排序但不能改已有 path；locale 缺键会显示原始 key。
- 自动发送可能因重复点击产生两条消息；按钮 pending 时禁用。
- 场景路由可能随业务 manifest 变化；响应每次根据已注册路由与权限计算。模板扩充不得让前端按六项写死；复制/改绑中的租户/档案授权竞态要失败关闭，不得回退其他档案。
