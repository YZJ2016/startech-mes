## 1. Spec

### Capability

- Name: READY 专库启动补齐 + 登录 Flyway 版本门禁
- Module: `startech-mes-basic/backend/ktg-system`（ApplicationRunner / 补齐服务，复用 77 的 `TenantFlywayMigrator`）；`ktg-framework`（`TenantLoginGuard` / `SysLoginService` 登录前版本校验）
- Priority: P0
- Related requirement/design documents:
  - 设计：`docs/03.design/05.mes-flyway-integration.md`（FLY5/FLY6/FLY7、§2 启动步骤 3–5、登录段）
  - 缺口：`docs/02.requirements/02.mes-multi-tenant-gaps.md`（I6、I10、D9）
  - 总控：`docs/04.specs/75.mes-flyway-program.md`
  - 上一单元：`docs/04.specs/77.mes-flyway-dedicated-provision.md`
  - 下一单元：无（本切线收口）。新 tenant DDL 自此只进 `db/migration`

### Business Goal

应用启动时，在主库 Flyway **成功之后**，对已 `READY` 的 `DATABASE` 租户用一次性 JDBC 补跑尚未应用的 tenant 增量：并行 N≤2，失败将该租户改为 `FAILED` 且 **不** 让主库进程退出。登录不跑 DDL；专库 tenant 版本落后于主库已应用的 tenant 版本则拒登录，文案仍「用户名或密码错误」。

### Scope

In scope:

- `ApplicationRunner`（或等价，须 `@Order` / `DependsOn` 保证发生在 Boot Flyway migrate 之后）：查询 `isolation_level=DATABASE` 且 `provision_status=READY`；并行 N≤2 调 `TenantFlywayMigrator`；**不** `ensurePool`
- 缺 `TENANT_JDBC_CIPHER_KEY`：主库 migrate 已完成的前提下，跳过专库补齐并将这些租户标失败（设计 §7）；不得用「主库未对齐」掩饰密钥问题
- 补齐失败：`FAILED`，不建池，不抛到进程，不回落主库
- 登录：`DATABASE` 且非 `READY` 仍拒（41 已有）。本单元增加：专库 `flyway_schema_history` 中 **tenant location 版本** 的当前值落后于主库 history 中同一批 tenant 版本 → 拒登录。比较范围 **不含** `master/` 脚本
- 一次性 JDBC 读 history / migrate；lookup key 仍 `TENANT_{id}`；日志不打印 URL/口令
- 未 baseline 的 READY 专库：补齐会因快照 `CREATE` 撞表失败 → `FAILED`（与设计 4.3 一致）

Out of scope:

- 登录时补跑 migrate（FLY7 明确禁止）
- 改主库 locations、改快照、改开通 HTTP（76/77）
- 改 Vue2/Vue3 登录页文案（后端仍 D9）
- 启动 eager 建全部专池
- 把失败租户自动回滚为 READY

### Acceptance Criteria

- 主库 migrate 失败：进程起不来（76）；本单元测试不得把专库失败变成进程失败
- 三个 READY 专库启动补齐：同时最多 2 个 migrate（信号量可与开通共用或独立，但上限 2）
- 无 READY 专库业务访问时，补齐结束后专池数仍为 0
- 故意让一个专库 migrate 失败：主库进程存活；该行 `FAILED`；主库无该 `tenant_id` 业务写入；登录该厂走 D9
- 专库 history 落后：登录拒绝，D9，不回落主库，不在登录线程跑 DDL
- 专库已追上：既有 READY + ping 成功路径仍可登录（不改 `tenantCode` 必填）
- `mvn -pl ktg-system,ktg-framework -am test`（第 4 节；撰写时 **未执行**）

### Rules and Constraints

Tenant isolation:

- 补齐与登录校验都不得把 DATABASE 会话打到主库业务表
- ROW/平台不进补齐循环

Security and masking:

- 登录失败统一 D9，不返回「schema 落后」
- 读 `flyway_schema_history` 的异常同样剥连接串，对外仍 D9

Audit and lineage:

- `FAILED` 可经 41 的「创建 schema/表」重试（77 的全链 migrate 对已有部分表可能失败；重试语义保持 41：可改口令后重试，不删登记）。本单元不新造第三套开通 API

AI/rule-engine rules:

- 不涉及

Database rules:

- 比较「tenant 版本」= classpath `db/migration/tenant/` 中的 versioned 号与两边 history 已 applied 的交集/最大已应用 tenant 版本
- 禁止 `outOfOrder`；禁止登录路径 `Flyway.migrate()`

## 2. Plan

### Implementation Approach

1. 确认 77 的 `TenantFlywayMigrator` 可对任意 JDBC 跑 tenant location。
2. 新增启动补齐组件：主库 Flyway 之后执行；N≤2；捕获异常 → `updateProvisionStatus(FAILED)`。
3. 新增版本读取：一次性连接查询 `flyway_schema_history` 成功 applied 的 version；过滤为 tenant 目录中存在的版本；取最大。
4. `TenantLoginGuard` 或 `SysLoginService` 在既有 READY 检查之后：DATABASE 再比主库 vs 专库 tenant 最大版本；落后则抛既有 `TenantException`（登录层已映射 D9）。
5. 测试：并行上限；失败不杀进程；落后拒登录且无 migrate 调用；池计数为 0。

### Affected Modules

- `ktg-system`：补齐 Runner/Service；可能扩展 `TenantFlywayMigrator`（读当前版本）
- `ktg-system` `SysTenantMapper`：列出 READY DATABASE（若无则加查询，不改对外 HTTP）
- `ktg-framework`：`TenantLoginGuard`、`SysLoginService`（不改 `POST /login` 字段）
- 测试：`ktg-system` / `ktg-framework` 新建或扩展 `TenantLoginGuardTest`、`SysLoginServiceTenantTest`

### Public Contracts

- `POST /login` 仍必填 `tenantCode`；失败 `msg` 仍为「用户名或密码错误」
- 无新平台 API

### Persistence Changes

- 专库可能新写入 `flyway_schema_history` 行（补齐成功）
- `sys_tenant.provision_status` 可能 READY→FAILED
- 无新业务表

### Transaction Boundaries

- 每个专库补齐独立连接；更新 `provision_status` 走主库事务，与专库 DDL 不是同一事务（DDL 已提交）

### Risks

- Runner 抢在 Flyway 完成前执行 → 用错主库租户版本；必须排在 Boot Flyway 之后
- 用全部 history 版本（含 master）去比专库 → 专库永远落后；必须过滤 tenant location
- 登录时误调 `migrate()` 把首请求打成 DDL

### Verification Strategy

- 单测 mock JDBC / in-memory history 表
- 并行用 41 同款「三路最多两路」手法
- 未连现网则第 4 节声明
