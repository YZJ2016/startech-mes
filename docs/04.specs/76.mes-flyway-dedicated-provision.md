### Business Goal

平台「创建 schema/表」对空专库不再从 `sql/`/`tenant-sql/` 拼 `CREATE` + 增量清单，改为一次性 JDBC 跑 Flyway `tenant/` 全链（从快照到最新）。失败关闭语义与 41 相同：登记保留、`FAILED`、可重试、不写主库业务行、不克隆 `sys_menu`、不建专池。

### Scope

In scope:

- 新建 `ktg-system` 专库 migrator（名称随现有风格，如 `TenantFlywayMigrator`）：解密后的 JDBC → 一次性连接 → `locations = classpath:db/migration/tenant` → `migrate()`；**不**注册 `DynamicDataSource` 专池
- `TenantSchemaProvisioner.provision`：预算 + N≤2 + `CREATE DATABASE IF NOT EXISTS` 保留；将 `TenantWarehouseSql.dedicatedCreates()` / `incrementalStatements()` 替换为一次 tenant Flyway migrate；其后仍 `copyRoleTemplates` + ping + `READY`
- `assertNoGlobalCreates`：改为扫 `tenant/` 脚本文本（可复用 75 的扫描测试）；开通路径不再执行仓库 dump 抽取
- 空专库：无 history → 从快照版本跑到最新；不 baseline。开通 **只** 走这一次 `migrate()`，禁止再执行 `backend/sql/` 或 `TenantWarehouseSql`（完整顺序见 74「开通 schema 只跑一套 DDL」）
- HTTP 仍 `POST /platform/tenant/{id}/schema`；并行第三路仍 429；无 `CREATE DATABASE` 权限仍 `FAILED`、登记保留
- 开通成功后专库无 `sys_menu` / `sys_tenant` / `QRTZ_*` 表（或至少无这些 CREATE）
- 删除或停止开通路径对 `TenantWarehouseSql` / `TenantCreateTableSql` 的调用；若无其它引用则删除死代码（仅本切线引入的死引用，不扫无关类）

Out of scope:

- 主库 starter / 快照文件内容（75）
- READY 专库启动补齐、登录版本门禁（77）
- 改 I5 预算公式、改角色模板来源、改 ping
- 往 `tenant/` 追加快照之后的业务增量（74：77 完成前禁止）
- 改 Vue；改登录契约；eager 建专池

### Acceptance Criteria

- `TenantSchemaProvisionerTest`（及 migrator 单测）覆盖：空库 migrate 后 `tenantTables()` 均存在；无 `sys_menu` CREATE；失败 → `FAILED`、不删登记
- 并行 N≤2 既有用例仍成立（第三路 429，不得因改 Flyway 变成静默打满连接）
- ping 与 migrate 均不导致启动期专池数 > 0
- 不调用 `TenantWarehouseSql.dedicatedCreates` / `incrementalStatements` 作为开通迁表
- 占位 JDBC，禁止真实主机写入仓库
- `mvn -pl ktg-system -am test` 实际跑过（第 4 节；撰写时 **未执行**）

### Rules and Constraints

Tenant isolation:

- 专库 SQL 仍带 `tenant_id`（快照 DDL 已含列）；拦截器不在本单元改
- 禁止把该厂数据 INSERT 进主库

Security and masking:

- migrator 日志不得打印 URL/口令；异常剥连接串
- 密钥仍仅环境变量

Audit and lineage:

- 开通分步与 41 相同；只换迁表载体
- 不改已发布 75 快照字节

AI/rule-engine rules:

- 空库全链含 AI 租户表；不在本单元改 `ktg-ai` 业务

Database rules:

- 只用编程 API，避免第二套 Flyway 自动配置打专库
- `baselineOnMigrate` 保持 false：空库必须跑快照，不能被误钉基线跳过建表

## 2. Plan

### Implementation Approach

1. 确认 75 已合并：快照在 classpath、starter 已传到 `ktg-system`。
2. 实现 `TenantFlywayMigrator.migrateTenant(url, user, password)`：`Flyway.configure().dataSource(...).locations("classpath:db/migration/tenant").baselineOnMigrate(false).validateOnMigrate(true).load().migrate()`。
3. `provision` 在 CREATE DATABASE 成功后调 migrator，去掉 warehouse 两段 `executeStatements`。
4. 扩展既有 `TenantSchemaProvisionerTest`：mock/夹具改为断言 Flyway 被调用或空库表来自快照；保留 429 / FAILED / 无 `sys_menu`。
5. 开通路径不再引用 `TenantWarehouseSql` 则删除该类及其 `tenant-sql/` 资源（若仅被开通使用）。

### Affected Modules

- `ktg-system/.../TenantSchemaProvisioner.java`
- 新建 `ktg-system/.../TenantFlywayMigrator.java`（包名跟 `tenant` 包）
- `TenantSchemaProvisionerTest`、新建 migrator 测试
- 可能删除：`TenantWarehouseSql.java`、`TenantCreateTableSql.java`、`src/main/resources/tenant-sql/`、`TenantWarehouseSqlTest`
- 不改 `TenantDataSourceRouter` 懒加载语义

### Public Contracts

- `POST /platform/tenant/{id}/schema` 不变
- `provision_status` 枚举不变

### Persistence Changes

- 新开专库出现 `flyway_schema_history` + 快照及后续 tenant 版本
- 无新的业务列变更

### Transaction Boundaries

- 与 41 相同：开通失败不回滚 `sys_tenant` 行；DDL 在专库连接上执行

### Risks

- Flyway 与旧 warehouse 抽表结果不一致 → 空库缺列或多种表；用 `tenantTables()` 存在性验收，不以「语句条数」验收
- 误把 master location 配进专库 → 专库出现 `sys_menu`
- 误开 `baselineOnMigrate` → 空库跳过快照

### Verification Strategy

- 优先复用 41 的 provisioner 测试结构，迁表断言改为表存在 / history 行
- H2 对 MySQL DDL 可能不够；若跳过真实 MySQL，第 4 节写明，并用 mock 证明不再走 warehouse
