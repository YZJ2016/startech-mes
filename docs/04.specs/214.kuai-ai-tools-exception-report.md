# KU-AI 写 Tool：异常上报（HITL）

从 `docs/01.temlplates/01.development_unit_template.md` 复制，保留五章。状态：已完成。

## 1. Spec

### Capability

- Name: 新增三个写 Tool：`create_material_shortage_exception`、`create_delivery_delay_exception`、`create_quality_exception`，全部走确认闸。
- Module: `riveredge-backend/src/apps/kuaiai/services`（tools 适配层）、manifest `ai_tools`。
- Priority: P2（S10 异常上报；首个新增写 Tool 单元）。
- Related requirement/design documents: 需求 25 SC-D3、SC-D7、SC-D15；设计 26 §4、§6；前置 spec 189、190、192、193、194（确认闸全部就绪后才可开工）。

### Business Goal

班组长/计划员对助手说“WO-1023 缺料要停线了”，AI 收集关键字段后弹确认卡，用户确认即生成缺料异常单，进入异常处理流程。

### Scope

In scope（三种异常写权限各异，SC-D7 拆三个 Tool）：

| Tool | 参数 | 底层 service | 权限码 |
| --- | --- | --- | --- |
| `create_material_shortage_exception` | `work_order_id`（必填）、`material_ids[]`、`description?` | 生产执行异常 service 的缺料异常创建方法（T1 核对） | `kuaizhizao:production-execution-material-shortage-exceptions:create` |
| `create_delivery_delay_exception` | `work_order_id`（必填）、`reason?`、`expected_date?` | 同上系列的延期异常创建方法（T1 核对） | `kuaizhizao:production-execution-delivery-delay-exceptions:create` |
| `create_quality_exception` | `work_order_id?`、`material_id?`、`description`（必填）、`severity?`（闭集） | 同上系列的质量异常创建方法（T1 核对） | `kuaizhizao:production-execution-quality-exceptions:create` |

- 全部 `kind=write`，必须经确认闸：确认卡展示将写入的字段摘要（工单号、物料、异常类型、说明）；H4=a 只支持确认/拒绝。
- 确认执行后返回创建的异常单号与状态；幂等：确认闸保证同一 interrupt 只执行一次（spec 193 已有约束，本单元复核）。
- 关联单（工单等）在构造参数时先按只读 Tool 复核存在性与数据范围。

Out of scope:

- 异常的处理、关闭、升级（本单元只创建）。
- 新建其他类型异常（设备故障等按需另立）。

### Acceptance Criteria

1. 三个 Tool 均经确认闸；未确认不产生任何业务数据。
2. 确认后创建成功返回异常单号；业务校验失败返回该 service 的固定错误文案（不透出内部异常）。
3. 参数必填项缺失时 AI 侧可追问用户；Tool 层校验同样拒绝空必填。
4. 三个 Tool 登记于 manifest（`label`、`kind=write`），确认卡字段摘要齐全。

### Rules and Constraints

Tenant isolation:

- 传 `ctx.tenant_id`。

Security and masking:

- 确认卡 `args_summary` 展示将写入的全部参数（截断标量集）；审计 route 仅记首个 `*_id`/`code` 业务键、不落完整参数值——参数完整性由异常行业务行（全字段 + `created_by`）保证（写操作审计要求高于读）。

Audit and lineage:

- 沿用 Tool 级审计 + 确认闸审计（spec 193）；`route` 业务键记录工单与异常类型。

AI/rule-engine rules:

- LLM 不得编造 severity/物料；拿不准的字段追问用户而非默认。

Database rules:

- 无表结构变更；沿用异常单现有表。

### 场景模板（Y3=a、Y6=a）

本单元交付时同步登记场景模板 `exception-report`（异常上报助手）：预置档案 `enabled_tools` 为本单元三个写 Tool——**本场景破例含写 Tool**（Y6=a），理由：异常上报场景的全部价值就是写 Tool，且确认闸保证每次执行逐人确认（spec 193）；档案仍停用 + 空授权（Y4=a）。模板 key 即能力矩阵场景卡，默认绑定同 key 预置实例（spec 191）。system_prompt 只引用本单元 Tool，插画按 spec 201 T2 约定。

### T1 与 spec §1 表的冲突（以代码为准）

- 缺料：spec §1 写 `material_ids[]`/`description?`——service 为**单** `material_id` + 必填 `shortage_quantity`，无 `description` 字段（语义落 `remarks`）；Tool 参数按 service 收敛，多物料需多轮确认各建一单。
- 延期：spec §1 写 `reason?`——service `delay_reason` **必填**；spec 的 `expected_date` 在 `DeliveryDelayReportCreate`/`report_delivery_delay` 无对应字段，**不映射**（见 Known gaps）。
- 质量：spec §1 写 `description`——即 `problem_description`；`severity` 闭集 minor/major/critical 与 service `_normalize_severity`（:154）一致。

### 机制复核（不写代码，复用既有）

- 确认闸：`manifest kind=write` ∩ 档案 enabled_tools → `agent_assembler` 挂 `HumanInTheLoopMiddleware`（spec 193），本单元只做 Tool 适配；登记包见交付报告。
- 幂等：确认闸 CAS 认领 + token 单次 resume（spec 193 B-C1），本单元 e2e `test_resume_single_use_no_replay` 复核；service 层同工单/物料未处理去重作第二道兜底。
- 关联单复核：工单 `chat_tools._work_order_in_scope`（`kuaizhizao:work-order`）；物料 `scene_tools._scoped_row_ids` 套 `master-data:material`（master_data manifest data_scope_key :299）。
- 审计 route：`_audit_tool_call` 自动取首个 `*_id`/`code` 业务键参数（`work_order_id`/`material_id`），不落完整参数值，Tool 名编码异常类型；参数完整性由异常行业务行（全字段 + `created_by`）保证。确认卡 `args_summary` 由 `sse_adapter._interrupt_actions` 自动渲染标量参数全集（截断），前端无需定制。
- e2e 确认闸链路审计结论：`kind=write`→interrupt 无绕过路径、同 token 幂等 CAS、reject 无业务数据。
