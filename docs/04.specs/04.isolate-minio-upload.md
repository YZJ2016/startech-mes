# Development Unit Template

Use this template before each implementation unit.

## 1. Spec

### Capability

- Name: 隔离 Minio 上传分叉，恢复平台 `FileUploadUtils` 可替换性
- Module: `ktg-common` / `ktg-admin` → `ktg-mes`（或明确改回本地盘）
- Priority: P0
- Related requirement/design documents:
  - `docs/04.specs/00.backend-extract-program.md`
  - 调查：`FileUploadUtils.java` MES 约 418 行 vs 若依约 239 行，已接入 `MinioConfig` / `MinioUtil`

### Business Goal

文件上传在换壳后行为可预期：要么对象存储能力作为 MES 模块保留，平台恢复若依本地上传；要么产品确认全面改回本地盘。禁止继续把 Minio 写在即将被替换的 `ktg-common` 共享类里。

默认建议：**保留 Minio 行为**（现网 `FileUploadUtils` 已走对象存储），把配置与上传实现迁入 `ktg-mes`，业务调用改为 MES 上传门面；`ktg-common` 的 `FileUploadUtils` 回到接近若依的本地盘实现，供系统头像等平台功能使用。

### Scope

In scope:

- 迁出 `MinioConfig`、`MinioUtil`、`TaleUtils`、`FileCombine`（确认引用后）
- 迁出或改写 `UploadFilePathConfig`（`/template/**`、`/profile/**`、`/files/**` 磁盘映射）
- 提供 MES 侧上传门面，供 `WmBarcodeServiceImpl`、`ProWorkorderServiceImpl` 使用
- 评估 `SysProfileController`、`CommonController` 走平台本地上传还是 MES 门面（头像/通用上传与车间附件可能不同，需在任务中写死）
- `minio` 依赖改挂 `ktg-mes`；配置键仍用现有 `minio:` 前缀，**值不写入 spec**
- 从 common 的 `FileUploadUtils` 删除 Minio 分支

Out of scope:

- 更换对象存储供应商
- 把真实 AccessKey 写入仓库或文档
- Security 静态资源放行（`08`）

### Acceptance Criteria

- `ktg-common` 的 `FileUploadUtils` 不再 import Minio 类型
- `MinioConfig` / `MinioUtil` 仅存在于 `ktg-mes`（若选择保留 Minio）
- 条码图、工单附件上传路径行为与迁前一致（同一 bucket/前缀策略，不在文档中写具体 endpoint）
- `ktg-admin` 通用上传若仍给管理端用，行为在 PR 中写明「本地盘」或「MES 门面」二选一
- compile 通过；无密钥进入 diff

### Rules and Constraints

Tenant isolation:

- 不按租户分 bucket，保持现有单 bucket 配置

Security and masking:

- Minio 的 url / accessKey / secretKey / bucket 只允许环境变量或已有本地 yml，禁止复制到 spec、日志、新示例
- 日志不得打印对象存储凭据或完整预签名 URL 中的签名段

Audit and lineage:

- 不改附件业务表结构（`sys_attachment` 属于 `05`）

AI/rule-engine rules:

- 不涉及

Database rules:

- 本单元无表变更

## 2. Plan

### Implementation Approach

1. 画出调用图：`FileUploadUtils` ← `CommonController`、`SysProfileController`、`WmBarcodeServiceImpl`、`ProWorkorderServiceImpl`、`FileUtils`
2. 新建 `com.ktg.mes.file`（名称可调整）承载 Minio 配置与 upload API
3. MES 两处改为走新门面
4. 平台两处（profile/common）在 PR 中选定策略并改代码
5. 还原 common `FileUploadUtils` 为本地盘实现（可对照 `RuoYi-Vue` 的同名类思路，但仍编译在 Java 8 / 当前工程，不引入 Boot 4 API）
6. `UploadFilePathConfig`：若 MES 仍需 `/files/**` 映射，迁到 `ktg-mes` 配置类

### Affected Modules

- `ktg-common`：去 Minio 化的 `FileUploadUtils`；删除 Minio 类
- `ktg-mes`：上传门面；条码/工单改调用
- `ktg-admin`：`UploadFilePathConfig`、`CommonController` / `SysProfileController` 按选定策略修改
- `ktg-common/pom.xml`：移除 `minio`（无引用后）

### Public Contracts

- 现有上传 HTTP（如 `/common/upload`）路径尽量不变；若必须分 MES 上传接口，须在本单元 Public Contracts 落地时补一条并保持旧路径转发
- 配置前缀 `minio:` 保持，便于现网配置文件继续工作

### Persistence Changes

- 无表结构变化；对象存储中的对象键规则不主动改

### Transaction Boundaries

- 上传 IO 不纳入业务单据大事务（保持现状）

### Risks

- 平台头像上传与车间附件混用同一 `FileUploadUtils`，还原本地盘后头像与附件分裂，需在 T1 写死
- 误把现网 Minio 地址写入文档
- `TaleUtils.getUplodFilePath()` 拼写与绝对路径假设在 Windows/Linux 不一致

### Verification Strategy

- `rg MinioUtil|MinioConfig backend --glob *.java` 仅 `ktg-mes`
- `rg "io.minio" backend/ktg-common` 无匹配
- Maven compile
- 有环境时：打一次条码生成与一次通用上传，确认存储位置符合选定策略（不记录真实 URL）
