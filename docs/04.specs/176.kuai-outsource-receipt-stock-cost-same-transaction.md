# 快格委外收货 — 库存成本与确认同一事务

本单元只收口 **KR-ORP1**。修法已定：库存和成本放进现有确认事务，应付在提交后同步等待。

- 缺口：`docs/02.requirements/23.kuai-outsource-receipt-posting-gap.md`（**KR-ORP1**）
- 关系：`docs/04.specs/142.kuai-finance-inventory-same-fate.md` 把委外收货收成提交后的 detached task，失败以 error 日志为可见，并把「严格同事务」留为未决（Known gaps「委外入库 detached task」）。本单元只关闭委外收货这一条，采用采购入库 `confirm_receipt` 的拆法。不推翻 142 对其它单据的规定，也不实现 142 所说的持久化异步任务或补偿框架。
- 检验门禁：`docs/04.specs/171.kuai-outsource-receipt-iqc.md` 的必检 / 免检分叉保持。该 spec 事务边界里「免检创建……提交后再异步过账」已改为一句：库存、成本与应付的时序以本文件为准。171 的实现途径仍写「提交后 `_schedule_stock_for_outsource_receipt`」，T4 仍写「提交后异步过账」；这两处是当时的过账叙述，过账时序以本单元为准。171 的验收标准仍是「创建即完成并过账」，本轮不改那些验收句。
- 代码核对：`kuaigeyun-mes/riveredge-backend` 的 `outsource_material_receipt_service.py`。采购入库对照是 `warehouse_service.py` 的 `confirm_receipt` / `_confirm_receipt_posting`。

## 1. Spec

### Capability

- Name: 委外收货库存成本与确认同一事务，应付提交后同步失败可见
- Module: `kuaigeyun-mes/riveredge-backend`：`OutsourceMaterialReceiptService`
- Priority: P0（KR-ORP1）
- Related requirement/design documents:
  - 缺口：`docs/02.requirements/23.kuai-outsource-receipt-posting-gap.md`（**KR-ORP1**）
  - 上游未决：`docs/04.specs/142.kuai-finance-inventory-same-fate.md` Known gaps「委外入库 detached task」
  - 检验分叉：`docs/04.specs/171.kuai-outsource-receipt-iqc.md`

### Business Goal

免检创建或确认接口返回前，库存与成本已经落账。这两步失败时，收货单不能停在 `completed`，委外工单数量一起回滚。应付在事务提交后同步生成，失败时调用方收到 `BusinessLogicError`；这时收货单可以仍是 `completed`。

### Scope

In scope:

- `create_material_receipt` 的免检分支（`requires_iqc` 为假）：在现有 `in_transaction` 内，状态写成 `completed`、`_apply_outsource_receipt_quantities` 之后，调用 `InventoryService.increase_stock` 与 `InventoryCostService.on_outsource_receipt_confirmed`。
- `complete_material_receipt`：在现有 `in_transaction` 内，状态写成 `completed` 并回写工单数量之后，调用同样两个函数。
- 上述事务退出之后，`await` `_maybe_auto_create_payable_for_outsource_receipt`。失败包装成 `BusinessLogicError` 抛给接口。
- 去掉 `asyncio.create_task` 调度：`_schedule_outsource_receipt_followups`、`_schedule_stock_for_outsource_receipt`、`_schedule_cost_for_outsource_receipt`、`_schedule_auto_payable_for_outsource_receipt` 不再作为过账路径。调用方消失后删除这四个方法。
- `tests/apps/kuaizhizao/services/test_outsource_receipt_iqc_gate.py` 里对三个 `_schedule_*` 的调用断言，改成与上述时序一致，并补失败用例。
- 成本钩子与应付函数上引用「spec 142：detached task」的注释，改成与本时序一致。钩子失败仍上抛，不改成吞掉。

Out of scope:

- 不改委外收货 URL、method、认证头、响应外层结构。`POST /outsource-material-receipts` 与 `POST /outsource-material-receipts/{receipt_id}/complete` 的响应模型仍是 `OutsourceMaterialReceiptResponse`。
- 不改前端契约。入库确认 `inbound/index.tsx` 的 `submitSimpleConfirmPreview` 已用 `formatApiErrorDetail` 展示 `detail.message`；免检创建 `InboundOutsourcePullEntryPage.tsx` 的提交 `catch` 已读 `detail.message`。`formatApiErrorDetail` 能读出 `{message, trace_id}`。接口把 `BusinessLogicError` 转成 400 后，这两处会展示业务错误。本单元不改前端。
- 不引入持久化异步任务或补偿框架。
- 不改 `PayableService.create_payable` 的事务边界。
- 不改 142 对其它单据（销售出库、采购入库、成品入库、金蝶推送等）的规定。
- 不改 spec 171 的检验判定、必检停在 `draft`、确认前断言、列表不把 draft 改成 completed。
- 不改 `complete_material_receipt` 在 `status == "completed"` 时直接返回的早退。应付失败之后的再次生成不在本单元。
- 不改 `warehouse_wo_outsource_pull_service` 的逐单循环。

### Acceptance Criteria

1. 免检创建（`test_exempt_receipt_completes_and_posts` 覆盖的 source：`material` 且 eff `none`，以及 `stage_disabled` / `module_disabled`）与确认成功（合格检验或已处理让步）返回前：`increase_stock` 与 `on_outsource_receipt_confirmed` 已在该次 `in_transaction` 内执行完成。有 `product_id` 时才做这两步；没有 `product_id` 时与今天一样不做库存和成本。
2. `increase_stock` 或 `on_outsource_receipt_confirmed` 抛错时，服务方法把异常抛出，不返回成功的 `completed` 响应，也不调用应付生成。收货状态与委外工单数量留在该 `in_transaction` 内，由事务回滚，单据不能保持 `completed`。
3. 库存与成本成功并提交之后才 `await` 应付。`should_auto_generate_payable_on_purchase_receipt` 为假，或 `total_amount <= 0` 时，与今天一样跳过应付，这不是失败。应付生成抛错时，调用方得到 `BusinessLogicError`；收货单可以仍是 `completed`。
4. 必检创建仍只落 `draft`，不增加工单已收数量，不调用库存、成本、应付。确认断言失败时单据保持 `draft`，不调用这三项。已是 `completed` 的确认早退不重复过账。
5. 库存参数保持今天 `_schedule_stock_for_outsource_receipt` 传给 `increase_stock` 的那一组：`source_type="outsource_material_receipt"`，`movement_type="outsource_receipt"`，幂等键 `outsource_material_receipt:{source_doc_id}:inc`，以及现有的仓库、批号、数量、操作人。
6. 不新增表、不新增状态字段、不改响应外层结构。

### Rules and Constraints

Tenant isolation:

- 沿用收货单、委外工单、库存与应付上现有的 `tenant_id` 条件。不新增跨组织查询。

Security and masking:

- `BusinessLogicError` 文案可以带收货单编码，不包含凭据、cipher 或内部路径。

Audit and lineage:

- 不新审计表。库存流水仍用上述幂等键。应付仍走现有 `link_finance_document_relation` 与 `record_finance_accounting_event`（事件 `OUTSOURCE_RECEIPT_TO_PAYABLE`）。

AI/rule-engine rules:

- 不涉及。

Database rules:

- 不新增 aerich 迁移。回滚靠现有 `in_transaction`。`InventoryService.increase_stock` 带 `@atomic_stock_change`，内部是 `reuse_or_begin_transaction`：调用方已经在 `in_transaction()` 里时复用外层事务，不另起提交。因此本单元在现有事务内调用 `increase_stock`，成本失败时库存与之一同回滚。

## 2. Plan

### Implementation Approach

- 免检创建与确认两条路径，把今天事务结束后的 `_schedule_outsource_receipt_followups` 拆开。
- 库存与成本移入各自已经写着 `async with in_transaction()` 的代码块，放在状态与工单数量 `save` 之后、事务块结束之前。`increase_stock` 的参数从现有 `_posting_payloads_for_outsource_receipt` 的 `stock_payload` 来。有 `stock_payload` 才调用成本钩子，入参是 `tenant_id` 与收货单 id。
- 事务块结束后再 `await` `_maybe_auto_create_payable_for_outsource_receipt`。`except` 里打 error 日志并 `raise BusinessLogicError`。应付函数内部今天的「记录后重新抛出」保留，由这一层收成业务错误，避免确认接口把未声明的异常漏成未处理错误。
- 采购入库的对照：`_confirm_receipt_posting` 在过账事务里做库存和 `on_purchase_receipt_confirmed`；`confirm_receipt` 在过账提交之后生成应付，失败抛 `BusinessLogicError`（文案含「已入库，但自动生成应付单失败」），入库单保持已入库。委外沿用这个拆法，文案改为委外收货单已完成但自动生成应付单失败。
- 删除四个 `_schedule_*` 方法，避免留下 `create_task` 路径。

### Affected Modules

- `src/apps/kuaizhizao/services/outsource_material_receipt_service.py`：`create_material_receipt`、`complete_material_receipt`、`_posting_payloads_for_outsource_receipt`、`_maybe_auto_create_payable_for_outsource_receipt`；删除四个 `_schedule_*`。
- `src/apps/kuaicaiwu/services/inventory_cost_service.py`：只改 `on_outsource_receipt_confirmed` 里关于 detached task 的注释。失败仍 `raise`。
- `src/apps/kuaizhizao/api/productions/outsource_receipt_api.py`：已把 `BusinessLogicError` 转成 400，本单元不改路由。
- `tests/apps/kuaizhizao/services/test_outsource_receipt_iqc_gate.py`
- 前端不改。

### Public Contracts

- `POST /outsource-material-receipts`、`POST /outsource-material-receipts/{receipt_id}/complete` 的 URL、method、认证头、响应模型不变。
- 成功时免检创建与确认的响应状态仍是 `completed`。必检创建的响应状态仍是 `draft`。
- 应付失败时确认与创建接口返回现有 400 结构：`detail.message` 加 `trace_id`。

### Persistence Changes

- 无。不新增列，不新增迁移。

### Transaction Boundaries

- 必检创建：只提交 `draft`。不回写工单数量，不调用库存、成本、应付。
- 免检创建与确认：同一个 `in_transaction` 内写 `completed`、回写工单数量、`increase_stock`、`on_outsource_receipt_confirmed`。任一步失败，事务回滚，单据不能保持 `completed`。
- 应付：上述事务提交之后 `await`。失败抛 `BusinessLogicError`，已提交的 `completed` 与库存、成本保留。
- `create_payable` 自带 `in_transaction()`。本单元不把它套进收货事务，也不改这个函数。

### Risks

- 应付失败后单据已是 `completed`。再次调用 `complete_material_receipt` 会走已完成早退，不会重试应付。本单元不补重试入口。
- `warehouse_wo_outsource_pull_service` 逐单 `await create_material_receipt`。某一单应付失败会抛出 `BusinessLogicError`，循环停在该单；此前已经提交的收货保持原样。不改这个循环。
- 成本钩子在收货行尚未提交时按 id 再查收货单。调用必须留在同一 `in_transaction` 内，使这次查询能看见未提交的收货行。

### Verification Strategy

- 在 `kuaigeyun-mes/riveredge-backend` 运行 `uv run pytest tests/apps/kuaizhizao/services/test_outsource_receipt_iqc_gate.py`。未跑通不得声称通过。
- 该文件今天无数据库，用 mock 的 `in_transaction`。断言改为：库存与成本在事务上下文内被 await；应付在上下文退出后被 await；库存或成本抛错时方法抛错且不调用应付；应付抛错时得到 `BusinessLogicError`，调用前状态可以已是 `completed`。
- 前端不改，不做新的浏览器验收。
