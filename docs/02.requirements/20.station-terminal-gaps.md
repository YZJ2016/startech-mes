- 轨道：**快格云** `kuaigeyun-mes`。工位触屏页面落在 `riveredge-frontend`，业务只打现有 `riveredge-backend`。Electron 壳落在 `kuaigeyun-mes/kuaigeyun-client/riveredge-app-station`，只放主进程。

- 设计：`docs/03.design/20.station-terminal-plan.md`
- 拍板：2026-09-29。下一端是触屏工位机。下文 **STN-D**、**STN-Q** 均已拍板。

## 用户故事

车间工位是一台 Windows 触屏电脑。它全屏常亮、开机自启，记住自己是哪一个工位，并能接扫码枪。屏幕上的页面来自服务器：操作员在已有登录会话下看工单、开工、暂停、恢复、结束、快捷报工、看工序文档，并发起四类安灯。计划、主数据、审批和财务仍在办公室浏览器里完成。

## 现网事实

核对口径：后端能力为本对话已核对的现有实现（2026-09-29）。前端页面分布为侧聊结论（2026-09-29）。本文按这些能力写需求，不另造后端没有的动作。

### 后端已有

专属前缀 `/api/v1/apps/kuaizhizao/station`。权限模块 `production-execution-terminal`。工位请求带头 `X-Client-Channel: station`。报工 `device_info` 带 `workstation_id`；交接班按工位汇总。

| 能力 | 现网 |
| --- | --- |
| 开工、撤回开工 | 在工单接口。撤回要求已开工且尚无报工 |
| 设备上下机 | 在工单接口，动作为 on / off |
| 暂停 | `StationService`。原因：缺料、待料、设备故障、换刀换模、质量异常、休息、其他 |
| 恢复、结束 | `StationService`。数量报工须合格数达到计划；状态报工按目标数量记合格。暂停中可以直接结束，并关闭停机 |
| 快捷报工 | `POST /reporting/quick`。接口现状支持数量、合格、不合格、工时、人员或小组；代报能力要求 reporting assign。可在同一事务记不良，之后可做上料 / 下料绑定，并由报工生成报废。方案 C 的默认工位角色不授 reporting assign，也不展示独立代报入口。渠道落「终端」 |
| 文档 | 工单列表有 ESOP / 图纸角标。工序文档含物料感知的 SOP 工步、工程图纸、物料附件、工单附件 |
| SOP 确认 | 按工单 + 工序 + 修订号 + 操作员确认。换版后重新确认。开工接口本身不调用本检查 |
| 安灯 | 质量→过程检验；物料→仅 `FULL_ORDER` 齐套叫料，且必须带工单；设备→故障单（须设备，级别轻微 / 一般 / 严重 / 紧急）；班长→站内消息。状态：发起 → 响应 → 关闭。仅发起人可撤销，且仅限未响应 |
| 人脸 | 登记、查看自己的、删除、比对。比对只识别操作员，不签发登录 |
| 上岗资质 | 有检查接口和维护接口。组织没有任何资质记录时，后端默认放行。开工接口本身不调用本检查 |
| 交接班 | 汇总与确认 |

### 前端已有（侧聊结论）

工位界面写在 `riveredge-frontend`，与办公室页面同一仓库。生产渠道按路径运行时计算：`/apps/kuaizhizao/production-execution/station` 及其子路径为 `station`，其余为 `pc`，不是工位单独构建注入。开发模式下 `VITE_CLIENT_CHANNEL` 只用于本地整站调试。触屏页使用本仓的 `TouchScreenTemplate`、`PremiumTerminalTemplate`。

| 页面 | 现网 |
| --- | --- |
| 主终端 | `kuaizhizao/pages/production-execution/work-orders/kiosk.tsx` 仍在，含绑定工位、工单列表、开工和报工。`kuaizhizao/index.tsx` 写明生产终端路由已下线，`/apps/kuaizhizao/production-execution/terminal` 被注释，文件还留着 |
| 仍挂在星制造路由上的触屏页 | 工单详情 `work-orders/:id/kiosk`、报工 `reporting/kiosk`、SOP `sop-viewer/kiosk`、图纸 `drawing-viewer/kiosk`、程序 `program-viewer/kiosk`。这些页走办公室那一套站点 |
| 尚无前端调用 | 安灯、刷脸、上岗资质、交接班。后端接口在，页面未写 |

侧聊结论：缺的是两层。一层是把已有触屏页收成一个仍在线的工位入口（并补上还没有页面的能力）。另一层是 Electron 壳去打开服务器上的这个入口。只有壳、入口仍是下线终端或办公室页面时，产线电脑打不开工位闭环。

### 部署现状

`fast-deploy` 今天有 `install-h5` 与 `build.mobile.web.sh`。仓库说明里的「终端仓 = 手机端 + 工位机」和这些脚本不一致：脚本覆盖的是手机端 Web。工位机 `.exe` 的打包脚本不在本仓，也不在 `fast-deploy` 的现有脚本里。本文把这一点记为已知缺口，不在本文补部署脚本。

标签装箱页面路径为 `/label-station`，属于另一条产线功能。本文覆盖的是触屏工位机。

## STN-D — 已拍板

- [x] **STN-D1** 产品顺序。下一端是触屏工位机。电视看板、小程序、企业微信不在本文排期。
- [x] **STN-D2** 交付形态。Windows Electron 桌面壳，交付物是 `.exe`（安装向导或便携都是 exe）。壳做全屏常亮、开机自启、记住本机工位、接扫码枪。壳升级慢。打包脚本不在本仓；本文只记录现状。
- [x] **STN-D3** 页面落点。工位触屏页面与办公室页面都在 `riveredge-frontend`，两个入口。生产渠道按路径运行时计算：`/apps/kuaizhizao/production-execution/station` 及其子路径为 `station`，其余为 `pc`，不是工位单独构建注入。开发模式下 `VITE_CLIENT_CHANNEL` 只用于本地整站调试。办公室继续用浏览器。登录、权限、接口封装与 PC 共用。改界面随服务器发布，产线电脑上的 `.exe` 不必为此重装。（页面仓库划分同时是侧聊结论。）
- [x] **STN-D4** 加载方式。Electron 加载服务器上的工位页面。安装包只含壳。界面与 API 一起发布。
- [x] **STN-D5** 壳的仓库。`kuaigeyun-mes/kuaigeyun-client/riveredge-app-station` 只放 Electron 主进程。壳里没有工单、报工、安灯界面。业务 UI 留在 `riveredge-frontend`。（侧聊结论。）
- [x] **STN-D6** 本机工位。这台电脑对应哪一个工位，由 Electron 壳记在本机，取值是星制造已有工位。页面上的绑定工位与壳记住的值指向同一工位。身份来源是本机配置，本文不单建「终端设备」登记表。（侧聊结论：记住本机工位是壳的职责。）
- [x] **STN-D7** 写入路径。业务只打现有后端。工序开工、撤回开工、设备上下机走工单接口。暂停、恢复、结束走 `StationService`。快捷报工走 `POST /reporting/quick`。请求头 `X-Client-Channel: station`。报工 `device_info` 带 `workstation_id`，交接班才按工位汇总。
- [x] **STN-D8** 刷脸。刷脸只识别操作员，不签发登录。终端必须先有登录会话。
- [x] **STN-D9** 开工前检查。SOP 确认与上岗资质是独立检查接口，开工接口本身不调用它们。页面要卡控时，先查再放行。组织无任何资质记录时，后端默认放行。
- [x] **STN-D10** 第一期能力边界。第一期用上一节「后端已有」的执行闭环。SOP 硬卡控和上岗资质硬卡控是页面开关，默认不挡开工，等现场要卡控再开。计划、主数据、审批、财务留在办公室 PC。第一期页面与快捷报工见 **STN-Q1**、**STN-Q4**。
- [x] **STN-D11** 部署缺口只记录。`fast-deploy` 现有脚本不打包工位机。本文不实现部署脚本。
- [x] **STN-D12** 工位产品边界。工位入口使用独立 `StationLayout`，不展示 PC 侧栏、应用切换、UniTabs、系统配置、个人偏好或任意地址跳转。Electron 只允许认证必需路径、锁屏与工位入口及其子路径，不再以「同源即可导航」作为边界。
- [x] **STN-D13** 终端账号。正式预设角色为「工位终端」，编码 `STATION_TERMINAL`，`role_type=station`、`functional_domain=production`、首页为 `/apps/kuaizhizao/production-execution/station`。管理员通过现有「加载预设角色」按租户主动、幂等创建；迁移不静默创建业务角色。
- [x] **STN-D14** 角色纯度。终端账号只能绑定 `station` 类型角色，不得与 `internal` 或 `external` 混挂。Electron 拒绝非纯工位账号并退出当前会话；纯工位账号从普通浏览器登录也始终进入工位入口，访问其他 PC 路由时重定向回工位入口。
- [x] **STN-D15** 授权边界。`window.stationShell`、路径、`workstationId` 与 `X-Client-Channel` 只标识客户端上下文，不作为授权证明。服务端继续按租户、登录用户和显式权限码鉴权。预设角色使用显式最小权限集合，不用宽泛权限前缀自动扩权。
- [x] **STN-D16** 操作员确认。点选姓名只产生候选人；刷脸或员工码解析结果与候选人一致后，才激活当前操作员。第一期不允许主管码、终端密码、填写原因或其他降级。当前操作员只改变业务与审计归属，不改变登录会话，不继承个人角色权限。
- [x] **STN-D17** 操作员会话。服务端使用数据库操作员会话，绑定租户、终端账号、工位、操作员和确认方式。客户端只持随机不透明凭据，数据库只存凭据哈希；凭据仅在当前页面内存保存，不写 Web Storage 或 Electron 配置。会话不设固定时长和闲置超时，只在显式换人、终端账号退出或下一次确认时关闭；页面刷新、Electron 重启、异常退出或断电恢复后不恢复凭据，必须重新确认。
- [x] **STN-D18** 写操作门禁。纯工位账号未持有效操作员会话时可查看工单与当前任务资料，但不得开工、报工、安灯、交接或执行其他产生业务记录的动作。现有业务 URL、HTTP method、登录认证头和响应外层结构不变；新增独立的操作员确认、关闭、状态接口与工位业务凭据头。

## STN-Q — 已拍板

- [x] **STN-Q1** 第一期页面。同一工位入口铺满现有闭环：绑定工位、开工到结束、快捷报工、四类安灯、ESOP / 图纸 / 工序文档、设备上下机、刷脸切换操作员、交接班、上料下料、报废，以及已在路由上的程序查看。SOP 确认与上岗资质仍是默认关闭的页面开关，不挡开工。
- [x] **STN-Q2** 登录会话。每台工位一个长期登录的纯 `station` 终端账号。点选只产生候选人；刷脸或员工码确认后才切换当前操作员，不签发新的登录，也不提升权限。壳保持常亮并记住本机工位。
- [x] **STN-Q3** 入口 URL。在线工位入口固定为 `/apps/kuaizhizao/production-execution/station`，子能力均在该前缀下。
- [x] **STN-Q4** 报工。第一期默认工位角色只开放已确认当前操作员的本人报工与小组报工，不授 `kuaizhizao:production-execution-reporting:assign`，不展示独立代报入口。都走现有 `POST /reporting/quick`，渠道记为终端。以后如需代报，单独建立纯 `station` 角色并另行评审。
